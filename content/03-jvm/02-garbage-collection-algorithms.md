## 电梯版回答

基础算法有三个：标记清除、标记复制、标记整理。标记清除实现简单但不连续、容易产生碎片；标记复制没有碎片但要浪费一半空间；标记整理没有碎片也不浪费空间，但移动对象要更新引用，代价高。分代收集就是把这三个算法用在对的地方——研究表明绝大多数对象朝生夕死，所以新生代用标记复制，只留一小块 Survivor 做复制目标，浪费很小、回收又快；老年代对象存活率高，复制代价太大，所以用标记清除或标记整理。现代收集器还会加上并发标记，用三色标记加读写屏障来解决标记期间用户线程修改引用的问题。

## 展开讲解

### 三个基础算法

**标记清除（Mark-Sweep）**

```
标记：从 GC Roots 出发遍历，可达对象打标
清除：遍历堆，回收未标记对象
```

- 优点：实现最简单，不需要移动对象
- 缺点：**产生内存碎片**；清除阶段要遍历整个堆，
  效率随堆大小下降；碎片多了以后大对象分配失败，
  会**提前触发一次 Full GC**

**标记复制（Mark-Copy）**

把内存分成两块，每次只用一块。回收时把存活对象**复制**到另一块，
然后整块清空。

- 优点：无碎片；分配只用移动指针（bump the pointer），极快；
  回收成本只与**存活对象数**成正比，与堆大小无关
- 缺点：**空间利用率只有一半**（或按比例浪费）；
  存活对象多时复制量大

**标记整理（Mark-Compact）**

标记后把存活对象**向一端移动**，然后清理边界外的内存。

- 优点：无碎片，也不浪费空间
- 缺点：移动对象后必须**更新所有指向它们的引用**，
  这是 stop-the-world 的代价；且要多次遍历（标记、计算新地址、调整引用、移动）

### 三者的取舍

| 算法 | 碎片 | 空间利用率 | 回收成本 | 何时便宜 |
|---|---|---|---|---|
| 标记清除 | 有 | 高 | 与堆大小成正比 | 存活率高时 |
| 标记复制 | 无 | 低（约 50%） | 与存活对象数成正比 | **存活率低时** |
| 标记整理 | 无 | 高 | 高（需移动+改引用） | 存活率高时，且在意碎片 |

关键洞察是**复制算法的成本只取决于存活对象**。
如果一批内存里 98% 都是垃圾，复制算法几乎不需要做什么工作；
反过来如果 98% 都存活，复制就变成了灾难。

这正好对应了分代假设。

### 分代收集的依据

**弱分代假说（Weak Generational Hypothesis）**：绝大多数对象
都是朝生夕死的。这不是空想，而是大量实测结论——
比如经典的统计是新生代对象中约 98% 活不过第一次 GC。

既然新生代「大部分是垃圾」，就适合**标记复制**；
老年代「大部分是活的」，就适合**标记清除或标记整理**。

### 新生代的复制怎么省空间

朴素复制要浪费一半空间，实际 HotSpot 用了一种巧妙的调整：

```
新生代 = Eden + Survivor0 + Survivor1     默认比例 8 : 1 : 1
```

每次只用 **Eden + 一块 Survivor** 作为分配区
（所以叫 From / To，下一轮角色互换）：

```
本轮：使用 Eden(8) + S0(1)，S1(1) 空闲
GC：  存活对象从 Eden + S0 复制到 S1
      清空 Eden 和 S0
下轮：使用 Eden(8) + S1(1)，S0(1) 空闲   ← 角色互换
```

所以真正浪费的只有 **1/10**，而不是 50%。
这是复制算法能用在新生代的前提——否则浪费一半堆是不可接受的。

问题在于：**如果存活对象超过 Survivor 的容量怎么办**？
这时需要**空间分配担保**：把装不下的对象直接晋升到老年代。
担保能成立的前提是「老年代有足够空间」，
所以 Minor GC 前会先检查老年代的可用连续空间
（`-XX:+HandlePromotionFailure` 控制这个检查的历史行为）。

### 对象何时晋升老年代

四条路径：

1. **年龄达到阈值**：每熬过一次 Minor GC 年龄加一，
   到 `-XX:MaxTenuringThreshold`（默认 15，CMS 是 6）晋升
2. **Survivor 装不下**：空间分配担保触发，直接进老年代
3. **大对象直接进老年代**：`-XX:PretenureSizeThreshold`
   设阈值，超过就绕过新生代。目的是避免大对象在
   Eden 和 Survivor 之间反复复制
4. **动态年龄判定**：如果 Survivor 中**相同年龄对象的总大小
   超过 Survivor 空间的一半**，则年龄大于等于该年龄的对象
   直接晋升，不必等到 15 岁

第 4 条最容易被忽略，但它是真实存在的优化：
一批同期的对象如果已经占了 Survivor 一半，说明它们大概率会继续存活，
继续来回复制不划算，不如直接进老年代。

### 并发标记的难题：三色标记

现代收集器（CMS、G1、ZGC）都要**并发标记**——标记线程与用户线程
同时跑，否则一次标记就要停顿整个堆，堆越大停顿越久。

三色标记把对象分成三类：

| 颜色 | 含义 |
|---|---|
| 白色 | 尚未被访问，标记结束仍是白色即为垃圾 |
| 灰色 | 自己已标记，但引用还没遍历完 |
| 黑色 | 自己和所有引用都已遍历完 |

并发的问题在于：**用户线程可能在标记期间修改引用**，
导致「漏标」——一个本该存活的对象被当成垃圾回收。

漏标必须同时满足两个条件（缺一不可）：

```
① 赋值器插入了一条从黑色对象到白色对象的引用
② 赋值器删除了全部从灰色对象到该白色对象的引用
```

破坏任意一个条件就能避免漏标，于是有两种屏障方案：

| 方案 | 破坏的条件 | 做法 | 代价 | 使用者 |
|---|---|---|---|---|
| **增量更新** | ① | 记录新增的引用，重新标记时以黑色对象为根再扫一遍 | 需要重新标记阶段 | CMS |
| **原始快照 SATB** | ② | 记录被删除的引用，按标记开始时的快照标记 | 会产生浮动垃圾 | G1、Shenandoah |

**读屏障 vs 写屏障**：SATB 用**写屏障**记录删除动作
（在引用被覆盖前把旧值记下来），增量更新也用写屏障记录插入动作。
ZGC 用**读屏障**——在读取引用时做染色指针校验，这样连并发移动对象
都能支持。

### 记忆集与卡表

跨代引用会带来一个麻烦：做 Minor GC 时，如果一个老年代对象
引用了新生代对象，那这个新生代对象是存活的，但 GC Roots
里找不到它（Rooots 是老年代对象）。难道要扫描整个老年代？

不用。用**记忆集（Remembered Set）**记录「老年代指向新生代的引用」
在哪些区域，做 Minor GC 时只扫这些区域就行。HotSpot 的实现叫
**卡表（Card Table）**：把老年代按 512 字节切成一张卡页，
用一个字节表示该卡页是否有跨代引用。

写入跨代引用时通过**写屏障**把对应卡页标记为 dirty，
Minor GC 时只扫描 dirty 的卡页。

代价是**伪共享（false sharing）**：一个卡页 512 字节里只要有
一个对象引用了新生代，整张卡页都要被扫。卡页大小是
「精确性」与「扫描开销」之间的折中。

## 追问链

### Q1: 为什么新生代用复制而不是标记整理？

核心原因是**成本模型**。复制算法的成本正比于**存活对象数**，
而标记整理的移动成本正比于**存活对象数加上遍历整个空间的成本**，
还要额外更新引用。

新生代 98% 是垃圾，存活对象极少：

```
复制：搬走 2% 的对象，清空整块 —— 几乎不花时间
整理：标记全部、计算新地址、调整引用、移动 2% —— 仍有全量遍历开销
```

而且复制天然无碎片，分配只需移动指针，这对**分配极其频繁**的
新生代格外重要。

再看空间账：因为 Survivor 只占新生代的 1/10，
真正浪费的是 10% 而不是 50%——代价可以接受。

#### Q1.1: 那为什么老年代不能用复制？

因为老年代**存活率高**。假设老年代有 4GB 且 80% 存活：

- 复制方案要准备一块能装下 3.2GB 的空间，
  等于把老年代的有效容量砍掉一半以上
- 复制 3.2GB 的对象是实打实的内存拷贝，停顿时间无法接受

所以老年代用**标记清除**（CMS，接受碎片）或**标记整理**
（Serial Old、Parallel Old，接受移动代价）。G1 则换了思路：
把堆切成小 Region，每次只回收「回收收益最高」的那批 Region，
对单个 Region 内部用复制（存活对象少时收益高），
把复制算法用在了「局部存活率低」的地方，
从而绕开了「老年代存活率高」这个约束。

##### Q1.1.1: 那 Survivor 里对象装不下会发生什么？

走**空间分配担保**：装不下的对象直接晋升到老年代。

```
Minor GC 前检查：
  老年代可用连续空间 >= 新生代所有对象总大小？
    是 → Minor GC 是安全的，即使全部晋升也能放下
    否 → 检查 -XX:HandlePromotionFailure：
           允许担保失败 → 尝试 Minor GC（可能触发 Full GC 兜底）
           不允许       → 直接 Full GC
```

担保的前提是「老年代有地方放」。如果老年代本身就快满了，
这次晋升会让它溢出，于是提前触发 Full GC 清理老年代。

这解释了线上常见的现象：**Minor GC 频率突然升高，
且伴随 Full GC**。往往是某段代码制造了大量中等生命周期对象，
撑爆了 Survivor，被迫提前晋升，进而把老年代一起拖下水。

### Q2: 三色标记为什么会漏标？怎么解决？

漏标必须**同时满足**两个条件：

```
① 黑色对象新增了对白色对象的引用
② 从灰色对象到该白色对象的引用被全部删除
```

为什么缺一不可：

- 只有 ①：因为还有灰色对象指向它，灰色对象遍历时会扫到它
- 只有 ②：因为它已经被灰色扫到、变成灰色了（或者即将被扫到）
- 两者都有：它既不会被灰色对象扫到（引用被删），
  也不会被黑色对象扫到（黑色不会再遍历），于是被当成垃圾

两种破坏方式对应两种屏障：

**增量更新（Incremental Update）——破坏 ①，CMS 使用**

```java
// 写屏障：当黑色对象新增指向白色对象的引用时
// 把这个黑色对象记录下来
void post_write_barrier(Object black, Object white) {
    if (is_marked_black(black) && is_white(white)) {
        record(black);      // 加入待重扫集合
    }
}
```

重新标记阶段以这些记录为根再扫一遍。
代价是需要一个**重新标记（Remark）阶段**，
这个阶段仍需 STW（虽然可以并行）。

**原始快照（SATB, Snapshot-At-The-Beginning）——破坏 ②，G1 使用**

```java
// 写屏障：引用被覆盖之前，把旧值记录下来
void pre_write_barrier(Object field, Object old_value) {
    if (!is_null(old_value) && is_white(old_value)) {
        push_to_satb_queue(old_value);   // 记录旧值
    }
}
```

按「标记开始那一刻的快照」来标记：只要在快照里是活的，
就一直当作活的。这样就不需要重新标记阶段。

代价是会产生**浮动垃圾（Floating Garbage）**——
标记期间新产生的垃圾这一轮收不掉，留到下一轮。
这通常可以接受，因为浮动垃圾的量正比于并发标记期间的分配速率，
远小于整个堆。

#### Q2.1: 为什么 G1 选 SATB 而 CMS 选增量更新？

主要原因是**停顿目标**。

CMS 面向的是「低停顿」，但它的增量更新需要一个
**重新标记阶段**，而这个阶段必须 STW。虽然可以并行加速，
但堆越大、标记越久，这个阶段就越长，与「低停顿」的目标冲突。

G1 的重新标记阶段本来就很短（它只需要处理 SATB 队列，
不像增量更新那样需要重新遍历），而且 G1 的停顿目标
（`-XX:MaxGCPauseMillis`，默认 200ms）比 CMS 更宽松，
SATB 产生的浮动垃圾也在可接受范围内。

另一个细节：G1 的 Region 结构让它可以在**新生代回收时顺带处理
SATB 队列**，把成本摊薄到多次 Young GC 里，而不是集中在一次
Remark 上。

## 常见坑

- **说「标记清除会产生碎片所以不能用」** —— CMS 就是标记清除，
  靠 `-XX:CMSFullGCsBeforeCompaction` 定期整理来缓解，
  在低停顿场景下碎片可控
- **说「分代收集是 Java 规范规定的」** —— 分代是**实现层面的优化**，
  JVM 规范并没有要求分代。ZGC 就是不分代的
  （ZGC 在 JDK 21 才引入分代）
- **认为复制算法固定浪费一半空间** —— 新生代靠
  Eden : Survivor = 8 : 1 : 1 把浪费压到 1/10
- **忘记空间分配担保** —— 只答「Survivor 装得下就复制」，
  说不出装不下时直接晋升老年代
- **忽略动态年龄判定** —— 除了固定的 15 岁阈值，
  还有「同年龄对象总大小超过 Survivor 一半就提前晋升」这条规则
- **把三色标记和 GC Roots 混淆** —— 三色标记是**扫描过程的表示**，
  GC Roots 是**扫描的起点**，两者是不同层次的概念
- **说「写屏障是给用户线程加锁」** —— 屏障是 GC 与赋值器之间的
  同步手段，在 JIT 编译后是几条指令，不是锁
- **认为并发标记可以完全不在 STW 下完成** —— 初始标记（找 GC Roots）
  和重新标记/最终标记仍需短暂 STW

## 加分点

- 能讲清**三色标记漏标的两个必要条件必须同时成立**，
  并据此说明增量更新破坏条件①、SATB 破坏条件②，这是理解
  CMS 与 G1 差异的关键
- 知道**浮动垃圾**是 SATB 的固有代价，并能把它与
  「为什么 G1 不需要冗长的 Remark 阶段」联系起来
- 提到**记忆集与卡表的伪共享问题**：卡页 512 字节的粒度是
  「精确性 vs 扫描开销」的折中，卡页太小则结构本身占空间、
  太大则打扫范围
- 能把成本模型说清楚：**复制成本 ∝ 存活对象数，整理成本 ∝ 全堆遍历**。
  由此推出「G1 用 Region 把复制算法用在局部存活率低的地方」
  这个设计动机，而不是死记「新生代复制、老年代整理」
- 知道 `PretenureSizeThreshold` 让大对象绕过新生代的目的
  是**避免在 Eden 和 Survivor 之间反复复制大对象**
- 提到 ZGC 用**读屏障 + 染色指针**，从而支持并发移动对象，
  把停顿做到与堆大小无关（10ms 以内），
  并能说明这是「以吞吐换停顿」的取舍

## 版本差异

| 版本 | 差异 |
|---|---|
| Java 8 | 默认收集器为 Parallel Scavenge + Parallel Old；CMS 已被标记为废弃（deprecated） |
| Java 9 | G1 成为默认收集器；CMS 正式废弃，并明确在后续移除 |
| Java 11 | ZGC 实验性引入（需 `-XX:+UnlockExperimentalVMOptions`） |
| Java 14 | CMS 彻底移除 |
| Java 15 | ZGC 与 Shenandoah 转正（ZGC 需 `-XX:+UseZGC`） |
| Java 21 | **ZGC 支持分代**（`-XX:+UseZGC -XX:+ZGenerational`），对新生代的短命对象做针对性回收，吞吐明显改善 |
