## 电梯版回答

一个对象在内存里分三块：对象头、实例数据、对齐填充。对象头在 64 位 HotSpot 上默认是 12 字节，由 8 字节的 Mark Word 和 4 字节的类型指针组成。Mark Word 用位域复用的方式存哈希码、GC 分代年龄、锁状态标志、偏向线程 ID 等；类型指针指向方法区里的类元数据，虚拟机靠它知道这个对象是哪个类的实例。实例数据是字段值，JVM 会把字段按宽度从大到小重排以减少 padding，父类字段排在子类字段前面。最后做对齐填充，HotSpot 默认按 8 字节对齐，所以任何对象的大小都是 8 的倍数。指针压缩是另一个关键优化，开启 `-XX:+UseCompressedOops` 后 8 字节的对象引用被压成 4 字节，堆小于约 32GB 时有效；堆一旦超过这个规模压缩就失效，引用重新变回 8 字节。对象创建要走类加载检查、分配内存、内存置零、设置对象头、执行构造器五步，分配时优先走 TLAB 以免加锁。

## 展开讲解

### 内存布局总览

以 64 位 HotSpot、开启压缩指针（默认）为例：

```
┌──────────────────────────────┐
│  对象头 Object Header         │
│   ├─ Mark Word        8 字节  │
│   └─ Klass Pointer    4 字节  │  ← 未压缩时 8 字节
├──────────────────────────────┤
│  实例数据 Instance Data       │  ← 字段值，按宽度重排
├──────────────────────────────┤
│  对齐填充 Padding             │  ← 补到 8 的整数倍
└──────────────────────────────┘
```

数组对象在对象头里还多 4 字节的**数组长度**：

```
数组对象头 = Mark Word(8) + Klass Pointer(4) + length(4) = 16 字节
```

所以数组的元数据开销比普通对象大，这也是为什么小数组（比如 `byte[1]`）的实际内存占用远大于数据本身。

### 对象头之一：Mark Word

Mark Word 只有 8 字节（64 位），却要存哈希码、分代年龄、锁状态等好几类信息，办法是**位域复用**——同一段二进制在不同状态下有不同解释：

| 位数 | 内容 | 说明 |
|---|---|---|
| 31 位 | identity hash code | 调用 `Object.hashCode()` 后才写入，延迟生成 |
| 4 位 | GC 分代年龄 | 每熬过一次 Minor GC 加 1 |
| 1 位 | 偏向锁标志 biased_lock | 是否启用偏向 |
| 2 位 | 锁状态 lock | 无锁 / 偏向 / 轻量级 / 重量级（见锁升级） |

分代年龄只有 4 位，最大能表示 15，所以 `-XX:MaxTenuringThreshold` 的默认上限也是 15——对象年龄到 15 就必须进老年代，即使还没达到阈值，也没有位数可加了。

Mark Word 的内容会随锁状态改变：

```
无锁    → hash + age + lock=01
偏向锁  → 偏向线程 ID + epoch + age + lock=01
轻量级  → 指向栈中 Lock Record 的指针 + lock=00
重量级  → 指向 monitor 对象的指针 + lock=10
GC 标记 → 转发指针 + lock=11
```

注意 `hashCode` 一旦计算过就被写进 Mark Word，之后即使锁状态变化也**不能覆盖这一段**，这就是「偏向锁与 hashCode 有冲突」的根源之一（偏向锁需要占用原本放哈希码的位置）。

### 对象头之二：类型指针（Klass Pointer）

类型指针指向方法区（元空间）中该类的 `InstanceKlass` 元数据，JVM 靠它判断对象的实际类型，方法调用、`instanceof`、类型检查、GC 的类型相关处理都要用它。

在开启指针压缩时它是 4 字节，否则是 8 字节。`-XX:+UseCompressedClassPointers` 控制，默认随 `-XX:+UseCompressedOops` 一起开启，堆超过压缩指针可寻址范围时两者都会失效。

### 实例数据与字段重排

实例数据里存真正的字段值，但字段的排列顺序**不是**你写代码的顺序，也不是简单的声明顺序，HotSpot 会做重排：

1. **父类字段先于子类字段**。父类定义的字段在前，子类新增的字段在后。
2. **同一层内按类型宽度从大到小排列**：`long`/`double`（8 字节）→ `int`/`float`（4 字节）→ `short`/`char`（2 字节）→ `byte`/`boolean`（1 字节）。
3. **引用类型字段通常排在最后**（压缩后是 4 字节，但仍单独成组）。

重排的目的是**减少对齐填充**。举例：

```java
class Bad {
    byte a;     // 1 字节
    long b;     // 8 字节
    byte c;     // 1 字节
}
// 若不重排：1 + 7(padding) + 8 + 1 + 7(padding) = 24 字节实例数据
// 重排为 long、byte、byte：8 + 1 + 1 + 6(padding) = 16 字节
```

重排不是语言规范保证的行为，而是 HotSpot 的实现细节，写代码时不该依赖字段顺序做序列化或内存操作。

### 对齐填充与对象大小

HotSpot 默认按 **8 字节对齐**（`-XX:ObjectAlignmentInBytes`，默认 8），所以**对象总大小必然是 8 的倍数**，不足的部分用 padding 补齐。对齐的意义在于让 CPU 的访存保持在字边界上。

举例算几个常见对象（64 位、开启压缩指针）：

| 对象 | 组成 | 大小 |
|---|---|---|
| `new Object()` | 8 + 4 头 + 0 字段 + 4 对齐 | 16 字节 |
| `new Integer(1)` | 8 + 4 头 + 4 int + 0 对齐 | 16 字节 |
| `new Long(1L)` | 8 + 4 头 + 8 long + 4 对齐 | 24 字节 |
| `int[4]` | 8 + 4 + 4 长度 + 16 数据 | 32 字节 |

`Integer` 是最常被拿来考的例子：**8 字节 Mark Word + 4 字节类型指针 + 4 字节 int 值 = 16 字节，正好对齐**，所以一个 `int` 装进 `Integer` 要多花 12 字节的元数据开销。这也是「优先用基本类型而非包装类型」在内存敏感场景下的量化依据。

### 指针压缩（Compressed Oops）

64 位 JVM 的引用天然是 8 字节，是 32 位 JVM 的两倍，这会让同样的程序占用更多内存、也给缓存带来更大压力。HotSpot 的解法是指针压缩：

- `-XX:+UseCompressedOops`（默认 `true`）把对象引用压成 4 字节
- `-XX:+UseCompressedClassPointers`（默认 `true`）把对象头里的类型指针压成 4 字节

它为什么可行：JVM 里的对象本来就按 8 字节对齐，**地址的低 3 位永远是 0**，没必要存。于是 4 字节的引用不再直接存字节地址，而是存一个「按 8 字节为单位的偏移量」，使用时左移 3 位还原：

```
实际地址 = 压缩引用 << 3
4 字节能表示 2^32 个偏移单位 × 8 字节 = 2^35 字节 = 32GB
```

所以压缩指针的**可寻址上限是 32GB**：

- 堆小于约 32GB：压缩指针生效，引用 4 字节
- 堆超过 32GB：压缩指针自动失效，引用回到 8 字节

由此得到一个常被面试问到的结论：**把堆从 31GB 调到 33GB，可用内存不一定变多，反而可能更少**。因为引用从 4 字节涨到 8 字节，同样的对象图整体变大，而且对象头也变大了（Mark Word 不变，类型指针从 4 变 8）。经验规则是：**要么把堆控制在 32GB 以内享受压缩指针，要么干脆远超 32GB（比如 48GB 以上），让多出来的物理内存真正换来可用的对象空间**。落在刚过 32GB 的位置是最亏的。

### TLAB：线程本地分配缓冲

分配内存时，如果堆是规整的（有压缩整理能力，如 Serial、ParNew、Parallel、G1 的 region 内），JVM 用**指针碰撞（bump-the-pointer）**：维护一个指针，分配时把指针往后挪对象大小的距离。这本身很快，但多线程同时分配就需要同步。

**TLAB（Thread Local Allocation Buffer）**把 Eden 区切出一块块线程私有的小区域：

- `-XX:+UseTLAB` 默认开启
- 每个线程在自己的 TLAB 里用指针碰撞分配，**不需要任何锁**
- TLAB 用完后申请一块新的（`-XX:+ResizeTLAB` 默认开启，动态调整大小）
- TLAB 放不下但对象本身能放进 Eden 时，走共享 Eden 的慢路径（需要 CAS 之类的同步）

TLAB 也会带来一点空间浪费：一个对象放不进 TLAB 剩余空间时，剩余部分可能被闲置，`-XX:TLABWasteTargetPercent`（默认 1）控制可接受的浪费比例。注意 **TLAB 仍在堆内**，只是把 Eden 做了逻辑切分，和逃逸分析带来的「栈上消除分配」是两件不同的事。

### 对象的完整创建过程

`new` 一条指令背后有完整流程：

1. **类加载检查**。`new` 的操作数是常量池里的类符号引用，JVM 先检查这个类是否已加载、解析、初始化；没有则触发类加载流程。
2. **分配内存**。根据堆是否规整选择指针碰撞或空闲列表；优先在 TLAB 内分配，避免同步。
3. **内存置零**。把分配到的空间清零，保证实例字段能拿到默认值（数值 0、`false`、`null`）。TLAB 分配的内存通常已经是干净的。
4. **设置对象头**。写入 Mark Word（哈希码此时还是空的，要等 `hashCode()` 被调用才填；分代年龄初始为 0；锁状态无锁）和类型指针。
5. **执行构造器 `<init>`**。按父类到子类的顺序执行实例初始化，包括字段初始化和构造方法体。

注意第 3 步和第 4 步之间：对象已经是「存在」的，但字段还是默认值、构造器还没跑。这也是为什么构造函数里把 `this` 传出去很危险（对象还没构造完就泄漏）。

### 用 JOL 看真实布局

**JOL（Java Object Layout）**是 OpenJDK 提供的对象布局分析工具，能直接打印真实的内存布局：

```java
// 依赖：org.openjdk.jol:jol-core
Object obj = new Object();
System.out.println(ClassLayout.parseInstance(obj).toPrintable());
```

输出里能看到 object header 的实际字节数、字段偏移量和总大小，是验证「指针压缩是否生效」「对象到底几字节」最直接的工具。注意布局与 JVM 版本、是否开启压缩指针、是否开启偏向锁都有关，换一个 JVM 参数结果就可能不同。

## 追问链

### Q1: Mark Word 只有 8 字节，怎么存得下哈希码、GC 年龄、锁标志这么多信息？

靠**位域复用**：同一块 64 位空间，在不同锁状态下按不同规则解释。无锁时里面放哈希码、年龄和锁标志；偏向锁时放偏向线程 ID 和 epoch；轻量级锁时变成指向栈上 Lock Record 的指针；重量级锁时变成指向 monitor 的指针；GC 期间又变成转发指针。

也就是说 Mark Word 是一个「会根据对象当前状态改变含义的联合体（union）」，同一时刻只会以一种状态的含义为准，所以不需要真的存下全部字段。

#### Q1.1: 那不同状态之间是怎么切换的？

锁状态由低到高升级，不可逆（常规情况下）：

```
无锁(01) → 偏向锁(01, 偏向位=1) → 轻量级锁(00) → 重量级锁(10)
```

当线程第一次获取偏向锁时，用 CAS 把自己的线程 ID 写进 Mark Word；出现第二个线程竞争就撤销偏向、升级为轻量级锁，Mark Word 换成指向当前线程栈帧里 Lock Record 的指针；自旋失败、竞争进一步加剧就升级为重量级锁，Mark Word 换成指向 ObjectMonitor 的指针，竞争线程进阻塞队列。

升级过程本质是**用更大的获取成本换取更强的并发处理能力**，且一旦升到重量级就基本不会降回去。

##### Q1.1.1: 那分代年龄为什么只给了 4 位？够用吗？

因为对绝大多数对象来说够用。4 位最大 15，`-XX:MaxTenuringThreshold` 的默认值也是 15，二者是对齐的。HotSpot 的判断逻辑是「年龄达到阈值就晋升老年代」，而默认情况下对象要熬过 15 次 Minor GC 才晋升，绝大多数对象根本活不到那么久（弱分代假说），能活到 15 次的通常是长生命周期对象，早点晋升反而合适。

另外位数不是想加就加的：Mark Word 只有 64 位，已经塞了哈希码、锁状态、偏向信息，再加宽年龄字段就要牺牲别的字段或干脆超出长度。

### Q2: 为什么堆一旦超过 32GB，指针压缩就失效了？

因为压缩引用本质上存的是「以 8 字节为单位的偏移量」。4 字节可以表示 `2^32` 个不同的偏移单位，每个单位 8 字节，所以可寻址范围是：

```
2^32 × 8 = 2^35 字节 = 32GB
```

堆的地址范围一旦超过 32GB，就没法再用一个 4 字节的偏移量表达所有对象的地址，压缩指针自动关闭（`-XX:+UseCompressedOops` 虽然还是 `true`，但实际不生效），引用恢复成 8 字节。

#### Q2.1: 失效之后会发生什么？为什么反而更费内存？

失效带来两个「变大」：

1. **每个对象引用从 4 字节变回 8 字节**。对象图越复杂、引用越多，膨胀越明显。
2. **对象头里的类型指针也从 4 字节变回 8 字节**，意味着每个对象至少多 4 字节。

结果就是同样的对象图占用更多堆内存，而且 `32GB × (32/40)` 之类换算下来，堆虽然名义上大了几 GB，能装的对象数可能反而更少，同时更大的对象图对 CPU 缓存也不友好。

经验做法：**要么把堆控制在 32GB 以内，要么一步跨到远超 32GB（比如 48GB 甚至更大）**，不要停在 33GB 这种刚过界的位置，那是最不划算的。另一个选择是换用 ZGC 这类不使用压缩指针、但通过染色指针（colored pointers）和读屏障来处理大堆的收集器，不过那需要单独评估。

##### Q2.1.1: 那 `-XX:ObjectAlignmentInBytes=16` 能突破这个限制吗？

能扩大范围，但有代价。把对象对齐从 8 字节改成 16 字节，压缩引用的偏移单位就从 8 变成 16，可寻址范围变成 `2^32 × 16 = 64GB` 左右。也就是说通过牺牲对齐来换取更大的压缩指针覆盖范围。

代价是**每个对象都要按 16 字节对齐**，小对象（比如 `Integer` 从 16 字节涨到 16 字节倒没变，但很多 12/20 字节的对象会向上取整）会浪费更多 padding，整体内存利用率下降。而且这个参数影响面很大，要整个 JVM 生命周期保持一致，调整时必须做完整的容量评估，不能随手改。

### Q3: 对象大小到底怎么算？为什么说对象大小一定是 8 的倍数？

对象大小的计算公式是：

```
对象大小 = 对象头 + 实例数据（重排后）+ 对齐填充
```

以开启压缩指针为例，对象头固定 12 字节；实例数据按重排后的字段宽度累加；最后把总大小向上取整到最近的 8 的倍数，差额就是对齐填充。因为对齐单位默认是 8 字节，所以**任何对象的大小都是 8 的倍数**，不会有 13 字节、19 字节这种对象。

#### Q3.1: 字段顺序是我写的顺序吗？

不是。HotSpot 会按「父类字段在前、同一层内按宽度从大到小、引用放在最后」的规则重排。之所以要重排，是为了减少 padding：如果按声明顺序把 `byte` 夹在两个 `long` 中间，会产生两次对齐填充；重新排成 `long` 在前、`byte` 挤在一起，padding 就少很多。

副作用是**字段的内存偏移不安全、不可依赖**。用 Unsafe 的 `objectFieldOffset` 拿到的偏移量、用 JOL 打印的布局，都会随 JVM 版本和参数变化，绝对不要写进序列化逻辑或持久化格式里。

##### Q3.1.1: 那 TLAB 解决的是什么问题？跟对象大小有关系吗？

TLAB 解决的是**内存分配时的并发安全问题**，跟对象大小没有直接因果，但对象大小会影响 TLAB 的行为。

没有 TLAB 时，多线程在同一块 Eden 上指针碰撞必须同步（CAS），分配会变成竞争点。TLAB 给每个线程划一块私有缓冲区，线程在自己的 TLAB 里用指针碰撞分配，不需要任何同步，只有 TLAB 用完去申请新块、或者对象太大装不进 TLAB 时，才需要走带同步的慢路径。

所以对象大小的影响在于：如果对象比 TLAB 剩余空间大，或者干脆比整个 TLAB 都大，就会绕过 TLAB 走共享分配，失去「无锁分配」的好处。这也是为什么大量创建大对象的程序，TLAB 带来的收益有限。

## 常见坑

- **说「对象头就是 Mark Word」** —— 64 位下对象头至少包含 Mark Word 和类型指针两部分，压缩指针开启时共 12 字节，类型指针也是对象头的一部分
- **说「对象头是 8 字节」** —— 那是 Mark Word 的大小，不是整个对象头。完整对象头在压缩指针下是 12 字节，未压缩是 16 字节
- **说「Java 对象大小只看字段，字段多大对象就多大」** —— 漏掉了对象头和对齐填充。`Integer` 只装一个 `int`（4 字节），实际占 16 字节
- **说「堆开到 33GB 比 31GB 能装更多对象」** —— 超过约 32GB 压缩指针失效，引用和类型指针都变 8 字节，对象图整体膨胀，可用对象数可能反而更少
- **说「TLAB 是在栈上分配对象」** —— TLAB 是 Eden 区内线程私有的缓冲区，**仍然在堆上**，它解决的是并发分配问题，不是「消除堆分配」
- **说「构造方法执行时对象才算创建完成，之前的对象不存在」** —— 分配和置零之后对象就已存在（字段是默认值），只是还未构造完成；这也解释了为什么构造器里泄漏 `this` 很危险
- **说「Mark Word 里的哈希码一创建对象就有」** —— 哈希码是**延迟生成**的，第一次调用 `hashCode()`（或 `System.identityHashCode`）时才写入 Mark Word
- **说「字段在内存里按声明顺序排列」** —— HotSpot 会重排，父类字段在前、按宽度从大到小、引用靠后；这是实现细节，不可依赖

## 加分点

- 能准确说出**数组对象头比普通对象多 4 字节长度字段**，因此数组的元数据开销是 16 字节（压缩指针下），可以解释为什么小数组浪费
- 知道**压缩指针的「地址低 3 位恒为 0」是它能压缩的根本原因**，并从 `2^32 × 8` 推出 32GB 上限，而不是死记硬背
- 提到 **`-XX:ObjectAlignmentInBytes=16` 能把可寻址范围扩到约 64GB**，但代价是对齐增大导致内存浪费，属于权衡而非免费午餐
- 知道 **Mark Word 的哈希码与偏向锁存在冲突**：偏向锁需要占用原本用于存哈希码的区域，对象一旦算过哈希码，偏向锁的某些场景会受影响，这是偏向锁在 JDK 15 被默认禁用、后续被废弃的原因之一
- 能现场给出「用 JOL 打印布局」的方法，并说明结论依赖 JVM 版本和参数
- 提到**对象的创建过程顺序**：类加载检查 → 分配 → 置零 → 设对象头 → 执行构造器，且能指出「置零保证字段有默认值」这一步是 Java 语言「成员变量有默认值、局部变量没有」的底层原因
- 把对象布局与 **缓存友好性** 联系起来：字段重排和指针压缩都能缩小对象，进而提高 CPU cache line 的利用率，这是高性能场景下真实可量化的收益

## 版本差异

| 版本 | 差异 |
|---|---|
| Java 8 起 | 64 位 HotSpot 默认开启 `UseCompressedOops` 与 `UseCompressedClassPointers`；对象头（含类型指针）共 12 字节 |
| Java 8 起 | 偏向锁默认开启，Mark Word 布局包含 biased_lock 位与 epoch |
| Java 15 | 偏向锁被标记为废弃（JEP 374），`-XX:+UseBiasedLocking` 不再建议使用，Mark Word 中的偏向相关位语义随之弱化 |
| Java 17 / 21 | 压缩指针默认行为不变；对象对齐默认仍为 8 字节，对象大小仍是 8 的倍数 |

## 自测题

````yaml
questions:
  - type: CHOICE
    stem: 在 64 位 HotSpot、开启压缩指针的默认配置下，一个 new Integer(1) 占多少字节？
    options:
      A: 8 字节
      B: 12 字节
      C: 16 字节
      D: 24 字节
    answer: C
    analysis: 对象头 8 字节 Mark Word + 4 字节类型指针 = 12 字节，加上 4 字节 int 字段共 16 字节，正好是 8 的倍数，不需要额外对齐填充。这也是「优先用基本类型」的量化依据。

  - type: JUDGE
    stem: Java 对象的大小一定是 8 的倍数。
    answer: T
    analysis: HotSpot 默认按 8 字节对齐（-XX:ObjectAlignmentInBytes 默认 8），对象头加实例数据不足 8 的倍数时用对齐填充补齐，所以对象总大小必然是 8 的倍数。

  - type: MULTI
    stem: 关于指针压缩与 32GB 这个界限，下列说法正确的有？
    options:
      A: 压缩指针把 8 字节引用压成 4 字节，存的是以 8 字节为单位的偏移量
      B: 可寻址上限约为 2^32 × 8 字节，也就是 32GB
      C: 堆超过约 32GB 后压缩指针失效，引用和类型指针都变回 8 字节
      D: 堆只要超过 32GB 一点，能装的对象数就一定比 31GB 时更多
    answer: ABC
    analysis: D 错误。刚超过 32GB 时压缩指针失效，引用从 4 字节变 8 字节、对象头里的类型指针也变大，对象图整体膨胀，能装的对象数可能反而更少。经验做法是要么控制在 32GB 以内，要么一步远超。

  - type: CLOZE

      Object obj = new Object();
      System.out.println(ClassLayout.{{1}}(obj).toPrintable());
      // HotSpot 默认对象对齐单位为 {{2}} 字节，所以对象大小必是其整数倍
      ```
    blanks:
      - ["parseInstance"]
      - ["8", "八"]
    analysis: ClassLayout.parseInstance(obj).toPrintable() 能打印真实的字段偏移与对象大小；HotSpot 默认 -XX:ObjectAlignmentInBytes=8，对象总大小因此必然是 8 的倍数。
````
