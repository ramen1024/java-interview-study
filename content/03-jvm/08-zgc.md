## 电梯版回答

ZGC 的目标是停顿时间小于 1 毫秒、并且与堆大小无关（早期 JEP 333 的目标是 10ms 以内）。思路是把绝大部分工作都挪到并发阶段：标记、转移（移动对象）全都和用户线程同时跑，STW 只留几段极短的根扫描。支撑「边移动对象边让用户线程正确访问」的关键是两项技术。一是染色指针，把 GC 元数据（Marked0、Marked1、Remapped、Finalizable 四个位）塞进 64 位指针的高位，指针本身携带标记状态，这要求 64 位平台且操作系统支持多视图映射，即同一块物理内存能映射到多个虚拟地址。二是读屏障，每次读取引用时检查指针颜色，发现是旧地址就借助转发信息把它「自愈」成新地址，从而把更新引用的成本从写时挪到读时。ZGC 在 Java 11 实验性引入（JEP 333），Java 15 转正（JEP 377），Java 16 把线程栈处理也并发化（JEP 376），Java 21 引入分代 ZGC（JEP 439，`-XX:+UseZGC -XX:+ZGenerational`），Java 23 起分代成为默认。代价是吞吐略低于 G1、内存开销更大，适合大堆加低延迟场景。

## 展开讲解

### 目标与取舍

ZGC 的设计目标是一条很硬的要求：**停顿时间不随堆大小增长**。传统收集器哪怕做了并发标记，转移（复制/压缩）阶段往往仍需 STW，堆越大、存活对象越多，这段停顿就越长。

ZGC 的做法是把 STW 压缩到极限，只保留有界且极短的几段：

```
Pause Mark Start          (STW，极短，扫描根)
Concurrent Mark           (并发)
Pause Mark End            (STW，极短)
Concurrent Prepare for Relocate (并发)
Pause Relocate Start      (STW，极短)
Concurrent Relocate       (并发，对象移动)
```

三段暂停都只做根相关的固定工作，不随堆大小增长。Java 16（JEP 376）把线程栈的扫描也改成并发，进一步压低了这几段停顿。代价是：读屏障让每次读引用都多几条指令，吞吐会比 G1 低一些；染色指针与多视图映射带来额外的虚拟地址空间和内存开销。

### 染色指针

普通对象引用就是一个 64 位地址。ZGC 把它的一部分高位借来存 GC 元数据，这种指针叫**染色指针（Colored Pointer）**：

| 位名称 | 含义 |
|---|---|
| Marked0 | 本轮标记中该对象已被标记（第 0 组） |
| Marked1 | 另一轮标记中该对象已被标记（第 1 组） |
| Remapped | 指针指向对象的当前地址，是最「健康」的状态 |
| Finalizable | 对象只能通过 finalizer 访问 |

为什么需要两组 Marked 位？因为相邻两轮标记必须能区分开：如果只有一组标记位，上一次标记留下的「已标记」会污染这一轮的判断。两组标记位在相邻 GC 周期之间**交替使用**，一轮用 Marked0、下一轮用 Marked1，这样旧标记的残留不会影响新判断。

关键前提：**地址空间要留得足够宽**，标记位才有地方放。所以 ZGC 要求 64 位平台，不支持 32 位。

### 多视图映射

染色指针有个显然的麻烦：加上标记位以后，指针的值不再等于对象真实地址了，怎么还能访问到对象？

答案是**多视图映射（Multi-Mapping）**：ZGC 把同一块物理内存映射到多个不同的虚拟地址区间，每个区间对应一种颜色组合。于是无论指针被染成哪种颜色，按它去访问都会落到同一块物理内存上，值不同但指向同一个对象。

```
物理内存 P  ──映射──  虚拟区间 A（Remapped 视图）
            ──映射──  虚拟区间 B（Marked0 视图）
            ──映射──  虚拟区间 C（Marked1 视图）
```

这依赖操作系统/硬件的多视图映射能力（Linux、macOS、Windows 等主流 64 位平台都支持）。所以 ZGC 不是纯 JVM 层面的优化，它对运行平台有明确要求。

### 读屏障与自愈

**读屏障（Load Barrier）**是 ZGC 的另一根支柱。JIT 编译后的代码在每次从堆中**读取引用**时，会插入一小段检查（几条指令）：

```
读取引用 → 检查颜色位
  ├─ 颜色正确（已 Remapped 且指向当前地址）→ 直接用
  └─ 颜色不正确 → 走慢路径：
        解析对象的转发信息，拿到新地址
        把该引用/该字段更新为新地址（自愈 Self-Healing）
        返回新地址
```

「自愈」是关键：第一次读到旧指针时付出解析成本，顺手把引用改写成新地址，之后同一处再读就是快路径。这带来两个能力：

- **并发转移**：对象正在被 ZGC 搬走时，用户线程读到旧地址也能被重定向到新地址，不必停下来等
- **成本从写挪到读**：读操作是常态且可被 JIT 内联，写操作更少；把开销放在读侧换来转移阶段完全并发

读屏障通常配合 JIT 优化，实际是「先做一次低成本的颜色检查，绝大多数情况走快路径」。

### 并发转移

ZGC 的回收分标记与转移两个大阶段，**对象移动与用户线程并发**：

```
标记：从根出发并发遍历，用染色指针记录标记状态（Marked0/Marked1）
转移：把选定 Region 的存活对象复制到新 Region
      更新引用交给读屏障按需完成，而不是停机统一改
```

因为引用不需要在 STW 里统一修正，ZGC 就没有了传统压缩收集器最痛的那段停顿。代价是：

- 读屏障开销使吞吐略低
- 需要转发信息来把旧地址解析到新地址
- 大量对象同时被搬运时可用的内存与 CPU 压力更高

### 分代 ZGC

最初（Java 11–20）的 ZGC 是**不分代**的：整个堆一起标记、一起转移，每次都要处理全部存活对象，短命对象也得参与昂贵的转移，这是它吞吐偏低的原因之一。

Java 21 通过 **JEP 439** 引入分代 ZGC，把堆分成年轻代与老年代：

```
-XX:+UseZGC -XX:+ZGenerational      # Java 21 启用分代 ZGC
-XX:+UseZGC                          # Java 23 起即默认分代
```

分代 ZGC 保留了染色指针与读屏障机制，但对年轻代做更频繁的小范围回收，避免每次都为短命对象付出全堆成本，吞吐明显改善。启用后可以通过 `-XX:ZYoungGCThreads` 之类的参数微调（不同版本参数名有调整，使用前以当前版本为准）。

### 与 G1 的取舍

| 维度 | G1 | ZGC |
|---|---|---|
| 停顿 | 目标 200ms 量级，随堆与老年代增长 | 目标 <1ms，与堆大小基本无关 |
| 转移 | STW 的 Evacuation | 并发转移 |
| 屏障 | 写屏障（SATB）+ RSet | 读屏障 + 染色指针 |
| 吞吐 | 较高 | 略低（读屏障开销） |
| 内存开销 | RSet 占堆百分之几 | 多视图映射、转发结构等，更高 |
| 适用 | 中小堆、平衡吞吐与停顿 | 大堆（TB 级）、停顿敏感的在线服务 |

结论：**不是 ZGC 全面更好**。堆不大、追求吞吐的服务用 G1/Parallel 反而更划算；堆大到 G1 的停顿无法接受、又对延迟极敏感时，ZGC 才体现价值。

## 追问链

### Q1: ZGC 怎么做到停顿与堆大小无关？

关键在**把所有随堆规模增长的工作都挪出 STW**。传统收集器的停顿大头有两块：标记（可以并发，但往往要 STW 做最终标记）和转移/压缩（移动对象并修正全部引用，长期只能 STW）。堆越大、存活对象越多，这两块越久。

ZGC 的处理：

- 标记全程并发，用染色指针直接记录标记状态，不需要为写标记而暂停用户线程
- 转移也并发执行，引用修正不靠停机统一做，而是交给读屏障按需完成
- STW 只保留根扫描等有界的固定工作，时间与堆大小无关

于是停顿变成了「几段固定开销」而不是「与堆规模成正比的阶段」。

#### Q1.1: 染色指针把标记信息放进指针，指针的值就变了，怎么还能指向同一个对象？

靠**多视图映射**。ZGC 把同一块物理内存映射到多个虚拟地址区间，每个区间对应一种颜色：

```
物理对象 P
  虚拟区间 A（颜色 Remapped）→ 指向 P
  虚拟区间 B（颜色 Marked0） → 指向 P
  虚拟区间 C（颜色 Marked1） → 指向 P
```

无论指针染成哪个颜色，按它的值去访问都会落到同一块物理内存。所以「指针值不同但对象相同」这件事在 ZGC 里是成立的。这也是 ZGC 要求操作系统支持多视图映射的原因。

##### Q1.1.1: 那这些颜色位会不会被误当成地址的一部分？

会，所以 ZGC 在需要真实地址时必须**把颜色位掩掉**（按掩码取出有效地址位），而不是直接把染色指针当普通地址用。指针的有效地址位数是 64 位减去 4 个元数据位后的部分（不同版本支持的堆上限不同，早期为 4TB 量级，后续版本扩展到更大的 TB 级）。

这也是为什么 ZGC 上「解引用」不能是裸指针访问：读屏障必须先检查颜色、必要时自愈，再做访问。用户代码看不见这一层，但 JIT 生成的指令里真实存在。

#### Q1.2: 读屏障为什么能支持并发转移？

因为读屏障给了 JVM 一个「在用户线程即将使用这个引用时做拦截」的机会。

并发转移期间，对象可能已经被搬到新地址，但某个字段里还存着旧地址（引用修正还没轮到它）。用户线程读到这个旧引用时，读屏障检查颜色发现不对，就解析转发信息拿到新地址，返回给用户线程，同时把这个引用自愈成新地址。

于是「对象移动」和「用户线程访问对象」可以同时发生：用户线程不会读到悬空指针，JVM 也不必为了批量改引用而停下来。这是 G1 做不到的——G1 的转移是 STW 的，因为它没有读侧拦截手段。

##### Q1.2.1: 自愈是怎么实现的？多线程同时读到旧引用会不会重复搬？

自愈就是「读到旧值时顺手把正确值写回去」：读屏障在慢路径解析出新地址后，把该引用（字段或栈上位置）更新为新地址，后续读取直接命中快路径。

多个线程同时读到同一个旧引用时，可能出现重复解析，但**不会重复搬对象**：对象的搬移由 GC 线程在转移阶段完成一次，读屏障只负责「把旧地址翻译成新地址并缓存」，翻译是幂等的。最坏情况是几个线程各解析一次，纯属多余计算，不影响正确性。

### Q2: ZGC 的并发标记和 G1 的 SATB 有什么不同？

G1 的 SATB 依赖**写前屏障**：引用被覆盖前把旧值记进队列，按标记开始时的快照判定存活。它只解决标记阶段的一致性问题，转移仍是 STW 的。

ZGC 靠**染色指针 + 读写屏障配合**：标记状态直接写进指针颜色，指针被读取时由读屏障检查与修正。这套机制同时支撑了标记和转移两件事——标记阶段记录颜色，转移阶段解析旧地址，所以 ZGC 才能连对象移动都并发做。

一句话：G1 的屏障是为标记服务的，ZGC 的障碍是为「标记 + 并发转移」服务的。

#### Q2.1: 那 ZGC 为什么在 Java 21 之前不分代？

因为它优先保证停顿与堆大小无关，而不分代正好符合这个目标：整个堆一起标记、一起转移，没有「新生代回收还需要扫描老年代」这类跨代依赖问题，设计更简单。

代价是**所有对象都被平等对待**：一个刚创建就死的临时对象，也要参与昂贵的转移，每次 GC 都要处理全部存活对象。这造成 ZGC 的吞吐低于 G1，尤其在分配速率高、对象生命周期短的应用里更明显。

##### Q2.1.1: 分代 ZGC 加了什么，代价是什么？

JEP 439（Java 21）引入分代 ZGC：把堆分成年轻代与老年代，对年轻代做更频繁的小范围回收，让短命对象在年轻代就被清掉，不进入昂贵的全堆处理，从而改善吞吐。

代价是复杂度上升：跨代引用需要额外记录（类似记忆集），年轻代回收必须把老年代指向年轻代的引用当作根，染色指针与读屏障要同时支持两代的状态，实现与调优参数都更复杂。启用方式是 Java 21 的 `-XX:+UseZGC -XX:+ZGenerational`；到 Java 23，`-XX:+UseZGC` 默认就是分代模式，非分代模式被废弃。

### Q3: 那线上无脑上 ZGC 就行了吗？

不行，要先看瓶颈是停顿还是吞吐。ZGC 换来低停顿的代价是读屏障开销、更大的内存占用和更多 GC 线程，吞吐通常低于 G1。如果服务本身吞吐吃紧、对几十毫秒的 GC 停顿不敏感，上 ZGC 反而可能得不偿失。

判断步骤：先用 GC 日志量出停顿分布（最大停顿、P99、Full GC 次数），确认瓶颈确实是 GC 停顿而不是分配速率或锁竞争；再确认堆足够大、平台是 64 位且操作系统支持多视图映射；然后灰度切收集器做对照压测。

#### Q3.1: 换收集器之外，还能怎么降低 GC 停顿？

先减少「垃圾产生」本身，这比换收集器更治本：

- 减少临时对象的分配（日志字符串拼接、装箱、大数组一次性拷贝、正则反复编译）
- 避免超大对象造成 Humongous/大对象分配（G1 里 Humongous 可直接触发 Full GC）
- 缓存要看命中率，别用「看起来省 CPU」的方式堆出大量长命对象

然后是容量与目标：给足堆避免频繁触发，设置合理的停顿目标，而不是把 `-XX:MaxGCPauseMillis` 一味调小。

最后才是收集器选择：大堆低延迟选 ZGC，通用场景用 G1，纯吞吐用 Parallel。

## 常见坑

- **「ZGC 停顿小于 1ms 是绝对的」** —— 这是目标值。STW 根扫描仍存在（虽然极短），且实际情况依赖堆、对象图与硬件，不是每次都能精确命中
- **「染色指针就是把标记信息放在低地址位」** —— 放的是 64 位指针的**高位**（Marked0、Marked1、Remapped、Finalizable 四个元数据位），地址用的是剩下的有效位
- **「ZGC 完全不需要 STW」** —— 仍有极短的暂停（Mark Start / Mark End / Relocate Start 的根扫描），只是每段都不随堆大小增长
- **「ZGC 在 32 位平台也能用」** —— 染色指针需要借用高位，要求 64 位平台
- **「ZGC 比 G1 全面更好」** —— ZGC 吞吐略低、内存开销更大；堆小或吞吐优先时 G1/Parallel 更合适
- **「ZGC 一直是分代收集器」** —— Java 11 引入时不支持分代，Java 21（JEP 439）才引入分代 ZGC
- **「Java 11 就能直接用 -XX:+UseZGC，不用解锁实验开关」** —— Java 11 起 ZGC 是实验特性，需要 `-XX:+UnlockExperimentalVMOptions`；Java 15（JEP 377）才转正
- **「ZGC 和 G1 一样靠写屏障」** —— G1 用写屏障（SATB），ZGC 的核心是读屏障，这正是它能支持并发转移的原因
- **「换 ZGC 不需要改任何参数」** —— 大堆场景通常还要关注 GC 线程数、堆预留与分配速率，否则可能出现分配停顿（Allocation Stall）

## 加分点

- 知道 **Shenandoah** 是另一条技术路线：它用 **Brooks 转发指针**（每个对象多一个转发字段）加读引用屏障（LRB），同样能并发转移，但不用染色指针，也不需要多视图映射。对比 ZGC 能讲清「染色指针 vs 转发指针」的取舍
- 知道两组 Marked 位交替使用的原因：**区分相邻两轮标记**，避免上一轮的标记残留污染这一轮的判断
- 知道 Java 16 的 **JEP 376** 把线程栈处理也改成并发，ZGC 的停顿才稳定落到 1ms 以下
- 知道 ZGC 的失败模式里有**分配停顿（Allocation Stall）**：堆被并发转移占满、来不及回收时，分配线程会被阻塞等待，这不是 STW 但同样影响延迟
- 能讲清多视图映射是**操作系统能力**而非纯 JVM 技巧，这是 ZGC 对平台有要求的原因
- 提到 ZGC 的调优关注点与 G1 不同：G1 调 Region 大小与 IHOP，ZGC 更关注 GC 线程数、堆是否给足、大对象与分配速率

## 版本差异

| 版本 | 差异 |
|---|---|
| Java 11 | ZGC 作为实验性收集器引入（JEP 333），需 `-XX:+UnlockExperimentalVMOptions -XX:+UseZGC`，停顿目标 10ms 以内，支持 TB 级堆 |
| Java 15 | ZGC 转正（JEP 377），不再需要 `-XX:+UnlockExperimentalVMOptions` |
| Java 16 | 线程栈处理并发化（JEP 376），移除了随线程数/栈深度增长的停顿，停顿稳定压缩到 1ms 以下 |
| Java 21 | 引入分代 ZGC（JEP 439），启用方式为 `-XX:+UseZGC -XX:+ZGenerational`，针对年轻代短命对象回收，吞吐明显改善 |
| Java 23 | 分代模式成为 `-XX:+UseZGC` 的默认（JEP 474），非分代模式被标记废弃 |
