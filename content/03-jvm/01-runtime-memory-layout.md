## 电梯版回答

JVM 运行时数据区按线程共享性分成两类。线程私有的有三个：程序计数器、虚拟机栈、本地方法栈。线程共享的有两个：堆和方法区。堆放对象实例，是 GC 的主战场，用 -Xms 和 -Xmx 控制；方法区放类元信息，JDK 8 之前叫永久代、在堆里，JDK 8 起改成元空间、用本地内存。另外还有一块直接内存，NIO 的 DirectByteBuffer 用它，不受 -Xmx 限制。其中程序计数器是唯一不会 OOM 的区域。

## 展开讲解

### 全景图

```
JVM 运行时数据区
├── 线程私有（每条线程一份）
│   ├── 程序计数器 (Program Counter Register)
│   ├── 虚拟机栈 (VM Stack)      —— 栈帧：局部变量表、操作数栈、动态链接、返回地址
│   └── 本地方法栈 (Native Method Stack)
└── 线程共享（整个进程一份）
    ├── 堆 (Heap)               —— -Xms / -Xmx，GC 主战场
    └── 方法区 (Method Area)     —— JDK 8 前：永久代；JDK 8 起：元空间（本地内存）

堆外
└── 直接内存 (Direct Memory)     —— -XX:MaxDirectMemorySize，NIO DirectByteBuffer
```

### 程序计数器

记录当前线程正在执行的字节码行号。分支、循环、跳转、异常处理、
线程恢复都靠它。

**它是唯一在《Java 虚拟机规范》中没有规定任何 OOM 情况的区域**。
原因很直接：它是线程私有的，每条线程一个，且只存一个指令地址，
所需内存极小且固定，不存在「扩张到内存耗尽」的路径。

为什么必须有它：CPU 时间片轮转，线程随时可能被切走。恢复执行时
必须知道「我刚才执行到哪了」。这个信息只能每条线程各自保存，
所以它是私有的。

（如果执行的是 native 方法，程序计数器的值是 undefined，
因为 native 方法由 C/C++ 执行，不产生字节码偏移。）

### 虚拟机栈

每个方法调用对应一个栈帧压栈，方法结束出栈。

栈帧结构：

| 组成 | 作用 |
|---|---|
| 局部变量表 | 存方法参数和局部变量，以变量槽（Slot，32 位）为单位。`long`/`double` 占两个槽 |
| 操作数栈 | 字节码运算的工作区，比如 `iadd` 就是从栈顶弹两个数相加再压回 |
| 动态链接 | 指向运行时常量池中该方法的引用，支持多态（`invokevirtual` 时才能确定实际方法） |
| 方法返回地址 | 方法正常或异常退出后，恢复上层方法的执行位置 |

两种异常要区分清楚：

- **`StackOverflowError`**：栈深度超过限制。典型成因是递归没有终止条件。
  用 `-Xss` 设置单线程栈大小。
- **`OutOfMemoryError`**：栈可以动态扩展时，扩展申请不到内存。
  多见于创建大量线程——每个线程都要一份栈空间。

一个常见的错误说法是「栈会 OOM 所以栈也是 GC 区域」。**栈不参与 GC**，
栈帧随方法调用和返回自动进出，是编译器就确定好的结构。

### 堆

所有对象实例和数组都分配在堆上（逃逸分析优化后的标量替换除外）。
逻辑上分代：

```
堆
├── 新生代 (Young)   —— 约 1/3 堆，-Xmn 或 -XX:NewRatio 控制
│   ├── Eden          —— 对象优先在这里分配
│   ├── Survivor 0
│   └── Survivor 1    —— 两个 Survivor 默认 1:1，始终有一个是空的
└── 老年代 (Old)      —— 长期存活的对象
```

参数：`-Xms` 初始堆大小，`-Xmx` 最大堆大小。
**生产上建议把 `-Xms` 和 `-Xmx` 设成相等**，避免运行期反复扩缩堆
带来的额外开销和 GC 抖动。

对象优先在 **TLAB（Thread Local Allocation Buffer）** 上分配。
TLAB 是 Eden 里给每条线程划分的一小块私有区域，这样分配对象只需
移动指针（bump the pointer），不需要原子操作，避免了全局锁竞争。
`-XX:+UseTLAB` 默认开启。

### 方法区：从永久代到元空间

方法区是**《Java 虚拟机规范》里的概念**，永久代和元空间是**具体实现**。
这两者经常被混为一谈。

方法区存：类元信息（类结构、字段、方法、字节码）、静态变量、常量、
即时编译器编译后的代码缓存。

| 版本 | 实现 | 位置 | 相关参数 |
|---|---|---|---|
| JDK 7 及以前 | 永久代 PermGen | **堆内** | `-XX:PermSize` / `-XX:MaxPermSize` |
| JDK 8 起 | 元空间 Metaspace | **本地内存** | `-XX:MaxMetaspaceSize`（默认不限） |

一个高频混淆点：**字符串常量池在 JDK 7 就从永久代移到了堆**，
不是 JDK 8。所以「JDK 8 之后字符串常量池在元空间」是错的。

### 直接内存

不是运行时数据区的一部分，但被频繁使用。NIO 的
`DirectByteBuffer` 在堆外分配，通过 `-XX:MaxDirectMemorySize` 控制
（默认约等于 `-Xmx`）。

价值：**避免堆内到堆外的二次拷贝**。普通的 `Socket` IO 要把数据
从内核缓冲区拷到堆内数组，DirectByteBuffer 让内核直接读写这块内存，
少一次拷贝。Netty 大量使用它。

这就是为什么排查内存问题只看 `-Xmx` 会误判：一个 `-Xmx4g` 的进程
RSS 可能到 6G 以上，差额来自元空间 + 直接内存 + 线程栈 +
JVM 自身 + 代码缓存。

## 追问链

### Q1: 哪些区域是线程私有的？为什么？

程序计数器、虚拟机栈、本地方法栈是私有的。根本原因是**它们承载的是
「执行状态」而不是「数据」**：程序计数器记录执行到哪条指令，
虚拟机栈记录当前方法调用链和局部变量。

线程是执行单元，执行状态天然必须每条线程独立。如果共享，
线程切换时状态会互相覆盖，多线程就无法正确运行。

堆和方法区存的是**所有线程都要访问的数据**（对象、类元信息），
共享才能让一个线程创建的对象被另一个线程使用。共享的代价就是
需要同步机制和 GC 来管理。

#### Q1.1: 程序计数器为什么是唯一不会 OOM 的区域？

三个条件同时成立：

1. **每条线程独立一份** —— 不会因为线程多而堆叠在同一结构里
2. **只存一个指令地址** —— 数据量固定且极小，不随程序复杂度增长
3. **没有「动态扩展」的设计** —— 虚拟机规范里也没有定义它的 OOM

对比虚拟机栈：虽然也是私有的，但栈深度随调用链动态增长，
所以会 `StackOverflowError`；创建线程时栈空间申请失败则会 OOM。

##### Q1.1.1: 什么时候会报 OutOfMemoryError: unable to create native thread？

这个报错**几乎总是线程数问题，而不是堆内存问题**。触发条件有两类：

1. **操作系统层面的线程数上限**
   - Linux 的 `ulimit -u`（单用户最大进程/线程数）
   - `/proc/sys/kernel/threads-max`（系统级）
   - `/proc/sys/vm/max_map_count`（线程多了会耗尽内存映射区）
2. **每个线程的栈空间耗尽内存**
   - 线程栈默认约 1MB（`-Xss` 可调），万级线程就是 10GB 虚拟内存
   - 32 位系统受地址空间限制尤其明显

排查顺序：

```bash
ulimit -u                                  # 单用户线程上限
cat /proc/sys/kernel/threads-max           # 系统线程上限
ps -eLf | wc -l                            # 当前线程总数
jstack <pid> | grep -c '^"'                # 单个 JVM 的线程数
```

值得注意的是：**这个 OOM 的信息里不会包含堆栈跟踪**，
JVM 明确说「如果这个错误抛在 native 栈上，堆栈信息可能不可用」。
所以别指望靠日志定位，得从线程数本身入手。

常见的真实成因是线程池配错（`newCachedThreadPool` 无限建线程）、
或者 `ThreadLocal` 用错导致线程无法回收——注意是**线程**无法回收，
不是线程本地变量对象无法回收。

### Q2: JDK 8 为什么把永久代换成元空间？

三个原因，从技术到工程依次是：

1. **永久代大小难调，且容易 OOM**。`-XX:MaxPermSize` 设小了
   在类加载多的时候 OOM，设大了浪费堆空间。而且永久代在堆内，
   它的大小直接挤压老年代，调优时两个目标互相牵制。
2. **永久代的回收效率低**。永久代只在 Full GC 时回收，
   且回收条件苛刻（类卸载要求该类加载器不可达、无实例、无引用），
   结果就是「放进去就出不来」，典型的动态代理/热部署场景必然 OOM。
3. **HotSpot 与 JRockit 合并的技术选择**。JRockit 没有永久代概念，
   合并后选择用元空间方案。

换成元空间后：**类元信息搬到本地内存**，默认不设上限，
只受物理内存约束；堆的大小不再被永久代挤压；`-XX:MaxMetaspaceSize`
仍然建议显式设置，否则一个类加载器泄漏会把物理内存吃干净。

#### Q2.1: 那元空间就不会 OOM 了吗？

会。`OutOfMemoryError: Metaspace`。因为「默认不限」不等于「无限」，
最终受限于物理内存和容器内存限制（`-XX:MaxRAMPercentage` 之类）。

元空间 OOM 的典型成因：

- **动态生成类过多**：CGLIB 代理、字节码增强（SkyWalking、Arthas）、
  Groovy/JSP 编译、`Lambda` 的 `LambdaMetafactory` 生成类
- **类加载器泄漏**：这是最本质的原因。类卸载的前提是
  **加载它的类加载器被回收**。只要有一个强引用指着类加载器，
  它加载的所有类都无法卸载，元空间只增不减

几个真实场景：

```
Tomcat 热部署     → 每次 reload 新建 WebAppClassLoader，旧的没释放 → 元空间涨
ThreadLocal 持有类 → 线程池线程长期存活，ThreadLocalMap 的 key 是弱引用但 value 是强引用
自定义类加载器     → 静态字段/缓存里存了 Class 对象
```

排查手段：

```bash
jstat -gcmetacapacity <pid> 1000     # 看 Metaspace 是否持续增长
jmap -clstats <pid>                  # 按类加载器统计已加载类数
jcmd <pid> VM.metaspace              # JDK 11+ 的元空间详细分布
```

判断标准很简单：**Full GC 之后 Metaspace 仍然持续上涨**，
就是类加载器泄漏，不是正常的类加载。

## 常见坑

- **说「方法区就是永久代」** —— 方法区是规范概念，永久代和元空间是实现。
  JDK 8 之后说「方法区」应该对应元空间
- **说「JDK 8 之后字符串常量池在元空间」** —— 字符串常量池在
  **JDK 7 就移到了堆**，比永久代移除还早一个版本
- **说「栈是线程共享的」** —— 虚拟机栈和本地方法栈都是线程私有的
- **混淆 `StackOverflowError` 和 `OutOfMemoryError`** ——
  前者是深度超限（递归），后者是空间申请失败（线程太多或堆满）
- **说「直接内存受 `-Xmx` 限制」** —— 它由
  `-XX:MaxDirectMemorySize` 控制，默认约等于 `-Xmx` 但不受其约束
- **只看 `-Xmx` 解释进程内存** —— 元空间 + 直接内存 + 线程栈 +
  代码缓存都要算进去
- **说「栈也需要 GC」** —— 栈帧随方法调用自动进出，不参与垃圾回收
- **认为 `-Xmx` 设大就一定好** —— 堆越大单次 Full GC 停顿越长，
  且剩余物理内存不足会触发 swap 或 OOM Killer

## 加分点

- 提到 **TLAB**：对象优先在 Eden 内线程私有的一小块区域分配，
  用指针碰撞（bump the pointer）分配，避免多线程分配对象的全局竞争。
  这是「用空间换无锁」的典型设计
- 知道**逃逸分析**能让对象不进堆：如果对象不逃逸出方法，
  JIT 可以做标量替换，把对象拆成几个局部变量直接在栈上使用。
  所以「所有对象都分配在堆上」严格说是不准确的——这是一种优化，
  不是必然发生的
- 能解释 **JDK 7 为什么先移字符串常量池**：因为永久代只在 Full GC
  才回收且效率低，而字符串常量池里的字符串往往是短命的临时对象，
  放在堆里能享受新生代 GC 的高效回收
- 知道 `unable to create native thread` 的日志里**没有堆栈**，
  这是规范规定的，所以不能靠异常堆栈定位
- 能把「元空间 OOM」和「类加载器泄漏」联系起来，并说出
  「类卸载的前提是类加载器可回收」这个判断依据
- 知道排查内存问题时 `jcmd <pid> VM.native_memory summary`
  (需开启 NMT) 能区分堆内堆外的占用分布

## 版本差异

| 版本 | 差异 |
|---|---|
| JDK 7 | 字符串常量池从永久代移到堆；永久代仍在 |
| JDK 8 | **移除永久代**，改为元空间（本地内存）；`-XX:PermSize` / `-XX:MaxPermSize` 失效，改用 `-XX:MaxMetaspaceSize`；默认 GC 从 Parallel 改为 G1 更晚，但内存结构变化在此版本 |
| JDK 9+ | 引入类数据共享（CDS）和分层编译的代码缓存调整，进一步降低元空间与启动开销 |
| JDK 11+ | `jcmd VM.metaspace` 可查看元空间细分（类、方法、常量池各占多少），排查泄漏更方便 |
