## 电梯版回答

JIT 把频繁执行的字节码编译成本地机器码，HotSpot 默认走分层编译：先由解释器执行，用方法调用计数器和回边计数器统计热度，达标后交给 C1 做快速编译并插入性能采样，更热的方法再交给 C2 做激进优化。C2 里最重要的优化是方法内联，它把被调方法的字节码展开进调用方，只有内联之后逃逸分析、常量传播、锁消除这些优化才有足够的作用范围。逃逸分析判断一个对象会不会逃出当前方法或当前线程，结论分为不逃逸、方法逃逸、线程逃逸三种；对不逃逸的对象可以做标量替换，把它拆成一组基本类型字段，根本不在堆上分配对象；如果锁对象也不逃逸，还能做锁消除，去掉不可能被其他线程竞争的锁。`-XX:+DoEscapeAnalysis` 和 `-XX:+EliminateAllocations` 在现役 HotSpot 上默认开启。所有这些优化都建立在激进假设之上，一旦假设被运行期事实打破就触发去优化，退回解释执行。

## 展开讲解

### 解释执行、编译执行与混合模式

Java 代码先由 `javac` 编译成字节码，运行时由 JVM 执行。HotSpot 默认是**混合模式（mixed mode）**，既保留解释器，也带 JIT 编译器：

| 执行方式 | 开关 | 特点 |
|---|---|---|
| 纯解释执行 | `-Xint` | 启动快，执行慢，调试可用 |
| 纯编译执行 | `-Xcomp` | 首次执行即编译，启动极慢，不推荐 |
| 混合模式 | 默认 | 解释器先兜底，热点代码再编译 |

解释器有两个不可替代的作用：一是让应用尽快跑起来，不必等编译；二是**编译出错的兜底和去优化的落点**——去优化之后代码就是回退到解释器继续跑。

JIT 编译器是独立的编译线程，编译产物放在 **CodeCache** 里。CodeCache 被 `-XX:ReservedCodeCacheSize` 限制，写满之后 JIT 会停止编译，表现为「运行一段时间后性能突然不再提升」甚至下降（退化回解释执行）。`-XX:+PrintCodeCache` 可以观察使用量。

### 分层编译（Tiered Compilation）

JDK 8 起 `-XX:+TieredCompilation` 默认开启，把执行划分为 5 个层级：

| 层级 | 执行方式 | 说明 |
|---|---|---|
| 0 | 解释器 | 采集方法调用次数、循环回边次数 |
| 1 | C1 编译 | 简单快速，不做 profiling |
| 2 | C1 编译 + 有限 profiling | 用于过渡，代码质量介于 1 和 3 之间 |
| 3 | C1 编译 + 完整 profiling | 采集类型、分支、去优化等 profile 数据 |
| 4 | C2 编译 | 基于 profile 做深度优化，代码质量最高，编译耗时最长 |

为什么不能一上来就用 C2：C2 编译一个方法可能要几十毫秒，如果所有方法（包括只跑一两次的）都编译，启动会明显变慢，而且大部分编译成本收不回来。分层编译先用 C1 让代码**快速脱离解释执行**，同时用 C1 插桩采集运行期 profile，等热度真的够了再交给 C2 做投机优化（speculative optimization）。代价是代码可能被编译多次，元空间和方法状态要相应管理。

### 热点探测

HotSpot 用**基于计数器**的热点探测，而不是采样。两个计数器分工明确：

- **方法调用计数器（Invocation Counter）**：统计方法被调用的次数。
- **回边计数器（Back Edge Counter）**：统计循环体往回跳的次数，也就是循环迭代次数。

只有调用计数器是不够的：一个方法只被调用一次，但方法体里跑的是个几十亿次的循环，它永远不会被判定为热点，循环就只能一直解释执行。回边计数器正是为这种情况准备的。

计数器不是只涨不跌。为了保护刚刚变热的新代码，HotSpot 有**计数器衰减（Counter Decay）**，`-XX:CounterHalfLifeTime` 控制半衰期，过了半衰期计数减半，否则一个曾经的热点方法会永久占据编译名额。

以 HotSpot 的默认值为例，C1 的编译阈值大约在方法调用 200 次量级，C2 大约在 5000 次量级（`-XX:Tier3InvocationThreshold`、`-XX:Tier4InvocationThreshold` 等参数可调，具体数值随版本可能微调）；关闭分层编译时则看 `-XX:CompileThreshold`，默认是 10000。

### 方法内联：最重要的优化

方法内联把被调方法的字节码直接展开进调用方，消除调用开销，更重要的是**扩大了优化的作用范围**：

```java
public int compute() {
    return add(1, 2) * 3;      // 内联后等价于 (1 + 2) * 3
}
private int add(int a, int b) {
    return a + b;
}
```

内联之后，`add` 的常量参数直接进入调用方，常量折叠、死代码消除、逃逸分析才可能跨方法生效。反过来说，如果一个短小的方法**没有被内联**，它内部的局部对象在调用方看来就是「逃逸到另一个方法」了。

内联的规模由字节码指令数控制：

- `-XX:MaxInlineSize`：普通方法的内联上限，默认是 35 字节码指令（大约）。
- `-XX:FreqInlineSize`：热点方法（已被判定为热点的）的上限，明显更宽松，默认在 300 多字节码指令的量级。
- `-XX:+PrintInlining` 可以打印内联决策（`inline (hot)` / `too big` / `not inlineable`）。

多态调用要靠**类型 profile + 类层次分析（CHA）**才能内联：如果某个 `invokevirtual` 历史上只出现过一种接收者类型（单态）或少数几种（双态），JIT 会生成类型判断加内联代码；一旦出现新的实现类型，内联假设被打破，就触发去优化。

### 逃逸分析（Escape Analysis）

逃逸分析回答的是：**一个对象的作用域有没有超出它被创建的地方**。HotSpot 的逃逸状态分三种（源码里是 `EscapeState`）：

| 状态 | 含义 | 能做的优化 |
|---|---|---|
| 不逃逸 NoEscape | 对象只在当前方法内使用 | 标量替换、锁消除 |
| 方法逃逸 ArgEscape | 作为参数传给其他方法，或作为返回值传出当前方法 | 通常只能做锁消除等保守优化 |
| 线程逃逸 GlobalEscape | 被赋给静态字段、被其他线程可见的字段，或被放入堆上的共享结构 | 不能做相关优化 |

判断依据主要是对象的引用去向：是否被赋值到堆上的字段、是否作为参数传给未知方法、是否被其他线程访问。

### 基于逃逸分析的三个优化

**① 标量替换（Scalar Replacement）**

把一个不逃逸的对象**打散成它的各个字段**（标量），字段直接分配在栈帧的局部变量表或寄存器里，**根本不创建对象**：

```java
public int total() {
    Point p = new Point(1, 2);   // Point 不逃逸
    return p.x + p.y;
}
// 标量替换后等价于：
public int total() {
    int x = 1;
    int y = 2;
    return x + y;
}
```

注意拆开之后连字段名都不需要了，对象头、对齐填充、指针全部省掉，堆压力和 GC 压力都降下来。`-XX:+EliminateAllocations` 控制这个优化，默认开启。

**② 栈上分配（Stack Allocation）**

概念上，对不逃逸的对象可以直接在栈帧上分配，随方法出栈自动释放，不需要 GC 参与。这是教学材料里最常提到的逃逸分析收益。但需要说明：**HotSpot 并没有实现教科书式的「在栈帧上分配完整对象」**，实际落地的主要手段是标量替换——对象被拆散了，连对象本身都不存在，自然也不在堆上。严格说这是两种不同的技术，很多八股文把它们混为一谈。

**③ 锁消除（Lock Elision）**

如果一个锁对象不可能被其他线程访问到，那么对它加锁就是多余的，可以整个消除：

```java
public String concat(String a, String b) {
    StringBuffer sb = new StringBuffer();   // sb 不逃逸
    sb.append(a);                            // append 是 synchronized 方法
    sb.append(b);
    return sb.toString();
}
```

`StringBuffer` 的方法都带 `synchronized`，但 `sb` 只在方法内使用，不逃逸，所以这些锁会被消除。`-XX:+EliminateLocks` 控制，默认开启。**前提仍然是逃逸分析判定锁对象不逃逸**——如果 `sb` 被返回出去或赋给成员字段，锁消除就不会发生。

### 去优化（Deoptimization）

JIT 的激进优化是**以假设换性能**：假设这个方法只会被某一种类型调用、假设这个类不会被继承、假设某个分支永远不走。一旦运行期事实推翻假设，编译后的代码就不再正确，必须**去优化**：

```
编译后的代码遇到 uncommon trap
  → 暂停当前执行
  → 从优化后的栈帧重建出解释器可识别的栈帧（重建局部变量和操作数栈）
  → 退回解释器继续执行（保持代码语义正确）
  → 若后续热度足够，基于新的事实重新编译
```

常见的触发原因：

- 单态/双态内联假设被新实现类型打破（类层次分析 CHA 失效，比如运行时加载了某个接口的新实现）
- `null` 检查的隐式抛异常路径被真正走到（uncommon trap）
- 类型 profile 与实际类型冲突
- 依赖的类或常量发生变化

去优化不是 bug，而是投机优化的必要机制；但**频繁去优化会明显拖慢性能**。可以用 `-XX:+UnlockDiagnosticVMOptions -XX:+TraceDeoptimization`（诊断参数，输出量很大）观察，`-XX:+PrintCompilation` 也能看到反优化记录。

## 追问链

### Q1: 分层编译为什么要把编译分成 C1 和 C2 两级，直接全用 C2 不行吗？

因为 C1 和 C2 的取舍完全相反：

- **C1**：编译快、优化保守、会插入 profiling 代码，生成的机器码质量一般，但能让代码**立刻脱离解释执行**。
- **C2**：编译慢、优化激进、生成的机器码质量最高，但单个方法的编译成本可能高出一个数量级。

如果所有方法都等 C2，启动阶段要花大量时间编译那些只执行一两次的方法，纯属浪费；而且 C2 需要 profile 数据才能做投机优化，没有 C1 阶段采集的数据，它只能做保守优化。分层编译的本质是**用少量的编译成本换取 profile 数据，再让 C2 把这份数据变成极致的代码**。

#### Q1.1: 那「热点」是怎么判定的？方法调用计数器和回边计数器各管什么？

两个计数器统计的对象不同：

- **方法调用计数器**：统计方法被调用的次数，管的是「这个方法被频繁调用」。
- **回边计数器**：统计循环体往回跳的次数，管的是「这个方法里有一段代码被频繁执行」。

只有方法调用计数器会漏掉一种情况：方法被调用一次，但内部是一个几十亿次的长循环。此时方法调用计数只有 1，永远达不到编译阈值，循环就得一直解释执行。回边计数器的存在就是为了覆盖长循环，它触发的是**栈上替换（OSR）**而不是普通编译。

##### Q1.1.1: 回边计数器触发时会发生什么？OSR 和普通编译有什么不同？

普通编译的生效时机是**下一次方法调用**：编译完成后，下次进入这个方法时用新版本，当前的这次调用还是旧代码跑完。回边计数器触发的是 **OSR（On-Stack Replacement，栈上替换）**：不退出当前方法的栈帧，在循环回跳这个执行点上直接把解释执行的栈帧替换成编译代码的栈帧，**当前这次调用就开始跑编译后的版本**。

这解决的是「一个长循环还没跑完，方法却永远编译不了」的问题。OSR 编译有专门的入口，进入循环后从当前迭代开始执行，前面的迭代不会重跑。

### Q2: 逃逸分析出来的结论，JVM 具体拿去做什么优化？

三个方向：**标量替换、栈上分配、锁消除**。

标量替换面向内存分配：不逃逸的对象被拆成字段，字段落到栈帧或寄存器，对象头部、对齐填充和堆分配一起省掉。栈上分配在 HotSpot 里主要就是通过标量替换体现的。锁消除面向同步：锁对象不逃逸，说明不可能有其他线程拿到这把锁，`synchronized` 只是空转，可以直接删掉。

需要强调一个前提：**这些优化绝大多数都要先有方法内联**。如果对 `new Point()` 的操作分散在几个没有被内联的方法里，逃逸分析看不到完整的使用路径，只能保守地认定对象「逃逸」。所以方法内联是逃逸分析发挥作用的前置条件。

#### Q2.1: 栈上分配、标量替换、锁消除分别在什么条件下才成立？

三者都要求对象**不逃逸**，但门槛不同：

| 优化 | 成立条件 | 开关 |
|---|---|---|
| 标量替换 | 对象不逃逸，且能被安全地拆解为标量字段 | `-XX:+EliminateAllocations` |
| 栈上分配 | 概念上同样是对象不逃逸；HotSpot 主要以标量替换落地 | 随逃逸分析 |
| 锁消除 | 锁对象不逃逸，且没有非逃逸路径能获取该锁 | `-XX:+EliminateLocks` |

最常见的失败原因是「看起来没逃逸，实际逃逸了」：对象被赋给成员字段、被放进集合、被传给未内联的方法、被 lambda 捕获后逃出方法、被写入 `ThreadLocal` 等。只要有一条路径可能逃逸，优化就被放弃。

##### Q2.1.1: 那「Java 对象都分配在堆上」这句话对吗？

作为默认心智模型基本成立，作为**绝对论断不严谨**。

规范的默认语义确实是对象在堆上分配，这也符合「堆是线程共享、栈是线程私有」的内存模型。但在开启逃逸分析的情况下，不逃逸的对象可以经过标量替换后**根本不以对象形式存在**，它的字段变成局部变量，落在栈帧或寄存器里——这时说「对象分配在堆上」已经不适用了。

所以更准确的说法是：Java 对象通常分配在堆上，逃逸分析允许编译器在能证明不逃逸时消除这次堆分配。另外要注意，**TLAB 虽然叫线程本地分配缓冲，它仍然在堆内**，只是把 Eden 切成线程私有的小块以避免分配时的同步，和逃逸分析带来的栈上消除是两回事。

### Q3: 既然逃逸分析和内联都是「投机」，那猜错了怎么办？

猜错就**去优化**。JIT 在编译时会为每个激进假设埋下守卫（guard）或 uncommon trap，运行期一旦走到守卫失败的分支，就暂停优化代码，把当前栈帧重建成解释器能理解的样子，退回解释执行，同时把这条 profile 记录更新掉。后续如果热度仍然足够，JIT 会基于新的事实重新编译。

去优化保证的是**语义正确性**——优化后的代码行为和解释执行必须一致，这也是为什么它要花力气重建栈帧而不是简单丢弃。

#### Q3.1: 什么情况最容易触发去优化？

最常见的是**类层次分析（CHA）失效**：JIT 观察到某个接口目前只有一个实现类，于是把接口调用内联成直接调用。运行期如果动态加载了新实现（新的 Jar、新的子类、代理类生成），这个假设就不成立了，所有依赖它的已编译代码都要去优化。

其次是**类型 profile 冲突**：profile 记录显示某处只出现类型 A，于是按 A 布局内联；后来 B 出现，假设被打破。

还有一类是**隐式异常路径被走到**：编译器把 `null` 检查优化成「先做访问，出异常再走 uncommon trap」，正常路径零成本；一旦真抛了 `ArrayIndexOutOfBoundsException` 之类的隐式异常，就会进慢路径甚至去优化。

##### Q3.1.1: 频繁去优化有什么表现，怎么排查？

表现是「性能时好时坏」「上线一段时间后 QPS 抖动」，用 `-XX:+PrintCompilation` 能看到同一个方法被反复编译，或出现 `made not entrant`、`deoptimized` 之类的记录。进一步可以用 `-XX:+UnlockDiagnosticVMOptions -XX:+TraceDeoptimization` 打印详细原因。

排查方向：

- 是不是运行期动态生成了大量实现类（CGLIB 代理、反射代理、脚本引擎），让某个接口的实现类型不断膨胀
- 是不是用反射/`MethodHandle` 高频调用同一个调用点，类型不稳定
- profile 数据本身是否被计数器衰减清掉，导致编译决策反复

## 常见坑

- **说「JIT 会把所有热点方法都编译成机器码，编译一次永久生效」** —— 编译结果可能因为去优化而失效，退回解释执行后还要重新编译
- **说「逃逸分析就是栈上分配」** —— 逃逸分析是分析手段，栈上分配只是它可能带来的一种结果；HotSpot 实际主要落地为标量替换，并未真正实现把完整对象分配在栈帧上
- **说「开了逃逸分析，堆内存压力立刻消失」** —— 只有能被证明不逃逸的对象才可能被优化，逃逸的对象还是老老实实分配在堆上，还要被 GC 管理
- **把方法内联当成可有可无的小优化** —— 它是逃逸分析、常量传播、锁消除能生效的前提，不内联时跨方法的优化基本做不了
- **说「方法调用计数器就够了，回边计数器是冗余设计」** —— 只调用一次但内部有长循环的方法靠调用计数器永远编译不了，回边计数器触发的是 OSR
- **说「锁消除是因为 JVM 发现锁没用」** —— 准确的因果是「逃逸分析证明锁对象不可能被其他线程拿到」，所以锁必然不产生竞争
- **把 `-XX:CompileThreshold` 的 10000 当成分层编译下的 C2 阈值** —— 分层编译开启时用的是 `Tier3InvocationThreshold` / `Tier4InvocationThreshold` 这一组阈值；`CompileThreshold` 主要对应关闭分层编译的场景
- **说「OSR 就是重新调用一次编译后的方法」** —— OSR 不退出当前栈帧，是在循环回跳点上就地替换，当前这次调用继续跑

## 加分点

- 能点明 **HotSpot 的逃逸分析主要收益是标量替换，而不是教科书式的栈上分配**，并解释两者区别：标量替换后对象根本不存在，栈上分配则是对象仍在栈帧上
- 知道 `StringBuffer` 的 `append` 是 `synchronized` 方法，而循环里 `new` 出来的 `StringBuffer` 通常不逃逸，所以锁会被消除——这是「锁消除」最有说服力的例子
- 能讲清**去优化的栈帧重建**：优化后的栈帧布局和解释器不同，必须先重建出解释器可识别的栈帧（局部变量表、操作数栈）才能继续执行，这是去优化开销的主要来源，也是它不能被随意滥用的原因
- 提到 **CHA（类层次分析）与去优化的关系**：动态生成代理类、热部署、OSGi、脚本引擎这类场景会让某个接口的实现类型不断变化，是去优化的高发区
- 知道 **CodeCache 写满后 JIT 停止编译**（`-XX:ReservedCodeCacheSize`、`-XX:+PrintCodeCache`），这会导致「运行很久之后性能突然下降」，且现象容易被误判成内存泄漏
- 能提到 profiling 带来的成本：C1 的第 3 层为了采集完整 profile，会插入类型检查等桩代码，这就是为什么它比第 1 层的代码慢
- 知道 `-XX:MaxInlineSize` 和 `-XX:FreqInlineSize` 两个内联阈值的存在，以及 `-XX:+PrintInlining` 可以看到 `too big` 这类拒绝原因
- 横向提到 Graal JIT（JEP 317，`-XX:+UseJVMCICompiler`）是 C2 的实验性替代实现，但生产上默认仍是 C2

## 版本差异

| 版本 | 差异 |
|---|---|
| Java 6u14 | 逃逸分析在 HotSpot Server VM 上转为默认开启；此前需要显式 `-XX:+DoEscapeAnalysis` |
| Java 8 | 分层编译（`-XX:+TieredCompilation`）默认开启 |
| Java 9 | 引入 Graal 作为实验性 JIT（JEP 317），需 `-XX:+UseJVMCICompiler`，默认仍是 C1/C2 |
| Java 10 起 | G1 成为默认 GC，JIT 侧无破坏性变化；分层编译、逃逸分析默认值延续 |
| Java 17 / 21 | 分层编译与逃逸分析仍是默认行为；`-XX:+DoEscapeAnalysis`、`-XX:+EliminateAllocations` 默认 `true` 未变 |
