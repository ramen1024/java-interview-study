## 电梯版回答

大 key 的核心危害是单次操作耗时长：Redis 6.0 引入的多线程只用于网络 IO，命令执行仍然是单线程，所以一次 O(N) 的读取或 DEL 会卡住后面所有请求；此外还会打满网络带宽、在集群里造成数据倾斜、拖慢持久化和主从同步。发现大 key 用 redis-cli --bigkeys，它基于 SCAN 增量扫描，不会长时间阻塞，再用 MEMORY USAGE key 看单个键的内存；线上绝不能用 KEYS。热 key 的危害是流量集中到单个节点或分片，集群加节点也分摊不掉，因为一个 key 只属于一个 slot。处理大 key 的思路是拆成多个小 key、压缩 value、用 UNLINK 异步删除、控制集合元素数量；处理热 key 的思路是本地缓存加失效通知、按随机后缀打散到多个副本、读写分离到多个从库、在入口限流。预防比补救重要：提前定规范并在监控里对大 key 和节点 QPS 倾斜告警。

## 展开讲解

### 大 key 与大 value

没有官方阈值，Redis 也不会因为你 set 了一个大 value 就报警。
工程上常见的判断标准是**操作这个键的代价**：一次 `GET` 要传几十 KB、
一次 `HGETALL` 要返回几万个字段、一次 `DEL` 要释放几百 MB 内存，
就该算大 key。常见的经验约定（不是官方标准）是 String 超过 10KB、
或集合类型元素数超过几千个时开始关注，但这个数字要结合实际访问模式定。

大 key 有两种形态，危害不同：

- **单 value 很大**（一个 String 几 MB）：读写时序列化/传输/网络开销大。
- **集合元素很多**（一个 Hash 几十万字段）：危害更大，
  因为还有一大类 O(N) 命令会作用在它上面。

### 大 key 的危害

**① 阻塞命令执行（最致命）**。Redis 的命令执行是单线程的，
一个耗时命令会把后续所有客户端的命令都排在后面：

```
GET bigkey            → 一次传输几 MB，网络先慢
HGETALL bighash       → O(N) 遍历几十万字段，主线程卡住
DEL bigkey            → 释放内存是 O(N)，主线程同步等待
LRANGE biglist 0 -1   → 把整个大列表取出来，内存和网络双爆
```

注意：**Redis 6.0 的多线程只用于网络 IO（读写 socket），
命令的实际执行仍然在单线程里**。所以"6.0 之后有多线程了，
大 key 不卡了"是错误理解。

**② 打满网络带宽**。一个几 MB 的 value 在高 QPS 下就是几十 Gbps 的流量，
可能先把网卡打满，而不是 CPU。

**③ 集群数据倾斜**。一个 key 整体落在某个 slot、某个节点上，
一个 5GB 的 Hash 会让这个节点的内存明显高于其他节点，
扩容时也不好迁移（迁移大 key 会长时间阻塞）。

**④ 拖慢持久化与主从同步**。BGSAVE/AOF 重写要序列化这个大 key；
主从全量同步要把整个 RDB 传过去；AOF 里这个大 key 的每条修改
也更大，放大器效应明显。

**⑤ 触发内存抖动**。删除大 key、过期大 key 时集中释放大量内存，
可能引起分配器碎片和延迟抖动。

### 怎么发现大 key

| 手段 | 原理 | 注意 |
|---|---|---|
| `redis-cli --bigkeys` | 用 SCAN 增量遍历，对每个键按类型统计长度，报告**每种类型里最大的一个** | 基于 SCAN 采样，不会像 KEYS 那样长时间阻塞；但只报告最大的那个，找不到"所有"大 key |
| `MEMORY USAGE key [SAMPLES n]` | 估算某个键占用的内存字节数 | 精确到单键；集合类型是采样估算 |
| 离线分析 RDB | 用 `redis-rdb-tools` 等工具解析 RDB 文件 | 最全面、对线上零影响；需要拿到 RDB |
| 慢查询日志 | 记录耗时超过 `slowlog-log-slower-than` 的命令 | 大 key 的操作会表现为慢命令，能反推是哪个 key |
| `--scan` + 业务侧统计 | 自己遍历后调 `STRLEN`/`LLEN`/`HLEN`/`SCARD`/`ZCARD` | 灵活，但要注意扫描节奏 |

```bash
redis-cli --bigkeys              # 每种类型最大的 key
redis-cli --bigkeys -i 0.1       # 每 100 条 SCAN 休息 0.1 秒，进一步降低影响
redis-cli MEMORY USAGE myhash    # 单键内存估算
```

`--bigkeys` 的实现要点值得知道：它内部用 `SCAN` 而不是 `KEYS`，
所以是分批遍历、不会一次性阻塞；它会对每个键调用类型对应的长度命令，
最后按类型汇报最大的那个。**它不等于"找出所有大 key"**，
如果有多个大 key，只会看到最大的。

### 热 key 的危害

热 key 指**单位时间内访问量高度集中在某一个键上**。

**① 单个节点被打爆**。集群里一个 key 只属于一个 slot、一个节点，
所有对它的请求都落在同一个节点上。这个节点的单线程命令处理能力和
网卡带宽很快成为瓶颈，其他节点却很空闲。

**② 加节点也分摊不掉**。这是热 key 最麻烦的地方：集群是靠
"不同 key 分到不同节点"来横向扩展的，而热 key 永远是同一个 key，
再加节点它还是落在那一个节点上。所以热 key 问题是**架构层面**的，
不是容量问题。

**③ 可能击穿到数据库**。热 key 如果过期瞬间，大量请求同时未命中，
会一起去查库（缓存击穿），把数据库也拖垮。
热 key + 过期时间 = 双重危险。

### 怎么发现热 key

| 手段 | 说明 |
|---|---|
| `redis-cli --hotkeys` | 基于 LFU 的访问频率计数找热点键；**要求 `maxmemory-policy` 是 LFU 系列**，否则报错 |
| `MONITOR` | 打印所有命令，能直观看到热点，但**性能损耗大，只能短时间排查用**，绝不能常开 |
| 慢查询日志 | 间接发现热点（热点命令的调用次数多） |
| 客户端/代理侧埋点 | 在 SDK 或 Proxy 层统计 key 的 QPS，精度高、成本可控；大厂的热点探测框架走这条路 |
| 节点级指标 | 看各节点 QPS/带宽是否严重不均，定位到节点后再找 key |

```bash
# 前提是 maxmemory-policy 为 allkeys-lfu / volatile-lfu
redis-cli --hotkeys
redis-cli OBJECT FREQ mykey       # 单键的 LFU 频率计数
```

### 处理大 key

**① 拆分成多个小 key**。这是最根本的手段：

```
原来的 key：user:feed:1001  （一个 List 存 10 万条）
拆成：user:feed:1001:0 ~ user:feed:1001:99  （每个 List 1000 条）
读取时按分片路由，或按页取某一小段
```

Hash 可以按字段 hash 拆到多个 Hash；List 可以按时间/序号分桶。

**② 压缩 value**。如果业务允许，value 用压缩算法（如 Snappy、LZ4）
存二进制，读出来再解压：省内存和带宽，代价是 CPU。

**③ 用 `UNLINK` 异步删除**。删除大 key 不要用 `DEL`：

```redis
DEL bigkey        -- O(N)，同步释放内存，主线程卡住
UNLINK bigkey     -- 从 keyspace 摘除是 O(1)，内存回收交给后台线程
```

还可以用 `lazyfree-lazy-user-del yes` 让显式 `DEL` 也走异步释放路径。

**④ 控制集合元素数量**。写入时就设置上限（比如 List 只保留最近
N 条、Hash 字段数超限就分片），而不是等到变成大 key 再治理。
`LPUSH` + `LTRIM` 是保留定长列表的常用组合。

**⑤ 过期清理也走异步**。大 key 到期被删同样会阻塞，
可用 `lazyfree-lazy-expire yes` 让过期删除异步化。

### 处理热 key

**① 本地缓存 + 失效通知**。最有效的手段：在应用本地（Caffeine 等）
缓存热 key，请求不再落到 Redis。

```
读：先查本地缓存 → 未命中再查 Redis → 回填本地缓存
写：更新 Redis → 发失效消息（pub/sub / MQ）→ 各节点清本地缓存
```

代价是引入一致性窗口，需要处理"本地缓存还没失效"的短暂旧值；
如果业务能接受秒级最终一致，这个方案性价比最高。

**② 按随机后缀打散到多个副本**。把一个逻辑 key 复制成 N 份：

```
key:hot:123      →  key:hot:123:0  key:hot:123:1  ...  key:hot:123:9
读：随机选一个后缀（或按请求 hash 取模）
写：N 份都写（或写主份 + 异步同步）
```

读流量被分摊到 N 个 key，而它们分属不同 slot、可由不同节点承载。
代价是写放大和一致性处理（N 份要一起更新）。

**③ 读写分离到多个从库**。热 key 的读请求分散到多个从库上，
利用从库的读能力。注意主从延迟对一致性有影响的场景要谨慎。

**④ 入口限流 + 请求合并**。在网关或应用层对单 key 限流；
对同一 key 的并发回源请求做合并（singleflight 思路），
只让一个请求去查库/重算，其余等结果。这同时能防缓存击穿。

**⑤ 预热与错峰**。秒杀、大促这类可预知的热点提前把数据加载到
本地缓存和多个 Redis 副本；TTL 加随机抖动避免集中过期。

### SCAN 与为什么禁用 KEYS

`KEYS pattern` 会**一次性遍历整个 keyspace 并把所有匹配的键返回**，
是 O(N) 且不可中断的阻塞命令。线上执行几乎必然造成秒级卡顿，
所以生产环境应视为禁用命令（很多云厂商直接在控制台屏蔽）。

`SCAN` 把遍历拆成多次调用：

```redis
SCAN 0 MATCH user:* COUNT 100
-- 返回：1) 下一次的游标（字符串数字）  2) 这一批的键
-- 游标为 "0" 表示遍历结束
```

语义要点：

- **游标不是"偏移量"**，不能理解成页码；它由内部的 reverse binary
  iteration 算法产生，只能"拿上一轮的返回值继续调"。
- **`COUNT` 只是提示**，Redis 可能返回多于或少于 COUNT 个元素，
  不能依赖它做分页。
- **同一批可能返回重复元素**，调用方需要自己去重。
- **不提供快照一致性**：遍历期间增删的键，是否出现在结果里取决于
  它是否全程存在；从头到尾都在的键保证会被返回，中途才加的键不保证。
- `MATCH` 是在取出元素**之后**过滤，所以 `COUNT` 小、匹配率低时
  可能要很多轮才凑够结果。
- Redis 6.0 起 `SCAN` 支持 `TYPE` 选项，可按类型过滤
  （注意：`TYPE` 是服务端过滤，比 `MATCH` 更高效）。
- `HSCAN` / `SSCAN` / `ZSCAN` 是同一套游标语义，用于遍历大集合；
  对大 Hash/List 用 `HSCAN` 分批取，而不是 `HGETALL`。

## 追问链

### Q1: 大 key 阻塞的根因是什么？为什么说 6.0 的多线程也救不了它？

根因是 **Redis 的命令执行模型仍然是单线程**。

Redis 6.0 引入的多线程（`io-threads`）只把**网络 IO** 并行化了：
多个线程负责读取 socket、解析协议、写回响应，而**命令的实际执行
（包括数据结构的查找和操作）仍然在一个主线程里串行完成**。
这样设计是因为命令执行一旦并行，就要面对所有数据结构的并发安全问题，
复杂度极高。

所以大 key 的几种操作都躲不开主线程阻塞：

```
GET 一个几 MB 的 String   → 命令本身 O(1)，但内存拷贝和网络发送放大
HGETALL / LRANGE / SMEMBERS → 命令本身 O(N)，遍历全部元素
DEL 大 key                 → 释放内存 O(N)，主线程同步释放
```

阻塞的后果是**连锁的**：主线程被占住的这段时间，
所有其他客户端的命令都在等待，应用的响应时间直线上升，
甚至触发客户端超时重试、重试又加重负载。

判断一个操作是不是"大 key 敏感"，看两点：
**命令复杂度是否 O(N)**，以及 **N 是不是很大**。
`HGET` 单个字段是 O(1)，对一个超大 Hash 也很快；
`HGETALL` 才是问题。

#### Q1.1: 那 `UNLINK` 为什么能解决 `DEL` 大 key 的阻塞？

因为 `DEL` 和 `UNLINK` **把"从 keyspace 摘除"和"释放内存"拆开了**。

```
DEL bigkey    ：
  ① 从 dict 里摘除 key（很快，O(1) 级别）
  ② 同步释放 value 占用的所有内存（大 key 是 O(N)，主线程全程阻塞）

UNLINK bigkey ：
  ① 从 dict 里摘除 key（很快）
  ② 把"释放这些内存"的任务丢进后台队列
  ③ 后台线程慢慢回收，主线程立刻返回
```

所以 `UNLINK` 的复杂度描述是"每个 key O(1) 摘除 + 后台 O(N) 回收"。
主线程不被内存回收卡住，其他命令能继续处理。

配套的 lazyfree 配置可以把其他会产生大块内存释放的路径也异步化：

```conf
lazyfree-lazy-user-del yes      -- 让显式 DEL 也像 UNLINK
lazyfree-lazy-expire yes        -- 过期删除大 key 时异步释放
lazyfree-lazy-eviction yes      -- 淘汰大 key 时异步释放
lazyfree-lazy-server-del yes    -- 隐式删除（如 RENAME 覆盖、SET 覆盖大 value）异步
```

监控上可以看 `INFO memory` 里的 `lazyfree_pending_objects`，
表示还有多少个对象在等待后台释放。注意：**`UNLINK` 只是不阻塞主线程，
不减少总的内存释放工作量**；如果短时间内大量删除大 key，
后台线程和内存分配器仍会承压。

##### Q1.1.1: 把大 key 拆成多个小 key 之后，原来的批量读取怎么办？

要分情况改造成"分段/分页读取"，而不是想办法一次全拿：

```
原来：LRANGE biglist 0 -1        → 一次拿 10 万条
改造：LRANGE biglist:0 0 99        → 只取需要的那一段
      或按业务把逻辑分组（按用户、按时间桶）

原来：HGETALL bighash            → 一次拿几十万字段
改造：HMGET bighash f1 f2 f3      → 只取需要的字段
      或在写入时把字段按 hash 拆到 bighash:0..N 多个 Hash
```

聚合类需求（求和、计数、分页）有两种应对：

- **应用层聚合**：读取多个小 key 后在应用里合并。
  可以用 pipeline 或 MGET 减少往返次数，但注意 MGET 本身在大 key 上也会放大。
- **维护汇总 key**：写入时同步更新一个小的汇总值（用 `HINCRBY` 等），
  读汇总时直接读它，避免遍历。代价是写入更复杂、要保证汇总与明细一致。

根本原则是：**不要设计出"必须一次取完"的访问模式**。
分页、按需取字段、增量维护汇总，这三种改造方向能覆盖绝大多数场景。
改造时要连同上游接口一起评审——很多大 key 问题本质是接口设计问题
（比如"一次性返回全部列表"的 API）。

### Q2: 热 key 为什么加节点也分摊不掉？怎么处理？

因为**一个 key 只属于一个 slot，一个 slot 只属于一个节点**。

```
key → CRC16(key) mod 16384 → slot → 节点
```

这个映射是确定性的。热 key 就是"同一个 key 被反复访问"，
所以无论集群有多少个节点，它的所有请求都必然打到承载它那个 slot 的
那一个节点上。集群的横向扩展能力建立在"不同 key 分到不同节点"上，
对"单个 key 的集中访问"完全无效。

于是那个节点的单线程命令处理、网卡带宽、连接数会先到瓶颈，
其他节点空闲——加机器不但没用，反而增加了集群维护成本。

处理思路要让**单个逻辑数据对应多个物理 key**：

- **本地缓存**：请求根本不到 Redis，效果最好
- **加随机后缀复制多份**：把 1 个热 key 变成 N 个，分摊到多节点
- **读从库**：利用主从架构把读流量分散
- **限流 + 请求合并**：削峰，同时防击穿

选哪种取决于业务对一致性和实时性的要求。

#### Q2.1: 本地缓存 + 多副本打散，怎么保证数据一致性？

分两个手段看，各自的坑不同。

**本地缓存（Caffeine 等）的一致性**：

```
读：本地缓存 → Redis → DB，逐层回填
写：更新 Redis/DB → 发布失效通知 → 各应用节点清掉本地缓存
```

- 失效通知可以用 Redis pub/sub（简单，但消息不可靠、有丢失和断连问题）
  或 MQ（可靠但更重）。用 pub/sub 时要有兜底：
  本地缓存设一个较短的 TTL（比如几秒），即使通知丢了也能自动过期。
- 一致性窗口是 **"通知到达前"** 的这段时间，通常毫秒到秒级。
  业务要能接受这段旧值。
- 应用节点数量多、上下线频繁时，通知的到达复杂度会上升（要处理重连补偿）。

**多副本打散的一致性**：

```
读：按请求 hash 取模选 key:hot:123:{0..N-1} 随机读一个
写：N 份都要写（或写一份主本 + 异步刷其余）
```

- **写放大 N 倍**，且 N 份之间可能暂时不一致。
  读流量被打散到 N 个节点的收益，要大于写放大和一致性处理的成本。
- 如果业务是"读极多写极少"（典型热 key 场景），这个代价通常划算。
- 更新时要注意**原子性**：可以用 Lua 脚本一次更新所有副本（保证同 slot 才能用），
  或接受短暂不一致、靠 TTL 收敛。

实务上的组合拳是：**本地缓存扛主要流量 + Redis 多副本兜底 +
短 TTL 保证最终一致**。不要指望某一种手段单打独斗。

##### Q2.1.1: 突发热点（比如秒杀开始）怎么提前发现并处理？

突发热点的难点是**不可预知**，所以要靠"探测 + 快速响应"而不是"提前规划"。

**探测**：

```
① redis-cli --hotkeys（需要 LFU 策略）定期扫描，发现频率异常高的 key
② 节点级指标告警：单节点 QPS、带宽、CPU 显著高于集群均值
③ 代理/SDK 层做 key 维度的 QPS 统计（大厂热点探测框架走这条路，
   能做到秒级发现并自动推送）
④ 慢查询日志：热点不一定慢，但大批量访问会表现为 QPS 而非单条慢命令，
   所以慢查询只能作为辅助
```

**处理**：

- **请求合并（singleflight）**：同一个 key 的并发回源只放一个请求出去，
  其余等待结果。这能同时抗"热点"和"击穿"。
- **本地缓存 + 短期不可变**：秒杀的商品信息这类数据在活动期间基本不变，
  可以在活动开始前预加载到本地缓存并设较短 TTL。
- **入口限流**：在网关按 key/用户维度限流，保护后端；
  宁可让部分请求快速失败，也不要让整个节点被拖死。
- **降级**：热点数据不可用时返回兜底值（默认值、静态页、排队提示），
  保证核心链路不雪崩。
- **预热**：可预知的热点（大促）提前把数据放进本地缓存和多个副本。

一个容易被忽略的点：**热 key 和缓存击穿经常同时发生**。
热点 key 一旦过期，瞬时大量未命中请求涌向数据库。
所以热 key 的 TTL 要加随机抖动，或者干脆让它逻辑上不过期、
由后台任务主动更新。

### Q3: 怎么系统地排查大 key？`--bigkeys` 的原理和局限是什么？

排查要有层次，从"性价比最高的手段"开始：

```
① redis-cli --bigkeys         线上快速初筛，几乎无侵入
② MEMORY USAGE key            对可疑键做精确评估
③ 慢查询日志                   从耗时命令反推
④ 离线 RDB 分析                要全面清单时的最终手段
```

`redis-cli --bigkeys` 的原理：

```
用 SCAN 增量遍历 keyspace（不是 KEYS，所以分批、不长时间阻塞）
对每个键根据 TYPE 调用对应的长度/大小命令：
  string → STRLEN      list → LLEN      hash → HLEN
  set    → SCARD       zset → ZCARD     stream → XLEN
记录每种类型里最大的那个键，遍历结束后汇总输出
```

它的局限：

- **每种类型只报告最大的一个 key**，有多个大 key 时看不到其他的。
- `STRLEN` 是字节数，集合类型是**元素个数**，不是内存占用——
  一个 100 万元素的 Hash 和一个 100 万元素的 List 内存差别可能很大。
  要看真实内存还得用 `MEMORY USAGE`。
- 遍历本身仍有开销（虽然是分批），可用 `-i` 参数控制节奏。
- 它不知道"业务上应该多大"，只能告诉你"谁最大"。

所以完整的排查是组合：`--bigkeys` 初筛 → `MEMORY USAGE` 确认 →
必要时离线上 `redis-rdb-tools` 拿全量清单。

#### Q3.1: `SCAN` 的游标语义是什么？为什么线上绝不能用 `KEYS`？

**`KEYS` 的问题**：单条命令遍历整个 keyspace，O(N) 且不可中断。

```
KEYS user:*
→ 遍历所有键 → 收集所有匹配的 → 一次性返回
→ 主线程全程阻塞，键越多越久（百万键级别可达秒级）
→ 期间所有其他客户端请求排队
```

这是**阻塞式**操作，没有任何"分批"的余地，所以生产环境应视为禁用。

**`SCAN` 的语义**：

```redis
SCAN cursor [MATCH pattern] [COUNT count] [TYPE type]
```

- 返回 `[下一个游标, 这一批的元素]`；**下一个游标为 "0" 表示结束**。
- 游标是内部 reverse binary iteration 算法产生的**不透明值**，
  不是偏移量、不是页码，**只能用上一轮的返回值继续调**。
  用 `SCAN 0` 反复从头开始，或者自己推算游标，都是错的。
- **`COUNT` 只是提示**：Redis 可能返回更多或更少的元素，
  不能拿它当分页大小。
- **可能返回重复元素**：调用方要去重。
- **不保证快照**：遍历期间被删除的键可能漏掉，新加的键可能看不到；
  但**从头到尾都存在的键保证会被返回**（这是 SCAN 的核心保证，
  也是它能替代 KEYS 的原因）。
- `MATCH` 是取出元素**之后**在客户端侧过滤，匹配率低时效率差；
  Redis 6.0 的 `TYPE` 是服务端过滤，更高效。
- `HSCAN`/`SSCAN`/`ZSCAN` 语义相同，是遍历大集合的正确方式
  （替代 `HGETALL`/`SMEMBERS`/`ZRANGE 0 -1`）。

一个典型用法：遍历要控制节奏，避免长时间占用 CPU：

```bash
redis-cli --scan --pattern 'user:*' --count 100
```

##### Q3.1.1: 那要拿到精确的大 key 全量清单，有什么更可靠的办法？

线上采样类工具都有各自盲区，要**精确且全面**，答案是**离线分析 RDB**：

```
① 在从库上或低峰期触发 BGSAVE，拿到 RDB 文件
② 用 redis-rdb-tools（rdb 命令行）解析：
   rdb -c memory dump.rdb --bytes 10240 -f bigkeys.csv
   --bytes 可以按"内存占用超过多少"过滤
③ 得到「键名 + 类型 + 元素数 + 内存字节数」的全量清单
```

优点：对线上零影响（只读文件）、结果精确（直接读序列化后的数据）、
能拿到真实内存占用而不是估算。缺点是要有 RDB 文件、解析有额外成本，
不能实时反映。

如果必须在线精确判断，可以对 `--bigkeys` 初筛出的候选
逐个 `MEMORY USAGE key`（它内部对集合类型是采样估算，可加 `SAMPLES`
控制精度）。另外两个辅助视角：

```redis
INFO memory                  -- 整体内存构成，判断是否被少数键撑大
INFO commandstats            -- 哪些命令调用次数异常（可能在对大 key 反复操作）
SLOWLOG GET 10               -- 最近最慢的命令，直接看 key
```

排查完之后更重要的是**防复发**：把"集合元素上限"写进开发规范、
在写入路径做长度检查、监控里对大 key 和节点倾斜告警。
大 key 是设计时埋下的，治理应该在写入端而不是等它出现。

## 常见坑

- **说「Redis 6.0 之后命令执行是多线程了，大 key 不会阻塞」** ——
  6.0 的多线程**只用于网络 IO**，命令执行仍是单线程，
  O(N) 命令照样阻塞所有客户端
- **用 `DEL` 删除大 key** ——
  `DEL` 同步释放内存，大 key 会长时间阻塞主线程；应该用 `UNLINK`
  （或配 `lazyfree-lazy-user-del yes`）
- **用 `KEYS` 或 `HGETALL` / `LRANGE 0 -1` / `SMEMBERS` 遍历大集合** ——
  这些都是一次性 O(N) 的阻塞操作；遍历应用 `SCAN`/`HSCAN`/`SSCAN`/`ZSCAN`，
  取数应按需分页
- **说「`--bigkeys` 能列出所有大 key」** ——
  它每种类型只报告**最大的一个**，其余大 key 看不到；
  要全量清单得离线分析 RDB
- **把 `--bigkeys` 的 `STRLEN`/`LLEN` 当成内存占用** ——
  那是长度不是字节数；真实内存要用 `MEMORY USAGE`
- **以为热 key 加节点就能解决** ——
  一个 key 只属于一个 slot/节点，加节点不会改变它的落点；
  必须让"一个逻辑数据对应多个物理 key"（本地缓存、随机后缀多副本、读从库）
- **把 `MONITOR` 当常规监控使用** ——
  `MONITOR` 会输出所有命令，性能损耗大，
  只能短时间排查热点，绝不能长期开着
- **说「`redis-cli --hotkeys` 随时都能用」** ——
  它依赖 LFU 的频率计数，**要求 `maxmemory-policy` 是 `allkeys-lfu`
  或 `volatile-lfu`**，其他策略下不可用
- **把 `SCAN` 的游标当页码 / 用 `COUNT` 做分页** ——
  游标是不透明的、`COUNT` 只是提示，都可能返回重复元素；
  正确做法是把上一轮返回的游标传回去，直到返回 0
- **认为 `SCAN` 结果有快照一致性** ——
  遍历期间的增删会影响结果，只有"全程存在"的键保证被返回
- **只在大 key 出现后才治理，不管写入端** ——
  大 key 是设计问题，应该在写入时限制集合长度、在规范里定死阈值，
  并做监控告警
- **忽略热 key 与缓存击穿的叠加** ——
  热点 key 过期瞬间大量请求回源到数据库，需要在 TTL 加抖动
  或用后台主动更新避免集中失效

## 加分点

- 能准确指出 **Redis 6.0 多线程的边界**（只并行网络 IO，
  命令执行单线程），这是很多八股的常见错误点
- 能区分"命令复杂度 O(N)"和"value 体积大"两类大 key 问题，
  并举出**大 Hash/List 最危险**（既有 O(N) 命令，元素又多）
- 知道 **`UNLINK` 把"摘除"和"释放内存"拆开**的原理，
  以及 `lazyfree-*` 系列配置能把过期、淘汰、隐式删除也异步化，
  还知道用 `lazyfree_pending_objects` 观察积压
- 能说清 **`--bigkeys` 只报告每类最大的一个**、且返回的是长度不是内存，
  这直接决定了排查要配合 `MEMORY USAGE` 或离线 RDB 分析
- 知道 **`--hotkeys` 依赖 LFU 策略**，这个前置条件经常被忽略
- 能解释热 key **"加节点无效"的根本原因**（slot 映射是确定性的），
  并给出"一个逻辑 key 对应多个物理 key"的统一思路
- 提到**本地缓存的兜底 TTL**：即使 pub/sub 失效通知丢了，
  短 TTL 也能保证最终一致——这是实践中比"通知机制选型"更重要的设计
- 能准确描述 **SCAN 的三条保证与三条不保证**：
  保证"全程存在的键都会被返回"，不保证快照一致、不保证不重复、
  `COUNT` 不是分页大小
- 提到 **`HSCAN`/`SSCAN`/`ZSCAN`** 才是遍历大集合的正确方式，
  而不是只盯着顶层 `SCAN`
- 能把大 key 问题上升到**接口设计**：很多大 key 源于
  "一次性返回全量列表"的 API，治本要改接口而不是只改存储
- 知道排查的**性价比排序**（`--bigkeys` 初筛 → `MEMORY USAGE` 精查 →
  离线 RDB 全量），而不是一上来就搞重型方案

## 版本差异

| 版本 | 差异 |
|---|---|
| Redis 4.0 | 引入 `UNLINK`（异步删除）与 `lazyfree-*` 系列配置；引入 `MEMORY USAGE` / `MEMORY DOCTOR` 等 `MEMORY` 命令族；引入 LFU 策略（是 `--hotkeys` 的基础） |
| Redis 6.0 | 引入网络 IO 多线程（`io-threads`），**命令执行仍单线程**；`SCAN` 新增 `TYPE` 选项（服务端按类型过滤） |
| Redis 7.0 | `maxmemory-clients` 可限制客户端输出缓冲，缓解"客户端积压把内存吃满"这类问题；Function 等特性使热点逻辑可下沉服务端 |
