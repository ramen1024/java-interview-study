## 电梯版回答

主流方案是 Cache-Aside：先更新数据库再删除缓存，而不是更新缓存。删缓存比更新缓存好，因为删除是幂等的，而且避免为可能没人读的数据做计算。顺序上必须先更新数据库，反过来「先删缓存再更新数据库」有一个更危险的不一致窗口——删完缓存、还没更新数据库时如果有并发读把旧值写回缓存，这个旧值会长期存在。但要清楚 Cache-Aside 也只是最终一致，在并发读写下仍然存在不一致窗口，所以缓存的定位是「降低数据库压力」而不是「保证正确性」。强一致做不到，因为缓存和数据库是两个独立的存储，没有分布式事务保证，任何方案都只能缩小不一致窗口。要提升可靠性就用延迟双删，或者订阅 binlog 异步删除作为兜底。

## 展开讲解

### 为什么不更新缓存而是删除缓存

三种写法对比：

| 写法 | 问题 |
|---|---|
| 更新数据库 + 更新缓存 | 并发下两个线程可能以相反顺序写缓存，留下脏数据；且缓存值可能需要复杂计算，为无人读取的数据付出代价 |
| 删除缓存 + 更新数据库 | 不一致窗口大（下文详述） |
| **更新数据库 + 删除缓存** | Cache-Aside 标准做法，不一致窗口最小 |

**「删除」相比「更新」的两个优势**：

1. **幂等**。删两次和删一次结果一样；而「更新」两次如果顺序错乱，
   最终值可能不对
2. **惰性重建**。删除后由下一次读取触发重建，
   避免为「写完就再没人读」的数据做无用功（写多读少的场景差别很大）

**为什么是「先更新数据库再删缓存」**：

看时序，两个方案的不一致窗口大小完全不同。

先删缓存、后更新数据库：

```
t0  线程 A：删缓存
t1  线程 B：读缓存未命中
t2  线程 B：读数据库，得到旧值
t3  线程 B：把旧值写入缓存        ← 关键：写回的是旧值
t4  线程 A：更新数据库为新值
    → 数据库是新值，缓存是旧值，且缓存不会自己过期（除非 TTL 到期）
    → 不一致持续到 TTL 结束
```

问题在于 **t1~t3 这个窗口包含了「读数据库 + 写缓存」两次往返**，
时间较长，且一旦发生，缓存里的旧值会长期存在。

先更新数据库、后删缓存：

```
t0  线程 A：更新数据库为新值
t1  线程 A：删缓存
    → 不一致窗口只存在于 t0~t1 之间
```

要产生不一致，必须满足更苛刻的条件：

```
t0  线程 B：读缓存未命中（此时缓存刚好已过期）
t1  线程 B：读数据库，得到旧值
t2  线程 A：更新数据库为新值
t3  线程 A：删缓存（缓存里本来就没东西，删了个寂寞）
t4  线程 B：把读到的旧值写入缓存     ← 又写回了旧值
    → 不一致
```

这个窗口要求「B 的读数据库发生在 A 的更新之前，
而 B 的写缓存发生在 A 的删缓存之后」——
需要 B 在 t1 到 t4 之间被长时间挂起（GC 停顿、线程调度），
概率远低于前一种方案。

**结论**：两个方案都不是绝对一致，但 Cache-Aside 的
不一致窗口更窄、发生条件更苛刻。**所以选它**。

### 删缓存失败怎么办

这是必须回答的追问。`DEL` 可能因为网络抖动、
Redis 短暂不可用而失败，此时缓存里是旧值，会长期不一致。

**方案一：消息队列重试**

```java
try {
    redis.delete(cacheKey);
} catch (Exception e) {
    // 删除失败，投递到 MQ，由消费者重试直到成功
    mqProducer.send(new CacheEvictMessage(cacheKey));
}
```

要点：

- 消费端必须**幂等**（删两次没危害，天然幂等）
- 必须**限制重试次数并告警**，否则会无限重试
- 严重依赖 MQ 的可靠性，所以 MQ 本身要持久化

**方案二：订阅 binlog（推荐，作为兜底）**

```
MySQL binlog → Canal → 解析出数据变更 → 删除对应缓存
```

优点非常明显：

- **不侵入业务代码**。业务只管写数据库，缓存失效由独立链路负责
- **补上了「应用侧删除失败」这条路径**。
  即使应用服务器的删除逻辑抛异常，binlog 这条链路照样会删
- 可以做更细的失效策略（只删变更的那条记录对应的 key）

代价是**引入了新组件**（Canal + MQ），
且要处理 binlog 解析延迟带来的时间差。

**实践建议：方案一和方案二叠加使用**。
应用侧同步删 + binlog 兜底。这样即使同步删除失败，
也有第二条路把缓存清掉。

### 延迟双删解决的是什么

针对「先删缓存再更新数据库」那个窗口的补救措施：

```java
// ① 删缓存
redis.delete(key);

// ② 更新数据库
db.update(entity);

// ③ 延迟一段时间后，再删一次
Thread.sleep(500);
redis.delete(key);          // 删掉并发读可能写回的旧值
```

**第 ③ 步针对的就是「并发读把旧值写回缓存」**。

但延迟双删有两个明显的落地困难：

1. **延迟时间难以确定**。必须大于「一次读数据库 + 写缓存」的耗时，
   但这个耗时在负载高时可能是几十毫秒，也可能是几秒。
   设小了没用，设大了影响接口响应（同步 `sleep`）
2. **同步 `sleep` 会拖长接口响应**，需要改成异步延迟任务
   （延时队列 / 定时任务），复杂度上升

**更重要的是**：如果一开始就用 Cache-Aside
（先更新数据库再删缓存），不一致窗口已经足够窄，
通常**不需要延迟双删**。

所以延迟双删的定位是：**在不得已采用「先删缓存」顺序时的补救**，
不是一个应该主动使用的通用方案。

很多人把延迟双删当成标准答案，其实它解决的是一个
「如果一开始顺序选对就不会有」的问题。

### 为什么做不到强一致

这是这个问题最本质的部分。**强一致做不到，不是方案不够好，
而是架构决定的**：

**原因一：两个独立存储，没有跨存储的事务**

```
数据库事务：BEGIN → UPDATE → COMMIT
Redis 操作：DEL

这两者之间没有全局事务协调者，
无法保证「要么都成功、要么都失败」
```

要用分布式事务（2PC / TCC）保证？那会让「缓存」
这个本来为了性能的组件，变成拖慢性能的瓶颈——
缓存的意义就没了。

**原因二：并发读写天然存在窗口**

只要「读」和「写」是两个独立的操作序列，
在并发下就一定存在交错。

```
读序列：读缓存 → 读数据库 → 写缓存
写序列：写数据库 → 删缓存

无论怎么排序，都能构造出一种交错产生不一致
```

这是**逻辑上的必然**，不是实现缺陷。

**原因三：CAP 的取舍**

分布式系统在分区发生时必须在一致性和可用性之间选择。
缓存架构选择了可用性和性能，代价就是放弃强一致。

所以正确的目标设定是**最终一致**：
不一致窗口尽可能小，且在有限时间（TTL）内自行收敛。

### 从业务侧兜底

既然缓存只能做到最终一致，**关键数据的一致性要靠别的地方保证**：

| 手段 | 适用 |
|---|---|
| 唯一索引 | 防重复插入（如秒杀去重） |
| 乐观锁版本号 | 防并发覆盖（如库存扣减） |
| 状态机 CAS | 防重复执行（如订单状态流转） |
| 幂等设计（业务单号） | 防重复提交 |

**设计原则**：缓存只用来「加速读」，
**不承担正确性职责**。读缓存拿到数据后，
关键判断仍要落到数据库上：

```java
// ❌ 把缓存当权威数据源
Integer stock = cache.get("stock:" + goodsId);
if (stock > 0) { ... }              // 缓存可能就是旧的

// ✅ 关键判断落库，用条件更新保证原子性
int affected = db.update(
    "UPDATE stock SET count = count - 1 WHERE goods_id = ? AND count > 0", goodsId);
if (affected == 1) { /* 扣减成功 */ }
```

## 追问链

### Q1: 更新缓存和删除缓存，到底哪个更好？

**删除更好**，但理由需要说清楚，而不是「大家都说删除好」。

**理由一：并发下的正确性**

更新缓存时，两个并发写可能以相反顺序落到缓存：

```
t0  线程 A：计算新值 A'（数据库值为 A'）
t1  线程 B：计算新值 B'（数据库值为 B'）
t2  线程 B：更新数据库为 B'
t3  线程 A：更新数据库为 A'          ← 数据库最终是 A'
t4  线程 A：写缓存 = A'
t5  线程 B：写缓存 = B'              ← 缓存最终是 B'，与数据库不一致
```

**缓存和数据库的最终值不同**，且各自都被写对了。
而采用「删除」时，两个线程都是 `DEL`，无论顺序如何结果相同
（都是「缓存为空」），下一次读取会从数据库重建出正确值。

**理由二：写多读少时的浪费**

如果是「更新缓存」，每次写都要立刻重建缓存值。
但如果这个数据写完就再没人读，那次重建完全是浪费——
尤其当缓存值需要多表 join 或复杂计算时。

**「删除」把这个成本推迟到「真的有人读」的时候**，
符合惰性求值的思想。

**什么时候可以更新缓存**：

- 缓存值计算极其廉价（比如就是数据库里的一个字段）
- 读远多于写，且写后必读
- 能保证更新顺序（比如单线程消费同一个 key 的变更）

即使如此，用「删除」也不会差，只是少了一次重建的开销。

#### Q1.1: 那「先更新数据库再删缓存」还有 3 个更隐蔽的问题？

对，值得主动说出来，显示思考深度：

**问题一：删除失败导致长期不一致**

`DEL` 抛异常、Redis 短暂不可用、网络抖动都会导致删除失败。
此时缓存里是旧值，**且不会自行恢复**（除非 TTL 到期）。
所以必须配重试或 binlog 兜底。

**问题二：主从延迟导致读到旧的缓存值**

如果 Redis 是主从架构且读走从库（读写分离），
可能出现：

```
删主库的缓存 → 主库→从库复制延迟 → 从库仍有旧值
后续读请求路由到从库 → 读到旧值 → 甚至可能把它写回主库
```

解法是**缓存读写都走主库**，或者接受短暂的读旧值。

**问题三：多个缓存 key 需要同时失效**

一个业务操作往往影响多个缓存（比如更新商品要失效
「商品详情」「商品列表」「搜索结果」）。
如果只删了部分，剩下的是脏数据。

解法是**维护依赖关系**（哪些 key 依赖这类数据），
或者干脆给这类缓存设短 TTL 让它自然过期。

这三个问题合起来说明一件事：**Cache-Aside 不是银弹，
它是一个「不一致窗口较小且可收敛」的折中**。

### Q2: 什么场景下可以不用缓存一致性方案？

**如果 TTL 足够短，可以不做任何主动失效**。

```
方案：纯 TTL 过期，写入时不删缓存
  缓存 TTL = 5 秒
  不一致窗口最大 5 秒
  实现成本：几乎为零
```

适用判断标准：

```
能接受「最长 TTL 时间内的数据延迟」吗？
  能 → 纯 TTL，最简单可靠
  不能 → 上 Cache-Aside + 兜底
```

**这是一个很实用的判断**。很多团队一上来就搞
binlog 订阅 + 延迟双删 + MQ 重试的复杂架构，
但实际上如果业务能接受 5 秒延迟，纯 TTL 就够了。

**其他可以考虑的简化**：

| 场景 | 简化方案 |
|---|---|
| 数据基本不变（配置、字典） | 永不过期，变更时手动刷新 |
| 能接受分钟级延迟（排行榜） | 定时任务刷新，不主动失效 |
| 写极少读极多（商品详情） | 长 TTL + 写入时删除 |
| 数据量大且变化频繁（Feed 流） | 只缓存 ID 列表，详情单独缓存 |

**容量规划也可以用来简化**：如果数据总量小
（比如几万条配置数据），直接全量放缓存并设置长 TTL，
配合定时全量刷新，比「精确失效」简单得多也可靠得多。

#### Q2.1: 那「缓存不设过期时间」可以吗？

**不可以，除非你能保证缓存一定能被正确删除**——
而前面的分析已经说明这不成立。

不设 TTL 的风险：

```
① 删除失败 → 脏数据永久存在，无法自愈
② 内存泄漏 → 无淘汰的 key 持续占用，最终 OOM
③ 逻辑变更 → 缓存结构变了，旧数据反序列化失败
④ 全量重建手段缺失 → 出问题时无法靠"等它过期"恢复
```

**TTL 是缓存的最后一道防线**。它的作用是
「无论前面哪个环节出问题，数据最多错这么久」。

实践建议：

- **业务数据的 TTL 要设**，长度按「能接受的最大不一致时间」定
- **对一致性要求高的 key，TTL 设短一点**（比如 30 秒）
- **对变化极少的数据可以设长一些**（比如 1 小时），但仍要设

本项目 `ContentCache` 就是给所有缓存都设了 TTL，
并在 TTL 上叠加 ±10% 随机抖动防止雪崩：

```java
private Duration jitter(Duration ttl) {
    long base = ttl.toMillis();
    if (base <= 0) {
        return ttl;
    }
    long offset = ThreadLocalRandom.current().nextLong(base / 10 + 1);
    return Duration.ofMillis(base + offset);
}
```

另外，变更内容时本项目用的是**版本号整体失效**而不是逐个删除：

```java
public void evictAll() {
    Long version = stringRedisTemplate.opsForValue().increment(VERSION_KEY);
}
// key 形如 jis:cache:v9:kp:hashmap-internals
```

一次 `INCR` 就让所有旧 key 失效，旧 key 交给 TTL 自然淘汰。
这样既避免了「遍历删除」的开销（`KEYS` 会阻塞 Redis），
也避免了「部分 key 删除失败」的问题——
**要么全部生效（版本号变了），要么全部不生效**，
天然没有中间状态。

## 常见坑

- **说「先删缓存再更新数据库」是推荐方案** ——
  这个顺序的不一致窗口更大（包含「读库 + 写缓存」两次往返），
  且一旦发生旧值会长期留在缓存里
- **把延迟双删当标准答案** —— 它是在「先删缓存」顺序下的补救，
  如果一开始就用 Cache-Aside 通常不需要它
- **认为 Cache-Aside 能保证强一致** —— 它只是「不一致窗口较窄」，
  依然是最终一致
- **不设置 TTL，认为主动删除就够了** —— 删除失败时
  脏数据永久存在，无法自愈。TTL 是最后一道防线
- **把缓存当权威数据源做关键判断** ——
  「缓存里的库存 > 0 就下单」是典型的错误用法，
  关键判断必须落到数据库并用条件更新保证原子
- **忽略 Redis 主从延迟对一致性的影响** ——
  读写分离时可能从从库读到旧值，甚至把旧值写回主库
- **只有一个缓存 key 做失效** ——
  一个业务操作往往影响多个 key（详情、列表、搜索），
  遗漏任何一个都是脏数据
- **`KEYS` 遍历删除** —— 在生产环境会阻塞 Redis，
  应改用 `SCAN` 或版本号方案

## 加分点

- 能**画出两种顺序的时序图并比较窗口大小**，
  而不是只说「先更新数据库再删缓存更好」。
  指出「先删缓存」的窗口包含两次往返、
  而 Cache-Aside 需要「读发生在更新前且写缓存发生在删缓存后」
  这种更苛刻的交错
- 知道 **binlog 订阅（Canal）作为兜底**的价值在于
  「补上应用侧删除失败这条路径」，
  以及它「不侵入业务代码」的优点
- 能主动指出 **Cache-Aside 的三个隐蔽问题**：
  删除失败、主从延迟、多 key 依赖，
  说明理解而不是背方案
- 提到**版本号整体失效**这个技巧：一次 `INCR` 让所有旧 key 失效，
  既避免遍历删除，也避免「部分 key 删除失败」的中间状态。
  本项目就是用这个方案
- 能给出「**先问能不能不用复杂方案**」的判断标准：
  业务能接受 TTL 级别的延迟就用纯 TTL，实现成本几乎为零
- 把「缓存不承担正确性职责」上升为设计原则，
  并举出唯一索引、乐观锁、状态机 CAS 三种业务侧兜底手段
- 提到 `KEYS` 会阻塞 Redis（O(N) 且单线程），
  应使用 `SCAN` 或版本号方案；同时指出 `SCAN` 也有
  「遍历期间的变更不保证可见」的局限

## 版本差异

| 版本 | 差异 |
|---|---|
| Redis 2.8 | 引入 `SCAN` 游标遍历，取代会阻塞的 `KEYS` |
| Redis 4.0 | `UNLINK` 异步删除大 key，避免 `DEL` 阻塞主线程 |
| Redis 6.0 | 客户端缓存（Client-side caching / Tracking）可让 Redis 主动通知客户端失效本地缓存，多级缓存的一致性因此更容易实现 |
| Redis 7.0 | Function 可替代部分脚本场景；`SHUTDOWN` 与持久化流程优化，降低故障恢复时的数据丢失窗口 |
| MySQL 5.7+ | `ROW` 格式 binlog + `binlog_row_image = FULL` 是 Canal 解析的前提（需要拿到变更前后的完整行数据） |
| MySQL 8.0 | binlog 默认开启 `log_bin`；`ROW` 为默认格式，binlog 订阅链路更容易落地 |

    stem: 关于缓存更新策略，业界推荐的做法是？
    options:
      A: 先删缓存，再更新数据库
      B: 先更新数据库，再删缓存
      C: 先更新数据库，再更新缓存
      D: 只设 TTL，不做任何主动失效
    answer: B
    analysis: Cache-Aside 的标准做法。相比 A，它的不一致窗口更窄（A 的窗口包含「读库 + 写缓存」两次往返，且一旦发生旧值会长期留在缓存里）；相比 C，删除是幂等的，也不会为无人读取的数据做重建。

  - type: MULTI
    stem: 关于延迟双删，下列说法正确的有？
    options:
      A: 它针对的是「先删缓存再更新数据库」顺序下，并发读把旧值写回缓存的窗口
      B: 延迟时间难以确定，需大于一次「读库 + 写缓存」的耗时，因此落地有难度
      C: 如果一开始就用 Cache-Aside 顺序，通常不需要延迟双删
      D: 它能保证缓存与数据库的强一致
    answer: ABC
    analysis: D 错误。延迟双删只是缩小不一致窗口，仍然做不到强一致——两个独立存储之间没有分布式事务，并发交错在逻辑上无法完全避免。

  - type: JUDGE
    stem: 只要实现了「更新数据库后删除缓存」，就不会出现缓存与数据库不一致的情况。
    answer: F
    analysis: 仍有多个窗口：删除操作本身可能失败（需重试或 binlog 兜底）；Redis 主从延迟可能让读请求从从库读到旧值；一个业务操作影响的多个 key 可能只删了部分。因此必须设 TTL 作为最后防线，关键判断落库保证正确性。

  - type: CHOICE
    stem: 「缓存不设置过期时间」的最大风险是什么？
    options:
      A: 读取变慢
      B: 一旦删除失败，脏数据永久存在且无法自愈，同时无淘汰的 key 会持续占用内存
      C: 无法支持 Redis 集群
      D: 客户端无法序列化
    answer: B
    analysis: TTL 是缓存的最后一道防线——无论前面哪个环节出错，数据最多错 TTL 这么久。不设 TTL 时删除失败会导致脏数据永久存在，且缓存结构变更后旧数据无法自愈，同时内存持续增长。

  - type: JUDGE
    stem: 在高并发场景下，应当用缓存中的库存值判断是否有货再决定下单。
    answer: F
    analysis: 缓存中的值可能是旧的，用它做关键判断会导致超卖。正确做法是把判断落到数据库并用条件更新保证原子性，例如 UPDATE stock SET count = count - 1 WHERE goods_id = ? AND count > 0，受影响行数为 1 才表示扣减成功。缓存的职责是加速读，不承担正确性。
