## 电梯版回答

Redis 删过期键有两种路径。惰性删除是访问到这个键时才判断并删除，缺点是没被访问的过期键会一直占内存。定期删除默认每秒约 10 次（大约每 100 毫秒）随机抽查一批设置了过期时间的键，抽查有数量上限和 CPU 预算，所以不能保证及时清理。正因如此才需要内存淘汰策略兜底：默认策略是 noeviction，内存达到 maxmemory 后写命令直接返回 OOM 错误，缓存场景通常改成 allkeys-lru 或 allkeys-lfu。Redis 用的是近似 LRU，随机采样几个键加上对象里的 lru 时钟字段和淘汰池来挑淘汰对象，而不是维护一条全局链表，因为严格 LRU 的内存和维护开销都太大。Redis 4.0 又加了 LFU，用 8 位对数计数器加时间衰减，避免一次性的扫描访问把热点数据挤掉。淘汰发生在命令执行之前；从库不主动删过期键，而是等主库的 DEL 传播，读取时对逻辑已过期的键返回 nil 隐藏。maxmemory 不能设成等于机器内存，要给 fork 的写时复制和内存碎片留空间。

## 展开讲解

### 过期删除：惰性删除 + 定期删除

**惰性删除**：所有读写命令在查找 key 时，都会先经过 `expireIfNeeded` 判断。
如果已过期，主库上直接删除并返回"不存在"。

- 优点：只在访问时判断，不浪费 CPU，也不会为永远不会再被访问的键做无用功。
- 缺点：**如果这个键一直不被访问，它就永远占着内存**——
  逻辑上死了，物理上还活着。

**定期删除**：由 `serverCron` 周期性驱动 `activeExpireCycle`，
默认 `hz = 10`，即每秒约 10 次、大约每 100 毫秒一轮。每一轮：

```
① 从每个 db 的「设置了过期时间的键」字典里随机抽查一批键
   （源码里每轮抽查的键数由 ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP 控制，20 个）
② 删掉其中已过期的
③ 如果这一批里过期键的比例超过 25%，说明还有大量过期键，
   就继续再抽查一轮
④ 但整个周期有 CPU 时间预算（默认不超过 25% 的 CPU 时间），
   超预算必须退出，把时间让给正常请求
```

所以它叫"**随机+有上限的抽查**"，不是遍历。官方文档给的经验值是这个机制
默认大约每秒清理 200 个键——对正常的键数量足够，
但对于"同一秒内齐刷刷到期的几十万个键"，清理会滞后，
这段时间它们仍然占内存、仍然可能触发淘汰。

**过期相关的命令语义**：

```redis
TTL key        -- 返回剩余秒数
               -- 返回 -1 表示键存在但没有设置过期时间
               -- 返回 -2 表示键不存在
PERSIST key    -- 移除过期时间，把易失键变成永久键（返回 1 成功）

SET key value EX 60          -- 设置值并带过期
SET key value KEEPTTL        -- 保留原有过期时间（6.0+，默认 SET 会清掉 TTL）
GETEX key EX 60              -- 读取的同时设置/清除过期时间（6.2+）
EXPIRE key 60 NX             -- 只在没有 TTL 时设置（7.0+ 支持 NX/XX/GT/LT）
```

### 八种内存淘汰策略

`maxmemory` 默认是 0，表示**不限制**（在 64 位系统上）。
一旦设了非 0 值并达到上限，就按 `maxmemory-policy` 决定行为：

| 策略 | 淘汰范围 | 说明 |
|---|---|---|
| `noeviction`（默认） | 不淘汰 | 内存满时，会分配内存的写命令返回 OOM 错误，读命令仍可用 |
| `allkeys-lru` | 所有键 | 按最近最少使用淘汰，**缓存场景最常用** |
| `allkeys-lfu` | 所有键 | 按访问频率（LFU）淘汰，适合能区分热点的场景 |
| `allkeys-random` | 所有键 | 随机淘汰 |
| `volatile-lru` | 只限设置了 TTL 的键 | LRU，但只在易失键里挑；没有易失键时行为等同 noeviction |
| `volatile-lfu` | 只限设置了 TTL 的键 | LFU，同上 |
| `volatile-random` | 只限设置了 TTL 的键 | 随机，同上 |
| `volatile-ttl` | 只限设置了 TTL 的键 | 优先淘汰剩余存活时间最短的键 |

```conf
maxmemory 4gb
maxmemory-policy allkeys-lru
```

几个必须知道的点：

- **`volatile-*` 系列在"没有任何键设了 TTL"时无法淘汰任何东西**，
  行为退化成 noeviction，写命令开始报 OOM。
  这是线上"明明设了 volatile-lru 还是 OOM"的常见原因。
- **淘汰发生在命令执行之前**。Redis 处理一条命令时会先检查内存，
  需要腾空间就先淘汰，腾不出来再执行（或对写命令返回 OOM）。
  所以不会出现"命令执行完才因超限被拒绝"的情况。
- 不想让某些键被淘汰，就别给它们设 TTL 并用 `volatile-*` 策略；
  但用 `allkeys-*` 时所有键一视同仁。
- OOM 报错长这样：`OOM command not allowed when used memory > 'maxmemory'`。
  只读命令通常仍可执行，因为不分配额外内存（Redis 4.0 起区分命令是否
  可能分配内存）。

### 为什么是近似 LRU，不是严格 LRU

严格 LRU 需要维护一条「最近访问时间有序」的链表：每次访问都要把节点
移到表头，这有额外内存（每个键多一个链表指针）和每次操作的开销；
Redis 想让键对象尽量小、操作尽量快，所以选择**近似**：

```
每个键对象里有一个 24 位（LRU_BITS）的 lru 字段，记录最近一次访问的时间戳
淘汰时：
  ① 随机采样若干个键（maxmemory-samples，默认 5）
  ② 比较它们的 lru 字段，挑最久未使用的
  ③ 把候选放入一个固定大小的淘汰池（16 个槽位），
     池中按空闲时间排序，淘汰池里最久未用的
```

淘汰池的作用是**在多次采样之间复用信息**，让近似效果更接近真正 LRU。
`maxmemory-samples` 越大越接近严格 LRU，但 CPU 开销越高——
默认 5 是精度与开销的折中，官方认为在这个采样数下，
近似 LRU 的效果已经足够好。

```redis
OBJECT IDLETIME key     -- 查看键的空闲时间（秒），LRU 相关
INFO memory
-- used_memory / used_memory_rss / mem_fragmentation_ratio
-- maxmemory_policy / evicted_keys / expired_keys
```

### LFU：用频率而不是"最近一次"

LRU 的软肋是**扫描式访问**：一个只被访问一次、但恰好是"最近访问"的冷键，
会把真正的热点键挤掉（比如批量扫了一遍全表缓存）。LFU 按**访问频率**淘汰，
天然抗这种污染。

Redis 4.0 引入 LFU。它没有额外开字段，而是**复用了那 24 位的 lru 字段**：

```
16 位：上次衰减时间（精度是分钟）
 8 位：对数频率计数器（0~255）
```

- 计数器是**对数增长**的：计数越大，再想加一就越难（概率越小），
  所以 8 位能覆盖很大的访问量范围，不会轻易溢出。
- 还会**随时间衰减**，否则老热点会永久霸占内存：

```conf
maxmemory-policy allkeys-lfu
lfu-log-factor 10      -- 控制计数器增长的快慢（值越大越难增长）
lfu-decay-time 1       -- 每 1 分钟衰减一次
```

```redis
OBJECT FREQ key        -- 查看键的 LFU 访问频率计数
```

选择上的经验：**能明确区分冷热的缓存用 allkeys-lfu**；
访问模式比较平稳、想实现简单用 allkeys-lru；
两者都不关心、只求不 OOM 可以用 allkeys-random。

### 从库的过期行为

从库**不主动删除过期键**，它等主库来驱动：

```
主库上的键过期 → 主库删除并合成一条 DEL → 通过复制流发给从库 → 从库执行 DEL
```

这样做的原因是**一致性**：如果从库自行判断时钟删除，而主从时钟不一致，
主从数据就会分叉。因此从库上可能短暂存在"逻辑上已过期但物理还在"的键。
为了不把脏数据读出去，从库在**读取命令**上会用逻辑时钟判断，
对已过期的键返回"不存在"（nil），只是**不物理删除**——
所以 `DBSIZE` 之类的统计仍可能把它们算进去。

另一个要点：**从库默认忽略 `maxmemory`**（`replica-ignore-maxmemory` 默认 yes）。
也就是主库淘汰时发 DEL 给从库，从库自己不做淘汰决策，这样主从数据一致。
代价是从库可能用掉比 maxmemory 更多的内存，需要单独监控。

### maxmemory 该设多大

**不能设成等于机器内存**。至少要留出这些空间：

- **BGSAVE / AOF 重写时 fork 子进程的 COW 页复制**，写入频繁时接近翻倍
- **内存碎片**：`mem_fragmentation_ratio > 1` 是常态，
  分配器分出去的块比实际数据大
- **客户端输出缓冲、复制缓冲区、Lua 脚本临时内存、AOF 缓冲**

实践做法：先看 `INFO memory` 的 `used_memory_rss` 和
`mem_fragmentation_ratio`，结合实例实际负载估算余量，
把 `maxmemory` 设在留有余量的位置，并监控 `evicted_keys` 是否异常增长
（说明策略在频繁淘汰，可能需要扩内存或调策略）。
如果开了持久化，还要保证「maxmemory + COW 增量」不超过物理内存。

## 追问链

### Q1: 定期删除为什么不能保证过期键被及时清理？

因为它的设计目标从一开始就不是"精确清理"，而是**在有限 CPU 预算内
尽量清理**，本质是抽样式清理：

```
每一轮随机抽 20 个（可配常量）设了 TTL 的键，删掉已过期的
如果这批里过期比例超过 25%，说明过期键很多，再来一轮
但整个周期有 CPU 时间上限（默认不超过 25% 的 CPU），超预算就退出
```

随机采样意味着**概率性遗漏**：某个键即使早就过期，也可能连续很多轮
都没被抽到。而 CPU 预算意味着即使抽到了大量过期键，也不能无限清下去，
必须把时间还给正常请求（否则主线程被清理占满，服务就卡了）。

所以结论是：**定期删除只能保证"过期键最终会被清掉"，
不能保证"在过期那一刻就被清掉"**。没被清掉的这段时间里，
它们仍占内存，仍会被算进 `used_memory`，仍可能参与被淘汰。

#### Q1.1: 那这些"逻辑已过期但还没删"的键，算进内存吗？会触发淘汰吗？

会，而且这正是需要淘汰策略兜底的原因。

```
逻辑过期：TTL 到了，业务上不应该再返回它
物理删除：定期/惰性删除真正把它从内存里移除
两个时刻之间，这个键照样占着 dictEntry、key 对象、value 对象
```

后果有三个：

- **算进 `used_memory`**：`maxmemory` 判断的是物理内存占用，
  不区分"是否逻辑过期"。所以一大批集中到期的键会让内存统计居高不下。
- **可能触发淘汰**：如果同时有很多过期键堵着，正常键的内存空间被挤压，
  会触发 LRU/LFU 淘汰，把**本来不该淘汰的有效数据**踢掉。
- **可能触发 OOM**：noeviction 下写命令直接报错，即使"数据其实都过期了"。

这也解释了为什么说「过期清理 + 内存淘汰」是两个独立机制：
**过期不保证及时，淘汰是最后一道闸门**。

##### Q1.1.1: 为什么不干脆在内存满时把过期字典整个扫一遍删干净？

因为那是一次 **O(N) 的阻塞操作**，会直接违反 Redis 的延迟承诺。

Redis 的 `expires` 字典可能存着几百万个键，全量扫描需要遍历并逐个判断，
这段时间**主线程什么都干不了**，所有客户端请求被卡住——
可能出现几百毫秒甚至数秒的停顿，比"多占一点内存"严重得多。
分布式缓存的核心价值就是低延迟，宁可多占内存，也不能卡主线程。

设计上体现的取舍是"**用内存换 CPU 与延迟**"：

- 抽样清理把开销摊平到每一轮 cron 里，单轮开销可控
- CPU 预算硬性限制清理不能挤占正常请求
- 淘汰策略负责最后的兜底，保证内存不会无限增长

配套的调优手段：

- `hz` 调大能让定期删除更频繁（默认 10），代价是 cron 更频繁、
  CPU 开销上升；Redis 还支持 `dynamic-hz`，负载低时自动降低频率省 CPU。
- 对"大批键同时过期"的场景，正确做法是在**业务层**给 TTL
  加随机抖动（比如 30 分钟 ± 5 分钟），避免同一秒集中到期——
  这也是缓存雪崩的经典防线。

### Q2: 近似 LRU 具体近似到什么程度？采样数越大越好吗？

近似 LRU 与严格 LRU 的差距主要看 `maxmemory-samples`。
机制是"**随机采样 + 挑最旧 + 淘汰池累积信息**"：

```
sample 5 个随机键 → 比较 lru 字段 → 最旧的进淘汰池（16 槽，按空闲时间排序）
下一次淘汰继续往池里放，池满则替换掉更"新"的
要淘汰时从池里选最久未使用的那个
```

淘汰池的价值是**把多次采样的结果累积起来**，避免每次只看 5 个键的
信息量太少。官方给的经验是：采样数 5 时近似 LRU 已经很接近真实 LRU，
采样数 10 时几乎与严格 LRU 相当，再往上收益递减而 CPU 开销递增。

所以不是越大越好：

- 采样越多，每条淘汰决策的 CPU 开销越高（淘汰可能很频繁）
- 收益在 5~10 附近就基本吃完了

更值得注意的是 LRU 的**适用性**问题：近似只是"最近访问时间"的估计，
它无法区分"访问一次"和"访问一万次"。业务上存在扫描、遍历、
批量回源这类一次性访问时，LRU 会把热点挤掉——这种场景该换 LFU。

#### Q2.1: LFU 是怎么解决 LRU 被一次性访问冲掉热点的问题的？

LRU 只看"最近一次访问时间"，一次偶发访问就能把一个冷键变成"最新"。
LFU 改成看"访问频率"，偶发的一次访问对频率贡献很小。

Redis 的实现巧妙在没有增加字段：`lru` 字段共 24 位，
LFU 模式下拆成 **16 位衰减时间 + 8 位频率计数器**。

关键设计是**对数计数器**：

```
计数器值较小时，加一的概率高（涨得快）
计数器值较大时，加一的概率低（很难再涨）
上限 255，不会溢出
```

这样 8 位就能表达从个位数到极高访问量的很大范围，
既省空间又能区分"访问 10 次"和"访问 10 万次"。

另一半是**衰减**：只增不减的话，一个曾经的爆款键会永久占着内存。
所以每隔 `lfu-decay-time`（默认 1 分钟）就按 `lfu-log-factor`
（默认 10）的规则把计数器减一点。这样 LFU 实际衡量的是
"**近期**的访问频率"，既抗一次性访问污染，又不会让历史热点永不退休。

```redis
OBJECT FREQ key     -- 查看某个键当前的对数频率计数
```

注意用 LFU 必须把策略设成 `allkeys-lfu` 或 `volatile-lfu`，
否则 `OBJECT FREQ` 看到的是别的含义（LRU 模式下没有频率计数的语义）。

##### Q2.1.1: 8 位的计数器怎么区分「访问 100 次」和「访问 10 万次」？

靠**概率性递增**把线性增长变成对数增长。

`lfu-log-factor` 控制的是递增难度曲线：

```
counter 很小（比如 0~10）  ：几乎每次访问都 +1，涨得很快
counter 中等              ：部分访问才 +1
counter 接近 255          ：只有极小概率才 +1，基本饱和
```

这种映射带来的效果是：**低访问量区间分辨率高，高访问量区间分辨率低**。
实践中并不需要精确区分"10 万次还是 11 万次"，只需要把"几百次"和"几万次"
分在不同档位即可。8 位空间刚好够表达这种粗粒度频率，
而且递增是**概率性的**，不需要每次访问都做一次写操作（对性能更友好）。

`lfu-log-factor` 的值越大，计数器越难增长（同样访问次数下计数更小）；
它和 `lfu-decay-time` 一起决定 LFU 对"频率"和"新近程度"的权衡：

```
lfu-log-factor 越大 → 越难涨 → 更看重长期积累的访问量
lfu-decay-time 越大 → 衰减越慢 → 老热点保留更久
```

调这两个参数要结合业务访问分布，不是越大越好。默认值
（log-factor 10、decay-time 1 分钟）适合大多数场景。

### Q3: maxmemory 设成机器内存的 80% 可以吗？有没有更靠谱的算法？

"80%"只是个流传的经验值，不能机械套用，核心约束是这几笔账：

```
maxmemory
+ fork 期间 COW 可能复制的内存（取决于 fork 后父进程写入量，最坏接近一份数据）
+ 内存碎片（mem_fragmentation_ratio - 1 这部分）
+ 客户端输出缓冲 / 复制缓冲区 / AOF 缓冲 / Lua 临时内存
+ Redis 自身运行时开销
≤ 物理内存
```

如果只开 RDB 且写入平稳，余量可以小一些；如果同时开 AOF 重写、
又处在写入高峰期，COW 的增量会明显更大。稳妥的做法是：

```
① 先看 INFO memory：
   used_memory（数据集与开销的逻辑总量）
   used_memory_rss（操作系统实际给进程的内存，含碎片）
   mem_fragmentation_ratio（rss / used_memory）
② 观察 rdb_last_cow_size / aof_last_cow_size 估算 fork 峰值
③ 给 COW 和碎片留出余量后，再定 maxmemory
④ 上线后监控 evicted_keys 与 maxmemory 距离，动态调整
```

一个常被忽略的点：**`maxmemory` 只管数据与相关开销，
管不住 fork 出来的子进程**。子进程共享父进程的页，但父进程写时复制出的新页
算在父进程头上。所以"maxmemory 没超，机器却 OOM"通常就是 COW 造成的。

#### Q3.1: 从库的 maxmemory 该怎么设？从库的过期行为和主库一样吗？

不一样，有两处关键差异。

**差异一：从库不主动删过期键。** 从前面的展开可以看到，从库等主库的 DEL。
所以在同一份数据下，**从库的内存占用可能比主库高**（那些逻辑过期
但还没收到 DEL 的键还占着）。这属于设计取舍，不是 bug。

**差异二：从库默认忽略 maxmemory。** 配置项 `replica-ignore-maxmemory`
默认是 yes，意思是即使从库超过 maxmemory 也不自己淘汰，
一切以主库的 DEL 为准，避免主从数据分叉。

由此得到的运维建议是：

- 从库**不要**把 maxmemory 设得比主库小，否则真到内存紧张时
  它既不淘汰（默认）又可能 OOM，反而更脆弱
- 从库要预留出比主库**更多**的内存余量（逻辑过期键的堆积 + 从库的
  复制缓冲/客户端缓冲通常更大）
- 监控从库的 `used_memory_rss`，它才是真正会触发 OOM Killer 的指标
- 如果确实要让从库自己淘汰（`replica-ignore-maxmemory no`），
  必须确保发生在从库上的写入都是幂等的，并接受数据可能不一致的风险——
  官方明确建议"要清楚自己在做什么"

##### Q3.1.1: 那从库上读到已经过期的键，会返回旧数据吗？

不会，但从库上也读不到那条 DEL 之后的删除效果之前的状态。

Redis 的处理是分层的：

```
① 物理上：从库收到主库合成的 DEL 之前，键还在内存里
② 读取时：从库用逻辑时钟判断，对已过期的键返回"不存在"（nil）
   ——即"逻辑上隐藏"，避免把过期数据读出去
③ 写入/统计时：它仍在 keyspace 里，会影响 DBSIZE 之类的计数
```

官方文档把这套机制描述为「从库用逻辑时钟，对不违反数据集一致性的
**只读操作**报告键不存在」。这样做的目的是保证：

- 客户端经从库读到的，不会是已经超过 TTL 的数据
- 主从之间不会因为各自时钟不同而产生分叉

需要注意的边界：**写入操作不能依赖这个逻辑过期判断**。
如果从库可写（`replica-read-only no`，不推荐），对逻辑过期键做 INCR
之类的操作会与主库行为不一致。这也是官方强烈建议从库保持只读的原因之一。

一旦从库被提升为主库，它就会**立刻开始独立过期和淘汰**，
不再依赖旧主库的 DEL——所以故障切换后，那些堆积的逻辑过期键
会在提升后的实例上被正常清理。

## 常见坑

- **说「键一到过期时间就被立刻删除」** ——
  实际是惰性删除 + 定期随机抽查，没被抽到、又没被访问的键会继续占内存
- **说「定期删除会遍历所有过期键」** ——
  它是**随机抽查**且每轮有数量上限和 CPU 预算，所以只是"最终会清"，
  不是"准点清"
- **说「过期键没删掉就不占内存/不算 maxmemory」** ——
  逻辑过期和物理删除是两回事，未删除的过期键照样计入 `used_memory`，
  还可能把正常键挤到被淘汰
- **说「Redis 用严格 LRU」** ——
  是**近似 LRU**：随机采样 + 24 位 lru 时钟字段 + 淘汰池，
  严格 LRU 的链表内存与维护开销太大
- **说「maxmemory-samples 越大越好」** ——
  采样越多越接近严格 LRU，但每条淘汰决策的 CPU 开销越高，
  收益在 5~10 附近基本到顶
- **说「LFU 也是概率式的所以不准，不如 LRU」** ——
  LFU 的概率性递增正是为了用 8 位表达大范围频率，
  它要解决的是 LRU 被一次性扫描访问冲掉热点的问题，用途不同
- **说「默认 maxmemory-policy 是 allkeys-lru」** ——
  默认是 **noeviction**，内存满时写命令直接报 OOM；
  allkeys-lru 是缓存场景**需要手动配置**的常用选择
- **说「设了 volatile-lru 就不会 OOM」** ——
  volatile 系列只淘汰**设了 TTL 的键**，没有易失键时淘汰不了任何东西，
  行为退化成 noeviction 照样 OOM
- **说「淘汰是在内存超限后才在后台慢慢做的」** ——
  淘汰发生在**命令执行之前**，先腾空间再执行命令；
  腾不出来则写命令返回 OOM 错误
- **说「从库会自己删除过期键」** ——
  从库等主库的 DEL 传播；它只在读取时对逻辑过期键返回 nil，
  不物理删除。从库还默认忽略 maxmemory，不会自行淘汰
- **说「maxmemory 设成机器内存的 80% 是标准答案」** ——
  余量取决于是否开持久化、写入强度、碎片率、缓冲区大小，
  要结合 `INFO memory` 与 `rdb_last_cow_size` 估算，没有万能百分比

## 加分点

- 能说出定期删除的**抽查比例与 CPU 预算**（过期比例超过 25% 就再来一轮，
  但整个周期 CPU 时间有上限），说明"为什么清理必然是滞后的"——
  这比背"定期删除"四个字有说服力得多
- 能解释**逻辑过期 vs 物理删除**的区分，并推出三个后果
  （占内存、参与淘汰、可能 OOM），这是理解"为什么需要淘汰策略"的关键
- 知道近似 LRU 的**三个部件**：随机采样、24 位 `lru` 时钟字段、
  16 槽淘汰池，并能说明淘汰池的作用是"在多次采样之间复用信息"
- 能讲清 **LFU 复用 24 位 lru 字段**（16 位衰减时间 + 8 位对数计数），
  以及"对数递增 + 时间衰减"分别解决"8 位表达大范围"和"老热点不退休"
- 提到读取逻辑过期键时**从库返回 nil 但保留在 keyspace**，
  并能解释这是为了主从一致性而不是 bug
- 知道 **`volatile-*` 在没有易失键时退化为 noeviction** 这个隐藏陷阱，
  能直接指出它是线上"配了淘汰策略还 OOM"的常见原因
- 能说明 **`SET` 默认会清掉 TTL**，需要保留要用 `KEEPTTL`（6.0+）——
  这是实际写代码时容易埋的坑
- 提到 **TTL 加随机抖动** 是防止大批键同时过期的正确做法，
  把它和缓存雪崩防线串起来
- 知道 **`maxmemory` 管不住 fork 出的 COW 内存**，
  能解释"maxmemory 没超但机器 OOM"这类线上现象
- 能给出 `INFO memory` 的**具体观测字段**：
  `used_memory`、`used_memory_rss`、`mem_fragmentation_ratio`、
  `evicted_keys`、`expired_keys`，而不是笼统说"看监控"

## 版本差异

| 版本 | 差异 |
|---|---|
| Redis 4.0 | 引入 **LFU 淘汰策略**（`allkeys-lfu` / `volatile-lfu`）与 `OBJECT FREQ`；引入 lazyfree 系列配置，过期键可异步释放 |
| Redis 6.0 | `SET` 新增 `KEEPTTL` 选项，可保留原有过期时间（默认 `SET` 会清除 TTL） |
| Redis 6.2 | 引入 `GETEX`，读取键的同时设置或清除过期时间 |
| Redis 7.0 | `EXPIRE` / `PEXPIRE` / `EXPIREAT` / `PEXPIREAT` 支持 `NX` / `XX` / `GT` / `LT` 条件选项 |

````yaml
questions:
  - type: CHOICE
    stem: Redis 的 maxmemory-policy 默认值是什么？
    options:

    answer: B
    analysis: 默认策略是 noeviction，即不淘汰任何键。内存达到 maxmemory 后，需要分配内存的写命令会返回 OOM 错误。allkeys-lru 是缓存场景常用的策略，但需要手动配置。

  - type: JUDGE
    stem: 给一个键设置了 TTL 之后，Redis 一定会在到期的瞬间把它从内存中删除。
    answer: F
    analysis: Redis 使用惰性删除加定期随机抽查。定期删除每轮只随机抽查一批键且有 CPU 预算上限，没被访问也没被抽到的过期键会继续占用内存，直到被再次访问或被抽查到才物理删除。

  - type: MULTI
    stem: 关于 Redis 的内存淘汰，下列说法正确的有？

    answer: ABC
````
