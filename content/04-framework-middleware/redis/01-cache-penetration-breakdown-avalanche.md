## 电梯版回答

三者都表现为请求打到数据库，但触发条件完全不同。穿透是查一个数据库里根本不存在的数据，缓存永远不命中，每次请求都穿到数据库，解决方案是缓存空值加短过期时间、或者用布隆过滤器提前拦掉。击穿是某一个热点 key 过期的那一瞬间，大量并发请求同时打向数据库，解决方案是加互斥锁只让一个请求去重建，或者用逻辑过期让请求先拿旧数据、后台异步重建。雪崩是大量 key 在同一时刻集中过期或者 Redis 整体宕机，解决方案是给过期时间加随机抖动、做多级缓存、以及熔断降级。

## 展开讲解

### 三者的区别

| | 触发条件 | 影响范围 | 数据是否存在 |
|---|---|---|---|
| 穿透 | 查询不存在的数据 | 每次都打库，持续性好 | **不存在** |
| 击穿 | 单个热点 key 过期瞬间 | 短时高并发打库 | 存在 |
| 雪崩 | 大批 key 同时过期 / Redis 宕机 | 数据库整体过载 | 存在 |

一句话记忆：**穿透是数据没有，击穿是一个 key，雪崩是一批 key**。

### 穿透：查不存在的数据

典型场景是恶意攻击，或者业务上的脏 ID：

```
请求 user_id = -1（不存在）
→ 查 Redis 未命中
→ 查 MySQL 也未命中
→ 没有回写缓存
→ 下一个同样的请求再走一遍
```

因为「查询结果为空」这件事没有被缓存，所以缓存层等于不存在，
所有流量都直接打到数据库。

**方案一：缓存空值**

查不到也写入缓存，但 TTL 要短：

```
SET user:-1 "" EX 60
```

短 TTL 的理由：如果后来这个 ID 真的被创建了，最多 60 秒后就能查到，
不会长期返回错误结果。TTL 太长会导致「数据明明存在却一直查不到」
这种更难排查的问题。

**方案二：布隆过滤器**

在缓存之前加一层布隆过滤器，把所有存在的 key 预先放进去。
查询时先问过滤器：「这个 key 存在吗？」

- 过滤器说**不存在** → 直接返回，不查缓存也不查库（**一定准确**）
- 过滤器说**存在** → 继续走正常查询流程（**可能误判**）

布隆过滤器的关键特性是**只有假阳性、没有假阴性**：
它说不存在就一定不存在，它说存在有可能其实不存在。
所以它只适合用来「挡住肯定查不到的请求」，不能作为判断存在的依据。

代价：
- 有误判率（由位数组长度和哈希函数个数决定）
- **不支持删除**。要用得用计数布隆过滤器（Counting Bloom Filter）或
  Redis 的 `BF.DEL`（RedisBloom 模块），代价是内存成倍增长
- 数据更新时要同步维护过滤器，一致性变复杂

**方案三：参数校验**

最便宜也最有效的一层。`user_id = -1` 这种请求在入口就拦掉：

```java
if (userId == null || userId <= 0) {
    throw new IllegalArgumentException("非法的 userId");
}
```

很多线上穿透问题其实是最外层没做基础校验。

### 击穿：热点 key 过期

```
某个秒杀商品的缓存 TTL 到了
→ 恰好有 10 万个请求同时到达
→ 全部未命中，全部去查 MySQL
→ 数据库连接被打满
```

注意是**单个 key**，而且往往是流量最集中的那个。

**方案一：互斥锁重建**

只让一个请求去查库重建缓存，其余请求短暂等待后重试：
这是本项目 `ContentCache` 的做法。核心逻辑：

```java
// 缓存未命中，抢锁
String lockToken = redisLock.tryLock(redisKey + ":lock", Duration.ofSeconds(10));
if (lockToken == null) {
    // 没抢到，说明别人正在重建，短暂重试读缓存
    String retried = retryRead(redisKey);
    if (retried != null) {
        return deserialize(retried);
    }
    // 等不到就直接回源：可用性优先于保护数据库
    return loader.get();
}
try {
    // 双重检查，可能已被上一个持有者写入
    // ... 回源、写缓存
} finally {
    redisLock.unlock(redisKey + ":lock", lockToken);
}
```

两个细节值得强调：
- **抢锁后要双重检查**。等锁期间前一个持有者可能已经把缓存写好了，
  不检查就白查一次库。
- **等待超时要兜底回源**。否则缓存重建失败时所有请求都失败，
  把「保护数据库」做成了「不可用」。可用性应该优先。

**方案二：逻辑过期**

缓存**不设物理 TTL**（或设得很长），在 value 里存一个逻辑过期时间：

```json
{ "data": {...}, "expireAt": "2026-09-10T20:00:00" }
```

读到数据后判断 `expireAt`：

- 未过期 → 直接返回
- 已过期 → **直接返回旧数据**，同时开一个异步线程去重建缓存

这样请求永远不会阻塞在缓存重建上。代价是**会返回一段时间的旧数据**，
适合「能接受短暂不一致、但绝对不能卡」的场景，比如商品详情页。

两个方案的取舍：

| | 互斥锁 | 逻辑过期 |
|---|---|---|
| 一致性 | 强（重建期间请求等待） | 弱（返回旧数据） |
| 可用性 | 依赖锁，可能等待 | 高，不阻塞 |
| 实现复杂度 | 低 | 高（需要异步线程池、额外字段） |
| 适用 | 数据准确性要求高 | 极致可用性要求 |

### 雪崩：大批 key 同时过期

最常见的人为成因是**批量预热时给所有 key 设了相同的 TTL**：

```java
// 反例：所有 key 同一时刻过期
for (Product p : products) {
    redis.set("product:" + p.getId(), json, 3600);
}
```

一小时后这些 key 同时失效，数据库瞬间承受全部流量。

**方案一：TTL 加随机抖动**

```java
// 本项目 ContentCache#jitter 的做法：在基础 TTL 上叠加最多 10% 的随机值
private Duration jitter(Duration ttl) {
    long base = ttl.toMillis();
    long offset = ThreadLocalRandom.current().nextLong(base / 10 + 1);
    return Duration.ofMillis(base + offset);
}
```

这样过期时间被打散在一个区间内，不会形成「同一秒集体失效」。

**方案二：多级缓存**

本地缓存（Caffeine）+ Redis。本地缓存挡住大部分热点读，
即使 Redis 挂了也不至于全部穿到数据库。代价是
**本地缓存的一致性问题**（多实例间不同步），
通常用短 TTL 或广播失效消息来缓解。

**方案三：熔断降级**

前面几条都是「尽量不发生」，熔断是「发生了也别把数据库打死」。
用 Sentinel / Hystrix 对数据库访问做限流和熔断，
超限直接返回兜底数据（默认值、静态页、友好提示），
而不是让请求堆积把数据库拖死。

**方案四：Redis 高可用**

雪崩也可能因为 Redis 整体宕机。这个要靠架构解决：
主从 + 哨兵、Redis Cluster、以及前面说的本地缓存作为兜底。

### 缓存更新的顺序：先删缓存还是先更新数据库

这是紧跟着三大问题的高频追问。

**为什么是「删缓存」而不是「更新缓存」**：
更新缓存看起来更直观，但有两个问题——一是如果缓存值需要复杂计算，
每次更新都算一遍很浪费（可能没人读）；二是并发更新时两个线程
可能以相反的顺序写缓存，留下脏数据。删除是幂等的，安全得多。

**为什么是「先更新数据库，再删缓存」**：
反过来（先删缓存再更新数据库）有个更危险的窗口：

```
① 线程 A 删缓存
② 线程 B 查缓存未命中，读数据库得到旧值，写入缓存
③ 线程 A 更新数据库为新值
→ 缓存里是旧值，且长期存在（除非过期）
```

先更新数据库再删缓存的话，不一致窗口理论上是「读取发生在
DB 更新前、缓存删除在 DB 更新后」这种极窄的交错，
概率低得多。所以业界普遍采用 **Cache-Aside：先更新 DB，再删缓存**。

**删除失败怎么办**：这是必须回答的追问。两个办法：

1. **消息队列重试**：删除失败就把 key 发到 MQ，由消费者重试，
   直到成功。要注意幂等和重试上限。
2. **订阅 binlog**：用 Canal 订阅 MySQL binlog，监听到变更后
   异步删缓存。这样即使应用侧删除失败，binlog 这条路径也能补上。

**「延迟双删」解决的是什么**：在「先删缓存再更新 DB」的顺序下，
为了处理上面那个窗口，在更新 DB 之后再延迟一段时间（比如 500ms）
删一次缓存。它针对的就是「步骤 ② 写入的旧值」。
但延迟时间难以确定（要大于一次读操作的耗时），
所以更推荐直接用 Cache-Aside 顺序 + 删除失败重试。

## 追问链

### Q1: 缓存穿透为什么不能靠「把空值缓存设得很长」来解决？

因为一旦这个 key 对应的数据后来真的被创建了，缓存里那个空值会长期
返回「不存在」。表现是「明明插入成功了，查询还是查不到」，
而且排查起来很绕——数据在库里好好的，前端就是查不到。

所以空值缓存的 TTL 必须短（几十秒级别），它的定位是
**挡住短时间内的重复攻击流量**，而不是长期表示「这个 key 不存在」。
真正需要长期判断存在性，要用布隆过滤器。

另外空值缓存还有个副作用：如果攻击者用大量随机 ID 来打，
每个都缓存一个空值，会占用可观的 Redis 内存。这时候应该
**限制空值缓存的总量或对随机 ID 做参数校验**，必要时直接上布隆过滤器。

#### Q1.1: 布隆过滤器的误判方向为什么是「说存在可能不存在」？

因为它的实现是位数组 + 多个哈希函数：

```
添加 key：
  用 k 个哈希函数算出 k 个位置，全部置 1

判断 key：
  用同样的 k 个哈希函数算位置
  只要有一个位置是 0 → key 一定不在集合里（一定准确）
  全部位置都是 1    → key「可能存在」（可能误判）
```

「全部是 1」不代表这个 key 被添加过——**可能是其他若干个 key
恰好把这些位置都置成了 1**。随着元素增多，位数组被填满的比例上升，
误判率随之升高。

由此推出它的适用边界：**只适合挡「肯定不存在」的请求，
不能用来判断「一定存在」**。所以它只能放在缓存之前做前置过滤，
不能替代缓存或数据库的存在性判断。

##### Q1.1.1: 布隆过滤器还有哪些工程上的限制？

1. **不支持删除**。把某一位清 0 会影响其他共享这一位的 key，
   产生假阴性——而假阴性是它原本不会犯的错，性质更严重。
   要支持删除得用计数布隆过滤器，每位用计数器代替 0/1，
   内存开销是原来的数倍。
2. **容量需要预估**。位数组长度 m 和哈希个数 k 要按预期元素数 n
   和可接受误判率 p 算出来：

   ```
   m = -n * ln(p) / (ln2)^2
   k = (m / n) * ln2
   ```

   元素数远超预估时，误判率会急剧恶化。所以要么留足余量，
   要么用可扩容的变体（分层布隆过滤器）。
3. **数据同步问题**。数据库和缓存都好说，过滤器要额外维护。
   常见做法是启动时全量构建 + 后续增量添加，或者用 Redis 的
   RedisBloom 模块让多个实例共享一份。
4. **不适用元素少的场景**。元素很少时，直接在业务层用 `Set`
   查一下更简单准确，没必要引入布隆过滤器。

### Q2: 分布式锁重建缓存时，锁该加在哪一层？

有个很容易踩的坑：**不要在拿到锁之后才去读缓存**，
也不要把锁的粒度和业务锁搞混。

正确的结构是「读缓存 → 未命中 → 抢锁 → 双重检查 → 回源 → 写缓存 → 释放」：

```java
// ① 先读缓存，命中直接返回，不碰锁
String cached = redis.get(key);
if (cached != null) return deserialize(cached);

// ② 未命中才抢锁
String token = lock.tryLock(key + ":lock", ttl);
if (token == null) {
    // ③ 抢不到说明别人在重建，短暂重试即可
    return retryOrFallback();
}
try {
    // ④ 双重检查：等锁期间可能已被写入
    String rechecked = redis.get(key);
    if (rechecked != null) return deserialize(rechecked);
    // ⑤ 回源 + 写缓存
} finally {
    lock.unlock(key + ":lock", token);
}
```

第 ④ 步不能省。否则在「抢锁成功但前一个持有者刚写完缓存」的时序下，
会白白再查一次数据库——在高 QPS 下这个浪费很可观。

还有一个细节：**锁的 TTL 要大于回源耗时**。否则会出现
「A 还在查库，锁已过期，B 拿到锁也开始查库」，锁形同虚设。
如果回源耗时不可控，就需要看门狗续期（Redisson 的 `lockWatchdogTimeout`
就是做这件事的）。

#### Q2.1: 那如果缓存重建一直失败呢？

必须有兜底，否则「保护数据库」会变成「服务整体不可用」。
三层兜底：

1. **等待超时后直接回源**。重试几次还读不到缓存就自己查库，
   宁可给数据库加点压力也不让请求失败。本项目的实现是
   `RETRY_TIMES = 3`、每次间隔 50ms，超时后 `return loader.get()`。
2. **回源也要有超时和限流**。如果回源本身慢或挂，
   要有独立的超时控制，避免线程被拖住。
3. **最外层降级**。返回兜底数据（默认值、静态内容），
   并打点告警。

这里有个设计原则值得说出来：**缓存的核心目标是降低数据库压力，
而不是让每个请求都必须走缓存**。可用性大于缓存命中率。
把「缓存未命中」当成异常来处理，往往会把缓存故障放大成服务故障。

## 常见坑

- **把击穿和雪崩说混** —— 击穿是单个热点 key，雪崩是批量 key 或
  Redis 宕机。说混了后面所有方案都会串
- **说「给所有缓存设置相同的 TTL」是正常做法** —— 这正是雪崩的
  人为成因，必须加随机抖动
- **说「先删缓存再更新数据库」是推荐顺序** —— 这个顺序在不一致窗口上
  比 Cache-Aside 更危险
- **说「布隆过滤器能 100% 解决穿透」** —— 有误判率，
  且不支持删除
- **空值缓存设很长的 TTL** —— 会导致数据后来真的创建了却查不到
- **只回答「加锁」而不提双重检查和等待超时兜底** —— 少了这两点，
  实现是错的
- **认为缓存未命中是异常** —— 未命中是正常状态，
  应该保证回源路径始终可用
- **说「更新缓存」比「删除缓存」更好** —— 更新缓存会放大写开销，
  且并发下容易留脏数据

## 加分点

- 能结合自己的项目说：「我这边的实现是空值哨兵挡穿透、
  Redis 锁串行化重建防击穿、TTL 加 ±10% 抖动防雪崩」——
  比只背方案名更有说服力
- 知道**逻辑过期和互斥锁的本质取舍是「一致性 vs 可用性」**，
  并能按业务场景选：商品详情页可以返回旧数据，账户余额不行
- 提到**缓存失效用版本号而不是遍历删除**：
  `jis:cache:v{n}:...` 每次内容变更只做一次 `INCR`，
  旧 key 交给 TTL 自然淘汰。避免 `KEYS`/`SCAN` 全库扫描
  （`KEYS` 在大实例上会阻塞 Redis，是经典线上事故）
- 提到**布隆过滤器在 Redis 里的落地**是 RedisBloom 模块
  （`BF.ADD` / `BF.EXISTS`），而不是自己用 `SETBIT` 拼
- 知道 `KEYS` 的替代品是 `SCAN`，但 `SCAN` 也有代价：
  游标遍历期间的数据变更不保证可见，且一次全量遍历仍是 O(N)。
  更好的做法是从设计上避免「需要按模式删除」这种需求
- 能把三大问题上升为**缓存治理体系**：监控命中率、
  大 key/热 key 探测、容量规划、以及缓存故障时的降级演练

## 版本差异

| 版本 | 差异 |
|---|---|
| Redis 4.0 | 引入 `UNLINK`（异步删除大 key，避免 `DEL` 阻塞主线程）与 `FLUSHALL ASYNC` |
| Redis 4.0 | 引入 RedisBloom 模块（`BF.ADD` / `BF.EXISTS`），布隆过滤器可以不必自己实现 |
| Redis 6.0 | 引入多线程 IO（只用于网络读写，命令执行仍是单线程）；客户端缓存（Tracking）可用于本地缓存失效通知 |
| Redis 7.0 | Function（替代部分 Lua 脚本场景）；`SHUTDOWN` 与持久化流程优化；多线程 IO 默认更积极 |
| Redisson 3.x | `tryLock` 支持看门狗自动续期（默认 30 秒租期，每 10 秒续一次），避免业务超时导致锁提前释放 |

    stem: 布隆过滤器判断某元素不存在时，该元素一定不存在。
    answer: T
    analysis: 布隆过滤器只有假阳性没有假阴性。某个位置是 0 说明没有任何元素把它置为 1，因此一定不在集合里；全部位置为 1 则只能说「可能存在」，因为这些位可能是其他元素共同置上的。

  - type: JUDGE
    stem: 缓存空值时应该设置较长的 TTL，这样能更长久地挡住穿透攻击。
    answer: F
    analysis: 空值缓存的 TTL 必须短（几十秒级别）。设长了会导致该数据后来真的被创建时，缓存仍长期返回「不存在」，出现「插入成功却查不到」的难排查问题。空值缓存的定位是挡住短时间内的重复流量，长期存在性判断应交由布隆过滤器。

  - type: CHOICE
    stem: 关于「先更新数据库再删除缓存」相比「先删除缓存再更新数据库」的优势，下列说法正确的是？
    options:
      A: 前者能保证强一致性，后者不能
      B: 后者的不一致窗口更大：删缓存后、更新DB前有并发读会把旧值写回缓存
      C: 前者的不一致窗口为零，所以被广泛采用
      D: 两者效果完全等价，选择哪个都行
    answer: B
    analysis: 先删缓存再更新 DB 时，若在删缓存后、更新 DB 前有并发读请求读到旧值并写回缓存，缓存里会长期保留旧值。Cache-Aside（先更新 DB 再删缓存）的不一致窗口窄得多。但要注意它也只是最终一致，A 和 C 都错在「保证强一致」上。
