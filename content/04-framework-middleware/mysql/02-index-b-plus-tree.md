## 电梯版回答

B+ 树适合做索引有三个原因：它是矮胖的多叉树，三层就能存两千多万行数据，一次查询只需两三次磁盘 IO；非叶子节点只存键不存数据，所以单页能放更多键，树更矮；叶子节点用双向链表串起来，范围查询和排序可以直接顺着链表扫，不用回到根节点重新查找。InnoDB 的主键索引是聚簇索引，叶子节点直接存整行数据，所以必须有主键且主键不宜过长。二级索引的叶子节点存的是主键值，通过二级索引查非索引列需要拿着主键回聚簇索引再查一次，这叫回表；如果查询的列都在索引里就不需要回表，这叫覆盖索引。联合索引遵循最左前缀原则，索引下推能把 where 条件的判断下推到存储引擎层减少回表次数。

## 展开讲解

### 为什么是 B+ 树而不是其他结构

| 结构 | 为什么不适合 |
|---|---|
| 哈希表 | 只支持等值查询，**不支持范围查询和排序**。而 `WHERE age > 20`、`ORDER BY`、`BETWEEN` 恰恰是 SQL 的常见需求 |
| 有序数组 | 等值和范围查询都很快，但**插入删除要移动元素**，O(n) 的写入代价不可接受 |
| 二叉搜索树 | 会退化成链表；即使平衡（AVL/红黑树），树太高——**每个节点只存一个键**，100 万行要 20 层，就是 20 次磁盘 IO |
| **B 树** | 每个节点既存键又存数据，**单页能放的键变少，树更高**；且范围查询需要中序遍历、跨层跳转 |
| **B+ 树** | ✔ 非叶子只存键（单页放更多，树更矮）；✔ 叶子连成链表（范围查询顺序扫）；✔ 所有查询都走到叶子（性能稳定） |

### B+ 树的三个优势

**优势一：矮胖，磁盘 IO 少**

InnoDB 一页 16KB。假设主键是 `BIGINT`（8 字节），
加上页内指针约 6 字节，一个非叶子节点能放：

```
16KB / (8 + 6) ≈ 1170 个键
```

那么：

```
第 1 层（根）  ：1 个节点，1170 个指针
第 2 层        ：1170 个节点，1170 × 1170 ≈ 137 万个指针
第 3 层（叶子） ：1170² ≈ 137 万个叶子页

假设每行 1KB，一个叶子页放 16 行
总行数 ≈ 137 万 × 16 ≈ **2190 万行**
```

**三层 B+ 树能存两千多万行，查任意一行最多三次磁盘 IO**
（而且根节点常驻内存，实际常常只需 1~2 次）。
这比二叉树的 20 多次 IO 好两个数量级。

**优势二：叶子节点双向链表支持范围查询**

```sql
SELECT * FROM user WHERE age BETWEEN 20 AND 30;
```

在 B+ 树里：定位到 `age = 20` 的叶子节点，
然后**顺着叶子链表向右扫描**直到 `age > 30`。
不需要回到根节点，也不需要在层间跳转。

B 树就做不到——它的数据分散在所有层，
范围扫描需要中序遍历整棵树，IO 模式是随机跳转。

**优势三：查询性能稳定**

B+ 树的所有数据都在叶子层，所以**任何一次查询的 IO 次数相同**
（都是树高）。B 树可能在非叶子节点就命中数据（更快）
也可能要走到叶子（更慢），性能有波动。

对数据库来说，**可预测的稳定性能比「有时更快」更重要**。

### 聚簇索引与二级索引

```sql
CREATE TABLE user (
    id   BIGINT PRIMARY KEY,    -- 主键
    name VARCHAR(32),
    age  INT,
    KEY idx_name (name)          -- 二级索引
);
```

**聚簇索引（主键索引）**：

```
叶子节点 = [id, name, age, ...整行数据]
```

数据**就存在索引的叶子节点里**，索引即数据。

**二级索引（辅助索引）**：

```
叶子节点 = [name, id]        ← 只有索引列 + 主键
```

**为什么二级索引的叶子要存主键**——用于回表定位整行。

### 回表

```sql
SELECT * FROM user WHERE name = 'Alice';
```

执行过程是**两步**：

```
① 在 idx_name 上找到 name = 'Alice' 的条目 → 拿到主键 id = 7
② 拿着 id = 7 回聚簇索引再查一次 → 拿到整行数据   ★ 这一步叫回表
```

**回表的代价**：一次二级索引查找 + 一次聚簇索引查找，
两次 B+ 树搜索。而且如果匹配的行很多，
回表次数会成倍增长。

### 覆盖索引（避免回表）

如果查询的所有列都在索引里，就不需要回表：

```sql
-- 只需要 name，而 idx_name 的叶子节点里有 name（和 id）
SELECT name FROM user WHERE name = 'Alice';
-- EXPLAIN 的 Extra 会显示 Using index  ← 覆盖索引

-- 需要 age，而 age 不在 idx_name 里
SELECT name, age FROM user WHERE name = 'Alice';
-- Extra 显示 NULL，需要回表
```

**优化手段**：把查询需要的列加进联合索引，制造覆盖索引。

```sql
-- 原来的查询需要回表
SELECT name, age FROM user WHERE name = 'Alice';

-- 建联合索引后变成覆盖索引，不必回表
ALTER TABLE user ADD KEY idx_name_age (name, age);
```

`EXPLAIN` 里 **`Extra = Using index`** 就是覆盖索引的标志。

**注意 `Using index` 和 `Using index condition` 的区别**：

- `Using index`：覆盖索引，**无需回表**（这行不需要去聚簇索引取数据）
- `Using index condition`：**索引下推**（ICP），
  条件下推到引擎层过滤，减少回表次数，但**仍可能回表**

### 最左前缀原则

联合索引 `(a, b, c)` 的排序方式：

```
先按 a 排序；a 相同则按 b 排序；a、b 都相同则按 c 排序
```

所以只有**从最左列开始的连续前缀**才能用上索引：

| 查询条件 | 能否用索引 | 用到哪些列 |
|---|---|---|
| `WHERE a = 1` | ✔ | a |
| `WHERE a = 1 AND b = 2` | ✔ | a, b |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✔ | a, b, c |
| `WHERE b = 2` | ✗ | 用不上（没有 a 就无法定位） |
| `WHERE a = 1 AND c = 3` | 部分 | 只用到 a，c 用不上（跳过了 b） |
| `WHERE a = 1 AND b > 2 AND c = 3` | 部分 | 用到 a、b；**范围查询后面的列失效** |

**最后一行是关键细节**：`b > 2` 是范围查询，
在 B+ 树里 `b` 之后的顺序不再是全局有序的
（`b` 相同的范围内 `c` 才有序，但范围扫描会跨越多个 `b` 值），
所以 `c` 无法用于索引定位。

**实践结论**：联合索引的列顺序应该是
**等值查询列在前，范围查询列在后**。

### 索引下推（ICP）

MySQL 5.6 引入的优化。对比一下有无 ICP 的执行过程：

```sql
SELECT * FROM user WHERE name LIKE '张%' AND age = 25;
-- 联合索引 idx_name_age (name, age)
```

**没有 ICP（5.6 之前）**：

```
① 在 idx_name_age 上找到所有 name LIKE '张%' 的主键
   假设有 1000 条记录
② 对这 1000 个主键逐个回表，取出整行
③ 在 Server 层过滤 age = 25，假设只剩 10 条
→ 回表 1000 次，其中 990 次是浪费的
```

**有 ICP（5.6+）**：

```
① 在 idx_name_age 上找 name LIKE '张%'，
   同时判断索引里已有的 age 是否等于 25     ★ 条件下推到引擎层
   只留下满足两个条件的 10 个主键
② 对这 10 个主键回表
→ 回表 10 次，减少 99%
```

关键在于 `age` 就在索引里，所以**不必回表就能判断**。
引擎层过滤后，回表次数大幅下降。

`EXPLAIN` 里 **`Extra = Using index condition`** 就是启用了 ICP。

**ICP 的适用条件**：

- 需要联合索引（被下推的列必须在索引里）
- 适用于 `range`、`ref`、`eq_ref`、`ref_or_null` 访问类型
- 对 InnoDB 有效（MyISAM 不支持）

### 索引失效的常见情况

| 写法 | 为什么失效 |
|---|---|
| `WHERE name LIKE '%张'` | 前导 `%` 无法利用有序性定位起点 |
| `WHERE YEAR(create_time) = 2026` | 对索引列用函数，B+ 树里存的是原值不是函数结果 |
| `WHERE age + 1 = 26` | 对索引列做运算，同上 |
| `WHERE name = 123` | 隐式类型转换（`name` 是 varchar，传入数字），相当于对列做 `CAST` |
| `WHERE a = 1 OR b = 2`（b 无索引） | OR 的一侧无法用索引，整体退化为全表扫描 |
| `WHERE a IS NOT NULL`（区分度低） | 优化器判断走索引不如全表扫（回表成本高于顺序读全表） |

**关于 `LIKE '张%'` 为什么能用索引**：
B+ 树按字典序排列，前缀匹配可以定位到一个起点，
然后顺着叶子链表向右扫。而 `'%张'` 没有确定的起点，只能全扫。

**关于「区分度低」**：索引的选择性是
`不重复值 / 总行数`。如果一个列只有 `性别`（2 个值）
这种低区分度数据，优化器会认为「走索引还要回表，
不如直接全表扫描顺序读」——这是**成本估算的结果，不是索引失效**。
`EXPLAIN` 看到 `type = ALL` 但 `possible_keys` 有值时，
通常就是这种情况。

### EXPLAIN 的关键列

```sql
EXPLAIN SELECT * FROM user WHERE name = 'Alice' AND age = 25;
```

| 列 | 关注点 |
|---|---|
| `type` | **最重要**。访问类型，从好到坏：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。至少要到 `range`，出现 `ALL` 要警惕 |
| `key` | 实际使用的索引。为 `NULL` 说明没走索引 |
| `key_len` | 使用的索引字节数。**用它可以判断联合索引用到了几列** |
| `rows` | 预估扫描行数。越小越好 |
| `filtered` | 按条件过滤后剩余的百分比 |
| `Extra` | `Using index`（覆盖索引）、`Using index condition`（ICP）、`Using filesort`（额外排序，要优化）、`Using temporary`（临时表，要优化） |

**`key_len` 怎么算**（判断联合索引用到几列的关键）：

```
一个 INT 在 utf8mb4 下：NOT NULL → 4 字节
                       可为 NULL  → 5 字节（多一个 NULL 标记字节）
一个 VARCHAR(32) utf8mb4：32 × 4 = 128 字节
                          + 2 字节长度前缀
                          (+ 1 字节 NULL 标记，如果可为 NULL)
```

例：联合索引 `(name VARCHAR(32) NULL, age INT NULL)`

```
只用 name      → 128 + 2 + 1 = 131
name + age     → 131 + 4 + 1 = 136
```

看到 `key_len = 131` 就知道只用到 `name`，`age` 没起作用。

## 追问链

### Q1: 为什么 InnoDB 必须有主键？主键为什么不宜过长？

**为什么必须有**：因为 InnoDB 是**索引组织表**
（Index-Organized Table）——数据就存放在聚簇索引的叶子节点里。
没有主键就没有聚簇索引，也就没有存放数据的地方。

InnoDB 的选择顺序是：

```
① 用户显式定义的主键
② 没有主键 → 选第一个「所有列都 NOT NULL 的唯一索引」当主键
③ 都没有   → 生成一个 6 字节的隐藏主键 DB_ROW_ID
```

第 ③ 种情况**应该避免**：因为
- 隐藏主键全局递增，**高并发插入会造成页分裂热点**
- 无法显式使用（你无法 `WHERE DB_ROW_ID = ...`）
- 后续加主键要重建整张表

**为什么主键不宜过长**：因为**所有二级索引的叶子节点都存主键**。

```
主键 BIGINT（8 字节）  → 每个二级索引条目 8 字节主键
主键 CHAR(36) UUID     → 每个二级索引条目 36 字节主键（+长度前缀）
```

假设表有 4 个二级索引、1000 万行：

```
BIGINT：8 × 1000 万 × 4 = 320 MB 用于存主键
UUID  ：36 × 1000 万 × 4 = 1440 MB  ← 多出 1.1 GB
```

**连带影响**：二级索引页能放的条目变少 → 索引树变高 →
查询 IO 增加；缓存命中率下降；插入时页分裂更频繁。

**这也是为什么推荐自增 `BIGINT` 主键**：

- 自增让新数据**总是追加到最右侧叶子页**，
  是顺序写，页分裂少
- 8 字节，作为二级索引的引用足够紧凑

**UUID 的问题是双重的**：既有体积问题，
又因为**随机分布导致插入位置随机**，会引起大量页分裂和碎片。

如果业务必须用 UUID，折中方案是：
用 UUID 做业务唯一键（加唯一索引），
同时保留自增主键做聚簇索引。

#### Q1.1: 那自增主键就没有缺点吗？

有一个真实的缺点：**并发插入的热点竞争**。

自增主键的插入总是发生在最右侧的叶子页，
所以**所有写请求都竞争同一个页的锁**。
在极高的并发写入下，这可能成为瓶颈。

另外还有两个工程上的问题：

**问题一：分库分表后不适用**

单机自增在多库多表下会冲突，需要改用分布式 ID：

```
雪花算法（Snowflake）：时间戳 + 机器 ID + 序列号
号段模式（如美团 Leaf）：一次取一批 ID 缓存在应用内存
Redis INCR：简单但依赖 Redis 可用性
```

这些方案生成的 ID **不再是严格单调递增**（雪花算法整体趋势递增
但有跳跃），所以还是会有些页分裂，不过比 UUID 好得多。

**问题二：敏感信息泄露**

自增 ID 会暴露业务量：

```
GET /api/orders/1001     ← 用户 1001 的第 1 单
GET /api/orders/1002
```

攻击者能推断出总订单量，还能横向越权遍历。
解法是**对外暴露一个不带顺序语义的 ID**
（比如加密后的 ID、或额外的 `order_no` 业务号）。

**注意：这属于接口设计问题，不该通过改主键类型来解决**。
用 UUID 做数据库主键来防遍历，付出的是索引膨胀的巨大代价，
得不偿失。

##### Q1.1.1: 那为什么二级索引要存主键而不是直接存行地址？

因为**行地址会变，主键不会**。

如果二级索引存的是「物理行地址」（类似 MyISAM 的做法）：

```
二级索引 → [name='Alice', 行地址=0x1A2B]
```

一旦发生以下操作，行地址就失效了：

- **页分裂**：数据在页之间移动
- **行迁移**：行变大超过页剩余空间时被挪到新页
- **表重建**：`ALTER TABLE`、`OPTIMIZE TABLE`
- **分区重分布**

那就必须**更新所有二级索引里的地址**，
这是一次全表级别的索引维护，代价极大。

而主键是不变的（业务上主键不会更新），
所以「二级索引 → 主键 → 聚簇索引」这条链路是稳定的。

**代价是查询时多一次「回表」**，但这换来的是
**写入时不必维护所有索引的物理地址**。
读写权衡下，这个选择是合理的——
毕竟读可以通过覆盖索引优化，而写放大无法避免。

**MyISAM 就是存行地址的**，它的索引和数据的分离结构
让「行地址」有意义（数据文件独立于索引文件）。
但它也因此不支持聚簇索引，且表数据损坏后的修复更麻烦。
这也是 InnoDB 取代 MyISAM 的原因之一。

### Q2: 什么叫「索引选择性」？怎么决定要不要建索引？

**选择性 = 不重复值数量 / 总行数**，越接近 1 越好。

```sql
-- 查看某列的选择性
SELECT
    COUNT(DISTINCT name) / COUNT(*) AS name_selectivity,
    COUNT(DISTINCT gender) / COUNT(*) AS gender_selectivity
FROM user;
-- name_selectivity ≈ 0.99   → 适合建索引
-- gender_selectivity ≈ 0.000001 → 不适合
```

**为什么低选择性不适合**：假设 1000 万行、性别只有 2 个值：

```
WHERE gender = 'M'  → 命中 500 万行
走索引：找到 500 万个主键（随机分布在索引页里）
      → 回表 500 万次，每次都是随机 IO
      → 比顺序全表扫描还慢
```

优化器的成本模型会算出这一点，所以选择全表扫描。
**这是「索引没被用」的最常见原因，而不是索引失效**。

**判断标准（经验值）**：

```
选择性 < 0.1  → 单独建索引通常意义不大
选择性 > 0.3  → 单独建索引通常有用
```

但这个经验值要结合查询模式看，而不是机械套用。

**几个实践要点**：

**① 联合索引的选择性看组合**

```sql
-- 单列选择性都低，但组合起来很高的情况很常见
-- 比如 (city, gender, age_range)
SELECT COUNT(DISTINCT city, gender, age_range) / COUNT(*) FROM user;
```

**② 把选择性高的列放前面**

联合索引 `(a, b)` 中，`a` 决定了树的第一层划分。
如果 `a` 的选择性高，第二层的 `b` 就能在更小的范围内区分——
树的层数更少、扫描更少。

不过这个规则的优先级**低于**「等值列在范围列之前」。
当两者冲突时，先满足「等值在前」。

**③ 不要盲目加索引**

每个索引都要在写入时维护：

```
INSERT  → 每个索引都要插入一条（可能触发页分裂）
UPDATE  → 改动的列若是索引列，相关索引都要更新
DELETE  → 每个索引都要标记删除
```

**一般建议单表索引不超过 5~6 个**，写密集的表要更少。

**④ 用真实数据验证**

```sql
-- 看优化器的成本估算
EXPLAIN SELECT ...;

-- 看优化器为什么选了这个索引
EXPLAIN FORMAT=JSON SELECT ...;

-- 实际执行并统计
EXPLAIN ANALYZE SELECT ...;   -- MySQL 8.0.18+
```

`EXPLAIN ANALYZE` 最有价值：它**真的执行**查询并对比
「预估行数 vs 实际行数」。当两者差距很大时，
说明统计信息不准（需要 `ANALYZE TABLE`）或条件估算有偏差。

#### Q2.1: 那什么时候该建联合索引，什么时候该建多个单列索引？

**优先联合索引**，因为 MySQL 的一条查询**只会用一个索引**
（除了 `index merge`，但效果通常不好）。

对比一下：查询 `WHERE name = ? AND age = ?`

```
方案 A：两个单列索引 idx_name、idx_age
  → 优化器只能用其中一个
  → 假设用 idx_name 命中 1000 行，回表后再过滤 age
  → 回表 1000 次

方案 B：联合索引 idx_name_age (name, age)
  → 两个条件都能在索引里判断
  → 假设命中 10 行，回表 10 次
  → 回表 10 次，快 100 倍
```

**联合索引的顺序原则**：

```
① 等值查询的列在前，范围查询的列在后
   (a, b, c) 中若 b 是范围，c 就用不上索引定位

② 等值列之间，选择性高的在前
   （在满足①的前提下）

③ 把 ORDER BY / GROUP BY 的列纳入索引
   这样可能直接利用索引的有序性，避免 filesort

④ 尽量让常用查询成为覆盖索引
   把 SELECT 需要的列也加进索引
```

**一个反直觉的实践：`(a, b)` 和 `(b, a)` 都需要吗？**

不需要重复建。`(a, b)` 已经能服务于：

```
WHERE a = ?              ✔（用 a）
WHERE a = ? AND b = ?    ✔（用 a、b）
WHERE b = ?              ✗（用不上）
```

只有当 `WHERE b = ?` 是高频查询时，才需要额外建 `(b)` 或 `(b, a)`。
**别为了「保险」把两种顺序都建上**——那是纯写入负担。

**index merge 的局限**：MySQL 有时会自动合并多个索引
（`EXPLAIN` 的 `type` 显示 `index_merge`），
但它通常意味着优化器没有合适的联合索引可用。
实践中 `index_merge` 的性能往往不如一个恰当的联合索引，
看到它应该考虑补一个联合索引。

## 常见坑

- **说「B+ 树因为平衡所以查询快」** ——
  平衡只是基础，**B+ 树的优势是「矮胖」**：
  非叶子节点只存键所以单页容量大、树高低、
  IO 次数少（三层千万行）
- **把 B 树和 B+ 树的区别说成「B+ 树数据都在叶子」就完了** ——
  更重要的是**非叶子节点不存数据让树更矮**，
  以及**叶子链表让范围查询可以顺序扫描**
- **认为主键索引和二级索引结构一样** ——
  聚簇索引叶子存整行，二级索引叶子存「索引列 + 主键」
- **把「回表」说成「查两次表」** ——
  回表是「二级索引 → 聚簇索引」的第二次 B+ 树查找
- **`Using index` 和 `Using index condition` 混为一谈** ——
  前者是覆盖索引（不回表），后者是索引下推（减少回表但仍可能回表）
- **说「加了索引就一定会用」** ——
  低选择性、函数操作、隐式类型转换、前导 `%` 都会让索引用不上；
  且优化器基于成本估算，可能主动选择全表扫描
- **`WHERE a = 1 AND b > 2 AND c = 3` 认为 c 也能用索引** ——
  范围查询后面的列无法用于索引定位
- **用 UUID 做主键只说「不好」不说原因** ——
  根因是「所有二级索引都要存主键」导致的索引膨胀，
  加上随机分布引起的页分裂
- **认为自增主键完美无缺** ——
  并发写入会竞争最右侧叶子页形成热点；
  分库分表下失效；还会暴露业务量

## 加分点

- 能**算出三层 B+ 树能存两千多万行**，把「矮胖」这个定性描述
  变成定量结论——这是最能体现理解的加分点
- 知道 `key_len` 的**计算方式**，并能用它判断联合索引
  实际用到了几列（比如 `key_len = 131` 说明 VARCHAR(32) 之后
  的列没生效）
- 能区分 **`Using index`（覆盖索引）与
  `Using index condition`（ICP）**，并说清 ICP
  是「把条件下推到引擎层以减少回表」而不是「避免回表」
- 提到 **InnoDB 是索引组织表**，并由此推出三条结论：
  必须有主键、二级索引叶子存主键、主键不宜过长
- 知道 **`EXPLAIN ANALYZE`（8.0.18+）会真正执行查询**，
  并对比预估行数与实际行数——差距大说明统计信息不准，
  需要 `ANALYZE TABLE`
- 能解释**为什么「索引没被用」不等于「索引失效」**：
  低选择性时优化器的成本估算会主动选择全表扫描，
  这时 `possible_keys` 有值但 `key` 为 NULL
- 提到**自增主键的热点竞争问题**，并给出分布式 ID 的替代方案
  （雪花算法、号段模式），说明这是分库分表后的必然演进
- 知道 **MyISAM 存行地址而 InnoDB 存主键**，
  并解释为什么行地址会因页分裂、行迁移、表重建而失效——
  由此说明 InnoDB 的选择是为了「写不放大」

## 版本差异

| 版本 | 差异 |
|---|---|
| MySQL 5.5 | InnoDB 成为默认存储引擎，聚簇索引结构被广泛使用 |
| MySQL 5.6 | **引入索引下推（ICP）**，`Extra` 出现 `Using index condition` |
| MySQL 5.7 | 引入虚拟列与虚拟列索引；`optimizer_trace` 可用于分析优化器决策 |
| MySQL 8.0 | 引入**降序索引**（`DESC` 索引真正生效，5.7 及之前会被忽略）；隐式类型转换的告警更明确 |
| MySQL 8.0 | 引入**直方图统计**（`ANALYZE TABLE ... UPDATE HISTOGRAM`），改善非索引列的选择性估算 |
| MySQL 8.0.18 | `EXPLAIN ANALYZE` 可用，能对比预估与实际行数 |
| MySQL 8.0 | 默认字符集改为 `utf8mb4`，影响索引字节数计算（每个字符 4 字节） |
