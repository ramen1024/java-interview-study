## 电梯版回答

主从复制的链路是三段：主库的 binlog dump 线程把 binlog 推给从库，从库的 IO 线程把收到的事件写进 relay log，再由 SQL 线程回放成数据变更。延迟的根因是从库回放速度跟不上主库写入，MySQL 5.6 及之前从库只有一个 SQL 线程，大事务和写并发一高就落后；5.7 起可以用基于组提交的并行复制，让互不冲突的事务在从库并行回放。半同步复制只保证至少一个从库收到 binlog 并落盘，不保证已经回放完，所以它降低丢数据风险但消不掉延迟。分库分表分垂直和水平：垂直按业务或字段拆，水平按行拆。分片键要能覆盖大多数查询、分布均匀、尽量不跨片；一旦拆了，跨片 JOIN 与聚合、深分页、分布式 ID、分布式事务都要额外处理。最重要的一条：拆之前必须先把索引和 SQL 优化到位，单表千万级配合合适索引往往还够用，分库分表是最后手段而不是第一反应。

## 展开讲解

### 主从复制的链路

```
主库（master）
  └─ 事务提交 → 写 binlog
  └─ binlog dump 线程：读 binlog，通过网络发给从库

从库（slave/replica）
  └─ IO 线程：接收事件，写入本地 relay log（中继日志）
  └─ SQL 线程：读 relay log，回放成数据变更
```

三个线程各司其职：

| 线程 | 位置 | 职责 |
|---|---|---|
| binlog dump | 主库 | 监听 binlog 变化，推送给从库；每个从库连接一个 |
| IO（replica_io） | 从库 | 拉取 binlog 写入 relay log，同时记录已拉到的位点 |
| SQL（replica_sql） | 从库 | 按顺序回放 relay log 里的变更 |

命令与状态观察：

```sql
SHOW REPLICA STATUS\G
-- Replica_IO_Running: Yes
-- Replica_SQL_Running: Yes
-- Seconds_Behind_Source: 12        -- 5.7 及之前叫 Seconds_Behind_Master
-- Relay_Source_Log_File / Read_Source_Log_Pos
```

`binlog_format` 决定 binlog 内容：`STATEMENT`（记 SQL，函数/随机数会不一致）、
`ROW`（记每行前后镜像，主从一致性最好，binlog 更大）、`MIXED`（按语句自动切换）。
主从复制默认是**异步**的：主库提交事务后不等从库，所以主库宕机可能丢还没传过去的 binlog。

### 主从延迟

**成因**，按出现频率排：

1. **从库回放慢**（最核心）。5.6 及之前从库只有**一个 SQL 线程**，
   主库却可以多线程并发写。回放能力是单线程的，写入并发一高就必然堆积。
2. **大事务**。一个事务更新几十万行，binlog 里是一坨事件，
   从库必须整块串行回放；期间 `Seconds_Behind_Source` 会持续上升。
   典型的坑是 `DELETE FROM big_table WHERE ...`（无条件大批量删除）。
3. **从库本身压力大**。读写分离后从库承担大量查询，甚至还有备份、
   统计任务在跑；从库硬件通常还比主库差。
4. **锁等待**。回放时如果和从库上的长查询/长事务抢行锁，SQL 线程会被阻塞。
5. **网络延迟**。
6. **从库还要写自己的 binlog**（开了 `log_replica_updates` 时），
   相当于把主库的写入又做了一遍。

**后果**：读写分离下「**刚写完就读不到**」。写走主库、读走从库，
在延迟窗口内从库还没回放完，读到的就是旧值。严重时不是"显示旧数据"这种小事，
而是业务判断错误，例如下单后立即查状态判定失败、支付成功后查不到订单。

**监控**：`Seconds_Behind_Source` 是常用指标，但它**不等于真实延迟**——
它只反映 SQL 线程当前回放的事件时间戳与 IO 线程已收到的最新事件时间戳之差，
当 IO 线程空闲（没拉到新事件）时它可能显示 0，而实际从库仍在落后。
更可靠的是 `pt-heartbeat`：在主库定期更新时间戳表，从库读这个表算差。

**应对**：

| 手段 | 说明 | 适用 |
|---|---|---|
| 强制走主库 | 写后一段时间内（如 1s）的读打回主库 | 简单有效，最常用 |
| 等待位点 | 拿到主库位点/GTID，在从库执行 `SELECT WAIT_FOR_EXECUTED_GTID_SET(gtid, timeout)`（5.7+）或 `MASTER_POS_WAIT()` | 对一致性敏感的读 |
| 缓存标记 | 写成功后往 Redis 写一个短 TTL 标记，读时发现标记就回主库 | 读多写少 |
| 半同步复制 | 至少一个从库确认收到才返回，缩小窗口 | 降低丢数据风险，不消除回放延迟 |
| 并行复制 | 从库多线程回放 | 直接提升回放吞吐 |

关键认知：**延迟只能减小、无法消除**（异步复制语义下）；
要业务上不踩坑，还是要靠「关键读走主库」这类应用层策略。

### 并行复制：为什么能安全并行

从库回放的难点是**不能乱序**——同一行上的两个事务并行回放会得到错误结果。
5.7 引入的 `LOGICAL_CLOCK` 策略给出了一个安全的并行依据：**组提交（group commit）**。

主库在刷 binlog 时会把同时进入 prepare/commit 阶段的一批事务编成一组，
它们既然能在主库同组提交，就说明这组内的事务在**主库上不冲突**
（顺序由组内顺序保证）。从库据此可以把组内事务分给多个 worker 并行回放：

```sql
-- 5.7 及 8.0 早期写法
SET GLOBAL slave_parallel_type = 'LOGICAL_CLOCK';
SET GLOBAL slave_parallel_workers = 8;          -- 默认 0，即关闭并行

-- 8.0.26 起推荐的新名字（旧的 slave_* 仍可用但已废弃）
SET GLOBAL replica_parallel_type = 'LOGICAL_CLOCK';
SET GLOBAL replica_parallel_workers = 8;
```

另一个值 `DATABASE` 只对「操作不同库」的事务并行，粒度太粗，效果有限。

还有两个配合项：

- `replica_preserve_commit_order = ON`：保证并行回放后从库的提交顺序
  与主库一致（否则从库上可能出现「后提交的事务先可见」）。用 LOGICAL_CLOCK
  时通常要打开。
- `binlog_group_commit_sync_delay` / `binlog_group_commit_sync_delay_count`：
  主库上人为延迟一点再组提交，让组更大，从库并行度更高——
  代价是主库提交变慢，属于用主库延迟换从库吞吐的调节项。

版本要点：MySQL 5.7 引入 LOGICAL_CLOCK；`replica_parallel_workers`
在 8.0.27 之前默认 0（并行关闭），**MySQL 8.0.27 起默认值为 4，
从库默认就是多线程回放**。

### 半同步复制

异步复制在「主库提交成功但 binlog 还没传给从库」时主库宕机就会丢数据。
半同步在中间取了一档：

```
主库提交 → 写 binlog 并 fsync 到磁盘 → 等至少一个从库 ACK
        → 收到 ACK 才提交到存储引擎并返回客户端
```

关键点：

- 从库的 ACK 表示**事务的 binlog 事件已经写入 relay log 并刷盘**，
  不是「已经回放完成」——所以半同步不影响回放延迟，也不保证从库读到的数据是新的。
- 等待点由 `rpl_semi_sync_master_wait_point`（8.0.26 起 `rpl_semi_sync_source_wait_point`）
  控制，默认 **`AFTER_SYNC`**：先同步 binlog 到磁盘、收到 ACK 前**不**提交到存储引擎。
  5.6 的 `AFTER_COMMIT` 是提交后再等 ACK，可能在等待期间主库宕机导致
  「主库已提交、从库没收到」的数据丢失，5.7 起默认改成 `AFTER_SYNC` 成为所谓
  "lossless semisync"。
- 超时参数 `rpl_semi_sync_master_timeout` 默认 **10000 毫秒（10 秒）**：
  超时后主库**自动降级为异步复制**，等从库追上来再恢复。这意味着故障时刻
  半同步可能已经悄悄退化成异步。
- 需要主从两端都装插件并开启（`rpl_semi_sync_source_enabled` 默认 0），
  等待的从库数量由 `rpl_semi_sync_source_wait_for_replica_count` 控制，默认 1。

### 分库分表

**垂直拆分**：按业务边界拆库（订单库、用户库、商品库），
或按字段拆表（把 `TEXT`、大 `VARCHAR` 等冷字段挪到扩展表，
主表变窄后单页能放更多行，扫描更快）。垂直拆分解决的是"表太宽、库太杂"，
通常最先做。

**水平拆分**：按行拆，同一张表的数据分散到多个库/表。
分片算法有三种：

```
范围（range）   ：id 0~1000万 一片，1000万~2000万 一片
                  优点：范围查询友好、扩容简单；缺点：热点集中在最新分片
哈希取模（hash） ：shard = hash(key) % N
                  优点：分布均匀；缺点：扩容要重新分布（除非一致性哈希）
一致性哈希      ：节点变化时只迁移相邻区间，扩容代价小，但实现更复杂
```

**分片键选择的原则**：

- **能覆盖大多数查询**。分片键最好就是高频查询的等值条件，
  这样查询能定位到单片；否则每次都要广播到所有分片。
- **分布均匀**。避免用性别、状态这类低基数列，否则数据全挤在一片。
- **尽量不跨片**。选「同一个业务聚合根的公共字段」，
  例如订单表按 `user_id` 分片，用户的订单就都在同一片，
  查「某用户的订单列表」永远单分片。
- **尽量不可变**。分片键一改就要跨片迁移数据，代价极高。
- 能确定全局唯一、最好还趋势递增的更好，配合分布式 ID。

**跨片查询与聚合的代价**（这是分片后最难受的部分）：

```sql
-- 没有分片键的查询：要广播到所有分片
SELECT * FROM orders WHERE status = 'PAID';

-- 聚合要各分片算完再归并
SELECT COUNT(*), SUM(amount) FROM orders;   -- 每个分片算局部结果，中间件求和
SELECT * FROM orders ORDER BY create_time DESC LIMIT 10;
-- 每个分片各取 10 条，中间件归并排序后再截取 10 条
```

跨片 JOIN 基本等于灾难（要么冗余字段，要么在应用层拼装），
所以分片设计要尽量让关联数据落在同一片（比如订单和订单明细都用 `user_id` 分片）。

**深分页问题**：`LIMIT offset, size` 的代价随 offset 线性增长，
在分片下更严重。假设 3 个分片，查 `LIMIT 100000, 10`：

```
每个分片必须返回前 100010 条（因为它无法知道全局第 100000 条在哪）
中间件归并 3 × 100010 ≈ 30 万条，排序后丢弃 100000 条，只留 10 条
```

30 万行数据只换来 10 行结果。解决办法：

- **游标/键集分页**：`WHERE id > 上一页最后一个 id ORDER BY id LIMIT 10`。
  每个分片只需返回 10 条，中间件归并 30 条即可，代价与页码无关。
  前提是分片键/主键全局有序（雪花 ID 很适合）。
- **二次查询法**：第一轮各分片按条件各取 `offset/N + size` 条确定边界，
  第二轮用边界值精确回查，减少第一轮的数据量。
- 产品上禁止跳页，只允许上一页/下一页。

### 分布式 ID

自增主键在分库分表下失效：多个库各自自增会撞 ID，
就算用「步长 2 错开」也只适用于固定分片数，且不再是全局单调。

| 方案 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 雪花算法 | 时间戳 + 机器 ID + 序列号 | 本地生成、趋势递增、性能高 | 依赖时钟，时钟回拨会重复 |
| 号段模式 | 一次从 DB 取一批 ID 缓存在内存 | 不依赖时钟、趋势递增、DB 压力小 | 依赖 DB 可用性，重启会浪费未用完号段 |
| Redis INCR | 集中发号 | 简单 | 依赖 Redis 可用性，多一次网络往返 |
| DB 自增表 | 单独建发号表 | 简单、严格递增 | 单点瓶颈、性能差 |

**雪花算法（Snowflake）**是 64 位 long，典型布局：

```
0 | 41 位毫秒时间戳 | 10 位机器 ID | 12 位序列号
  | 约可用 69 年     | 1024 个节点  | 同一毫秒 4096 个
```

（不同实现的分位可调，但 41/10/12 是 Twitter 原版的经典划分。）两个实战问题：
**时钟回拨**（NTP 校时、虚拟机迁移导致时间倒退，可能生成重复 ID，
需要检测回拨并等待/报警/换机器位），以及**机器 ID 分配**（通常靠
ZooKeeper/etcd/配置中心保证不重复）。

号段模式（美团 Leaf-segment 思路）的核心：

```sql
UPDATE leaf_alloc SET max_id = max_id + step WHERE biz_tag = 'order';
SELECT max_id FROM leaf_alloc WHERE biz_tag = 'order';
```

一次取一批（比如 step=1000）缓存在应用内存里，用完再取。
「双 buffer」指当前号段用到一定比例就异步预取下一个号段，
避免取号段时的请求阻塞。

### 分布式事务的几种思路

| 方案 | 思路 | 主要问题 |
|---|---|---|
| 2PC / XA | 协调者 prepare 所有参与者，全 OK 再 commit | **同步阻塞**：prepare 后资源被锁到 commit，协调者宕机则参与者长期持锁；MySQL 可用 `XA RECOVER` 查悬挂事务 |
| TCC | 业务层 Try 预留、Confirm 确认、Cancel 取消 | 业务侵入大，必须处理幂等、空回滚、悬挂 |
| Saga | 长事务拆成一串本地事务，失败则反向补偿 | 无隔离性，中间状态对外可见，补偿逻辑要写全 |
| 本地消息表 | 业务表和消息表在同一本地事务里写入，再由定时任务/异步线程投递 | 最终一致，实现简单，但表会膨胀、需要重试与幂等 |
| MQ 事务消息 | 先发半消息，本地事务成功后提交消息 | 依赖 MQ 能力，消费端仍要幂等 |
| 最大努力通知 | 主动重试通知，通知不到就靠对方主动查询对账 | 不保证强一致，适合对账类场景 |

工程上的排序建议是：**先想办法不用分布式事务**。把跨库操作改成
「同一个分片键下的单库事务」，或者用状态机 + CAS 让操作天然幂等，
比引入 XA/TCC 划算得多。XA 的阻塞问题在互联网高并发场景下基本不可接受。

### 什么时候不该分

分库分表的代价不只是"多写几行代码"：

- 跨片 JOIN、跨片聚合、全局排序分页都要额外实现
- 分布式事务与全局一致性
- 扩容要迁移数据（resharding），停机窗口和双写方案都很麻烦
- 中间件选型、分片规则变更、全局唯一 ID、运维复杂度全面上升

所以顺序应该是：

```
① 优化索引与慢 SQL（EXPLAIN、覆盖索引、避免回表）
② 优化表结构（垂直拆字段、合适的字段类型、冷热分离）
③ 读写分离、加缓存
④ 归档历史数据（热表只留近期数据）
⑤ 仍然扛不住，再考虑水平分库分表
```

单表到底能放多少行没有硬阈值：B+ 树三层就能容纳约两千万行，
单表千万级只要索引合适通常够用。业界常说的「500 万到 2000 万出现拐点」
是经验统计，取决于行宽、索引数量、访问模式和硬件——比这个数字更应该关注的是：
`ALTER TABLE` / 加索引的耗时、备份恢复窗口、单表容量与写入 QPS 是否真的到了瓶颈。

## 追问链

### Q1: 主从复制有延迟，从库到底卡在哪一步？

卡在**回放**这一步，而且多数时候不是网络也不是磁盘慢。

把链路拆开看：IO 线程负责把 binlog 拉回来写 relay log，
SQL 线程负责把 relay log 回放成数据变更。这两步是独立的，
所以会出现「IO 线程已经追平主库（relay log 里堆着大量未回放事件），
SQL 线程还在慢慢追」的状态——`Replica_IO_Running = Yes`、
`Replica_SQL_Running = Yes`，但延迟持续上升。

SQL 线程慢的根本原因是它**单线程串行**，而主库可以并发提交。
主库 8 个线程并发写，从库 1 个线程回放，吞吐比就是 8:1，
写入一上来延迟必然持续累积。大事务会把这个问题放大：
一个事务的 binlog 事件必须整块按序回放，中间不能插别的，
期间从库对其他事务完全停滞。

#### Q1.1: 那 5.7 的并行复制是怎么做到「安全并行」的？

靠**组提交**给出并行边界。

主库刷 binlog 时，会把同时进入提交阶段的一批事务编成一组一起刷盘。
关键推论是：**同一组内的事务在主库上是按组内顺序提交的，
组内不存在会让结果错乱的交叉**。从库据此可以认为组内事务彼此可并行，
把它们分给多个 worker 执行，而不同组之间保持顺序。

配置上就是：

```sql
SET GLOBAL replica_parallel_type = 'LOGICAL_CLOCK';
SET GLOBAL replica_parallel_workers = 8;
SET GLOBAL replica_preserve_commit_order = ON;
```

`LOGICAL_CLOCK` 就是"按逻辑时钟（组提交边界）划分并行单位"的意思。
对比另一个值 `DATABASE`：它只允许操作不同 database 的事务并行，
粒度太粗，同一库内的并发完全并行不了，所以实践里基本只用 LOGICAL_CLOCK。

一个反直觉的点：**主库的组越大，从库并行度越高**。所以主库上可以用
`binlog_group_commit_sync_delay` 人为攒一下再提交，让组变大来换从库吞吐——
但这是拿主库的提交延迟做交换，要按业务权衡。

##### Q1.1.1: 那并行度调大是不是就能解决延迟？

不是。有几种情况并行复制帮不上忙：

**① 大事务无法被拆分。** 一个事务（比如一次删 50 万行）在从库只能由
**一个 worker** 回放，并行度再高也没用。正确做法是把大事务拆成
小批量、多批次提交（`DELETE ... LIMIT 1000` 循环），
这既能减小从库回放抖动，也能减小主库锁范围。

**② 组本身就不大。** 如果主库写入并发低、每次提交组里只有一两个事务，
worker 再多也是空转。并行度要匹配实际的组大小，盲目调大反而增加调度开销。

**③ 瓶颈在从库的其他资源上。** 从库同时承担读查询、备份、统计任务时，
回放线程会和它们抢行锁、抢 CPU、抢磁盘 IO，SQL 线程会被锁等待卡住。
这时该做的是减轻从库读压力（给只读查询单独加从库、把备份放到延迟从库上），
而不是继续加 worker。

**④ 从库自己的 binlog 写入。** 开了 `log_replica_updates` 时，
从库回放完还要写自己的 binlog，相当于多做一遍写入。

所以延迟治理是组合拳：小事务化 + 并行复制 + 减轻从库压力 +
关键读走主库。另外 `relay_log_recovery = ON` 能在从库异常重启后
自动丢弃损坏的 relay log 并重新从主库拉取，避免回放中断在损坏位置上。

### Q2: 读写分离下「刚写完就读不到」，工程上怎么处理？

这是主从延迟在业务上的直接投影：请求 A 写主库成功，紧接着请求 B
（或同一个用户的下一个请求）读从库，从库还没回放完，读到旧值。

处理手段从简单到复杂：

**① 强制走主库**。最简单也最常用。做法是写操作后的一小段时间内，
该用户/该业务的读走主库。可以是硬编码（关键接口直接路由主库），
也可以是框架支持（ShardingSphere 的 `HintManager`、动态数据源注解）。

**② 等待位点**。写入时拿到主库的 GTID 或 binlog 位点，读之前先在从库上等：

```sql
SELECT WAIT_FOR_EXECUTED_GTID_SET('3E11FA47-71CA-11E1-9E33-C80AA9429562:23', 1);
```

超时参数单位是秒，返回是否在超时前已执行到该事务。这样能做到
「读至少能看到自己刚写的数据」，但会引入等待延迟。

**③ 缓存标记**。写成功后往 Redis 写一个带 TTL 的标记
（如 `read:force-master:{userId}`），读请求发现标记就把这次读路由到主库。
比固定时间窗口更精确，适合读多写少的场景。

**④ 业务上规避**。把「写后立即读同一份数据」的耦合去掉：
写操作直接返回需要的数据，或者读接口允许短暂旧值。这是最省事的做法，
很多场景其实并不需要读到自己刚写的数据。

选型逻辑：**先问业务能不能容忍旧值**。不能容忍的少数关键接口才上手段①或②，
不要给全站读都加等待位点，那样等于把从库的优势抵消掉了。

#### Q2.1: 那用半同步复制能不能保证从库读到的就是新数据？

不能。半同步解决的是「**主库已提交的事务会不会丢**」，
不是「**从库读到的数据新不新**」。

原因在于 ACK 的语义：从库确认的是**binlog 事件已写入 relay log 并刷盘**，
此时它还没有回放（SQL 线程可能还没开始处理这个事务）。
去从库读到的仍然是旧值。半同步把「丢数据窗口」缩小到
「至少一个从库收到」，但完全没有触碰回放延迟。

半同步还有两个容易忽略的点：

- **超时会降级。** `rpl_semi_sync_master_timeout` 默认 10 秒，
  超时后主库自动退回异步复制，直到从库追上才恢复半同步。
  所以「我开了半同步所以不丢数据」这个假设在故障时刻可能不成立。
- **AFTER_SYNC 与 AFTER_COMMIT 的差别。** 默认的 `AFTER_SYNC`
  先等 ACK 再提交到存储引擎，因此主库已提交的事务一定在至少一个从库上；
  5.6 的 `AFTER_COMMIT` 是提交后再等，等待窗口内主库崩溃会导致
  已提交事务丢失。5.7 起默认改为 `AFTER_SYNC`，这就是"无损半同步"。
- 只保证「至少一个」从库收到。如果唯一收到 binlog 的从库随后也坏掉、
  而其他从库没收到，仍可能丢数据。

结论：半同步提升的是**故障时的数据安全性**，不是读一致性。
读一致性要靠「读自己刚写的数据」这类应用层路由。

##### Q2.1.1: 那主从切换时怎么保证不丢数据、不脑裂？

分三块看：

**① 选主：谁的 binlog 最新谁当主。** 用 GTID 可以自动比对位点，
找到数据最全的从库提升。工具上 MHA、Orchestrator、MySQL Router、
云上的高可用组件都做这件事。GTID 的好处是位点不再依赖文件名+偏移量，
切换后其他从库能自动定位自己缺哪些事务。

**② 防止旧主「复活」造成脑裂。** 旧主只是网络分区而非宕机时，
它恢复后可能还在接受写入，出现两个主库。必须做隔离（fencing/STONITH）：
强制下掉旧主、或让旧主以 `read_only` / `super_read_only` 启动，
需要人工确认后才能重新加入。

**③ 兜底策略。** `replica_preserve_commit_order = ON` 保证从库提交顺序
与主库一致（否则即使数据不丢，可见顺序也可能错）。
开启半同步能大幅缩小「已提交但未传播」的窗口。对一致性要求更高的场景
可以直接上 MySQL Group Replication（MGR，基于 Paxos 的组复制），
它提供的是组内多数派确认，比半同步强一档，代价是写延迟更高。

一句话：**主从切换的正确性依赖"谁的数据最新"能被准确判断（GTID）
+ 旧主一定能被隔离（fencing）**，这两条缺一不可。

### Q3: 分库分表怎么分？分片键怎么选？

先分类型：

- **垂直拆**：按业务拆库、按字段拆表。解决"库太杂、表太宽"，
  通常是第一步，改动小、收益直接。
- **水平拆**：按行拆到多库多表。解决"单表太大、写入 QPS 太高"，
  代价最大，放在最后一步。

分片键的选择是第一优先级的设计决策，原则：

```
① 覆盖大多数查询：分片键是常用查询的等值条件 → 查询能定位单片
② 分布均匀：避免性别/状态这类低基数列，否则数据倾斜
③ 尽量不跨片：同一个业务聚合根的公共字段（订单用 user_id）
④ 尽量不可变：改了分片键就要跨片迁数据
⑤ 类型尽量小：分片键会进入每个索引条目，越长索引越膨胀
```

反例很直观：订单表按 `order_id` 分片，查「我的订单列表」需要广播到所有分片
（因为不知道用户的订单散在哪些片）；改成按 `user_id` 分片，
这个查询就永远是单分片。代价是查单个订单 `WHERE order_id = ?` 反而要广播——
所以现实里常用**基因法**：把 `user_id` 的低位嵌进 `order_id` 的某些位，
让两个查询都能定位到同一片。

跨片代价都要提前算清：跨片 JOIN 基本不可用，跨片聚合要各分片算局部值再归并，
跨片排序分页要归并后截断。**分片键选错，后面所有查询都会难受**。

#### Q3.1: 为什么不能再用数据库自增主键？分布式 ID 怎么生成？

多库多表下自增会撞：库 A 生成 id=1，库 B 也生成 id=1。
「不同表设不同起始值 + 相同步长」只能应付固定分片数，扩容时立刻失效，
而且 ID 不再全局单调递增。另外自增 ID 对外暴露时会被遍历、暴露业务量
（`/orders/1001`、`/orders/1002`），这是个独立的接口设计问题。

主流方案：

**雪花算法**：64 位 long = 1 位符号（恒 0）+ 41 位毫秒时间戳
+ 10 位机器 ID + 12 位序列号。41 位约能用 69 年，10 位支持 1024 个节点，
12 位支持同一毫秒 4096 个 ID。本地生成、无网络开销。
坑是**时钟回拨**：NTP 校时或虚拟机迁移让时间倒退会产生重复 ID，
需要检测回拨（等待或报警或借用保留位）；机器 ID 也要靠额外机制分配。

**号段模式**：DB 里存 `(biz_tag, max_id, step)`，应用一次取一批
（`UPDATE ... SET max_id = max_id + step`）缓存在内存，用完再取。
不依赖时钟、DB 压力小（取一次管很多个）。
坑是应用重启会浪费当前号段（可用双 buffer 预取缓解）、强依赖 DB 可用性。

选择上：**能接受趋势递增就雪花**（分片键用主键时趋势递增对 B+ 树插入友好，
避免随机插入造成的页分裂）；**对时钟敏感、或想要更简单的实现就号段**。
两者都不保证严格连续，中间会有空洞——本来就不该把 ID 连续性当业务能力。

##### Q3.1.1: 那分片之后，跨片的写事务怎么办？

先强调顺序：**优先想办法避免跨片事务，而不是挑一个分布式事务框架。**

能避免的典型做法：

```
① 分片键选对 → 相关数据同片 → 单库本地事务就够
   例如订单、订单明细、支付记录都用 user_id 分片
② 状态机 + CAS → 天然幂等，不需要"回滚"
   UPDATE ... SET status='PAID' WHERE id=? AND status='PENDING'
③ 把跨库操作改为"最终一致"：本地消息表 / MQ 事务消息 + 消费端幂等
```

如果确实需要，几种方案的取舍：

- **XA / 2PC**：prepare 后资源被锁到 commit，参与者在此期间持锁，
  并发直接下降；协调者宕机还会留下悬挂事务（MySQL 用 `XA RECOVER` 查）。
  高并发互联网场景基本不用它。
- **TCC**：把每个参与方的操作拆成 Try（预留资源）/ Confirm / Cancel。
  一致性较好、性能优于 XA，但业务侵入大，必须实现幂等、空回滚防护、
  悬挂防护（Cancel 比 Try 先到时要有记录挡住后续 Try）。
- **Saga**：把长事务拆成一串本地事务，失败就反向补偿。
  无隔离性——中间状态对外可见，补偿逻辑要覆盖所有失败分支。
  适合流程长、对中间态不敏感的业务（旅行订票类）。
- **本地消息表 / MQ 事务消息**：追求最终一致，实现相对简单，
  但消费端必须幂等（这是硬要求，不是可选项）。

实务上的判断标准：**能不能接受最终一致**。能，就用消息/补偿类方案
（复杂度可控）；不能，说明业务对强一致的要求很高，那应该优先
从分片键设计上把跨片事务消掉，而不是靠分布式事务硬撑。

## 常见坑

- **说「主从复制是同时复制数据和 binlog 的」** ——
  主库只发 binlog，从库靠回放 binlog 重建数据；
  没有"复制数据本身"这回事
- **把主从延迟简单归因于网络** —— 网络通常不是瓶颈，
  核心是**从库 SQL 线程单线程回放跟不上主库并发写**，
  以及大事务、从库压力、锁等待
- **说「半同步复制能保证从库读到最新数据」** ——
  ACK 只表示 binlog 写入 relay log 并落盘，**不代表已回放**；
  读到新数据要靠读主库或等待位点
- **说「开了半同步就绝不丢数据」** ——
  默认超时 10 秒后会自动降级为异步；
  且只保证「至少一个」从库收到，该从库也坏掉时仍可能丢
- **以为 `Seconds_Behind_Source` 是精确延迟** ——
  它只在 IO 线程有积压时才有意义，IO 线程空闲时可能显示 0 但实际仍落后；
  要精确测量用 `pt-heartbeat`
- **说「5.7 能并行复制就能解决所有延迟」** ——
  大事务在从库仍由单个 worker 串行回放，拆小事务用并行复制才有效
- **说「分库分表后还继续用数据库自增主键」** ——
  多库自增会撞 ID；需换雪花算法或号段模式
- **说「分片就是为了提高性能，先分再说」** ——
  分片的代价（跨片查询、分布式事务、扩容迁移、运维复杂度）
  常常大于收益；**先优化索引和 SQL、先垂直拆、先读写分离和归档**，
  单表千万级配合合适索引往往够用
- **分片键按「最常用的查询条件」随手选，不看分布和跨片** ——
  低基数列会导致数据倾斜，选错会导致大量查询变成广播
- **忽略深分页在分片下的放大** ——
  `LIMIT 100000, 10` 会让每个分片都返回 10 万条，
  中间件归并几十万条只留 10 条；必须改成游标分页或禁止跳页
- **认为 XA 是"标准方案所以更稳"** ——
  XA 的同步阻塞和悬挂事务问题在高并发下不可接受，
  能用最终一致或状态机就别用 XA

## 加分点

- 能画出**三段链路**并指出 IO 线程与 SQL 线程是独立的两段：
  「IO 已追平但 SQL 还在追」是延迟最常见形态，
  这解释了很多「`Replica_IO_Running` 是 Yes 为什么还延迟」的疑惑
- 能说清**半同步 ACK 的确切含义**（binlog 已落 relay log，不是已回放），
  以及 `AFTER_SYNC` 与 `AFTER_COMMIT` 的差别和默认值——
  这是区分「背过八股」和「真配过」的分界线
- 知道 **`LOGICAL_CLOCK` 的并行依据是组提交**，
  并能推出「主库组越大、从库并行度越高」，
  进而理解 `binlog_group_commit_sync_delay` 是用主库延迟换从库吞吐
- 提到 **`Seconds_Behind_Source` 的局限**，并举出 `pt-heartbeat`
  这个更准确的方案
- 能从**延迟的后果**推到应用层策略：强制走主库、等待位点
  （`WAIT_FOR_EXECUTED_GTID_SET`）、缓存标记，
  并说清「先问业务能否容忍旧值」的选型逻辑
- 分片键设计能讲到**基因法**（把 user_id 低位嵌进 order_id），
  让「按用户查」和「按订单查」都能定位单片——
  这是分片设计的实战细节
- 深分页能给出**量化例子**（3 分片 × 10 万条只换 10 行结果）
  和两种解法（游标分页、二次查询法），而不是只说"分页有性能问题"
- 能主动说「**分库分表是最后手段**」，并给出正确的优化顺序
  （索引 → 表结构 → 缓存/读写分离 → 归档 → 才分片）
- 分布式事务能指出**XA 的阻塞与悬挂事务**，
  并强调「能不用分布式事务就不用」——按分片键让相关数据同片是
  最优雅的"分布式事务解决方案"

## 版本差异

| 版本 | 差异 |
|---|---|
| MySQL 5.5 | 引入半同步复制插件，**没有** `AFTER_SYNC`，只有提交后等待 |
| MySQL 5.6 | 引入 GTID；从库仍是单 SQL 线程，延迟问题突出 |
| MySQL 5.7 | 引入基于**组提交**的并行复制 `LOGICAL_CLOCK` 与 `slave_preserve_commit_order`；半同步默认等待点改为 **`AFTER_SYNC`**（无损半同步）；`WAIT_FOR_EXECUTED_GTID_SET()` 可用 |
| MySQL 8.0.22 | 复制术语更新：`START SLAVE` / `SHOW SLAVE STATUS` 等语句与字段开始改用 `REPLICA` 命名，旧写法保留但废弃 |
| MySQL 8.0.26 | 半同步插件变量改用 source/replica 命名（`rpl_semi_sync_source_timeout`、`rpl_semi_sync_source_wait_point` 等），旧 `master` 版本插件不能与新版本同时安装 |
| MySQL 8.0.27 | `replica_parallel_workers` **默认值改为 4**，从库默认开启多线程回放（此前默认为 0，即关闭） |
